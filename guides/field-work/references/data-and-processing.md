# 情報の形と、行う処理を分ける

行列や固定項目の情報、自由な文章や画像、キーやタグで整理された情報では扱い方が違う。ただし、ファイル単位の分類だけで実装方式は決まらない。
JSONに固定IDと自由記述が混ざる、PDFに表と文章がある、といった部分ごとの構造を見る。JSON自体はデータ交換形式で、契約によって厳密な項目定義にもできる。

正確なID照合や計算は、既存機能や決定的処理を候補にする。文意の解釈は人やLLMで品質を比較する。APIは呼出し口なので、API経由で文章解析を頼むこともある。APIとLLMを二者択一にしない。
データベースにも文書の全文検索機能があり、「文章は従来システムで使えない」とは決めない。検索/直接参照/計算/解釈を必要な操作から選ぶ。

属性は、どの対象・環境・版に使える資料かを見分ける手掛かり。原資料の位置、状態、利用範囲、更新担当と条件をつなぐ。タグがあっても、それだけで正しい根拠を取れたりアクセスが制限されたりするわけではない。
今後作る情報から整え、判断へ必要な既存情報を小さく回収する。表記統一や項目分割では原意と識別子・既存参照を保つ。全過去データの整備を始める条件にしない。
意味単位の分割では、条件と例外、質問と回答、表の見出しと単位を離さない。具体的な検索や分割の比較は対象の根拠を使う試行で行う。

データの受渡しは、構文、項目の契約、業務上の意味と根拠、操作権限を順に区別する。JSONが読めても、必須項目や追加項目を制限しなければ契約として足りない。契約が合っていても、内容が正しい/登録が許可される証拠にはならない。

技術上の確認資料: [JSON形式とパース](https://docs.python.org/3/library/json.html)、[JSON Schemaの項目・必須・追加項目](https://json-schema.org/understanding-json-schema/reference/object)、[PostgreSQLの全文検索](https://www.postgresql.org/docs/current/textsearch-intro.html)。製品/環境ごとの採用や効果は別途検証する。
