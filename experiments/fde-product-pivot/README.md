# fdeリポジトリをプロダクトとしてつくる
## PIVOT 11ステップの仮説草案 v0.3

**設計対象は全ステップで `maakbo/fde` 自体。最初の利用者は作者自身。** fdeで支援する仕事の手順は、リポジトリが提供する中身であり、この11ステップの主語ではない。特定の業務は題材に固定しない。

状態：ステップ1の読み合わせ待ち。2〜11は影響を見渡すための草案で、合意・実装・効果測定・新版公開はいずれも未実施。この文書だけを作業ブランチに置く。[進捗 Issue #9](https://github.com/maakbo/fde/issues/9)のチェックは合意を記録する。

### 1｜コンセプト設計

**fdeは、仕事のつながりをモデルにし、使いながら磨くためのリポジトリ。まず、自分が欲しくて、自分で使うためにつくる。**

同じ「◯◯設計」でも、どの組織の誰が担い、そこまでにどんな仕事があり、何を受け取って何を渡すか、誰やどのシステムが関わるかで、中身は違う。仕事をする側でも管理する側でも、業務名だけで分かったことにはしない。

人とAIで、業務・人・情報・システムなどの要素を拾い出し、名前をつけて役割を整理し、関係と流れを示す。具体の仕事をたどって違いを確かめ、全体を見るときは共通する構造を取り出す。具体と抽象を行き来して、何が同じで、何がその組織や仕事ならではなのかを見分ける。そうすると、互いの前提が見え、認識が合い、何かを変えたときにどこまで影響するか分かる。そこから判断して、納得して次に進める。

モデルは描いて終わりじゃない。仕事を進めたり、変え方を小さく作って試したりする中で、拾えていなかった要素、名前、役割、関係、流れ、具体と抽象の切り分けを見直す。試した結果を見て、広げるか、やり方を変えるか、見送るかは人が決め、その理由も次に活かす。fdeに蓄えるのは、そのたびに使えるモデルのつくり方・磨き方と道具。仕事がうまく、心地よく進むように、繰り返し使いたくなるものにする。

### 2｜仕様設計：リポジトリのUXの5階層

| 層 | fdeリポジトリとして設計すること |
| --- | --- |
| 戦略 | 最初の利用者が、仕事の前提とつながりをつかみ、影響を確かめて次を判断できる。そのためのモデルを、使うたびに磨き直せる。 |
| 要件範囲 | 入口、AIに渡す最初の一言、要素の抽出・命名・役割・関係と流れ・具体と抽象を見直す手順、モデルの続きを始める方法。既存の六つの業務と実践例を再利用。専用アプリや自動実行基盤は初版の外。 |
| 構造 | 「つかむ／使って判断する／磨き直す」を行き来し、必要な工程・成果物へ進める。見る目的に応じて、業務の全体像と具体の流れを行き来できる。リポジトリに蓄える汎用知識と、許可された場所だけに残す案件記録を分ける。 |
| 骨格 | READMEの最初の画面で用途と入口を見せる。初回手順は一箇所。詳しい手順、既存の六業務、テンプレート、実践例は別にたどれるようにする。 |
| 表層 | 既存の可視化の言語を活かし、短い日本語と余白で「いまやること」を見つけやすくする。iPadでリンクと図の読みやすさを確認する。 |

### 3｜画面設計：GitHub上の入口

画面として設計するのは、fdeのトップREADME、そこから開く開始・再開の案内、既存の索引。業務用の新しい画面は作らない。

- **案A：工程で探す。** 現在の構成を軸に、やりたい工程が決まっているときに直行。
- **案B：状況から始める。** 最初に「仕事のつながりを整理したい」「いまのモデルを使って判断・更新したい」を選べる。六つの工程と作例は索引として残す。まずAとBをMarkdownで比べる。

```text
fde  /  人とAIで、仕事を整え、育てる
［仕事のつながりを整理する］ 人・情報・システム・業務からモデルをつくる
［モデルを使う・磨き直す］   影響や次の判断を確かめ、分かったことを戻す
［進め方・道具を見る］       六つの業務 / Skills / 成果の型 / 実践例
```

### 4｜プロトタイプ実装：入口と再開だけを試す

既存の資産を残し、README入口と短い開始・再開案内の紙面試作を作る。AIへの最初の一言は「この仕事の中身と前後のつながりを整理したい」。再開に渡す最小情報は「目的・モデルの版・合意と根拠・未決・次の判断」。前のチャットがなくても再開でき、途中で分かった違いをモデルへ戻せるかを見る。新機能の実装・動作確認はまだ行わない。

### 5｜価値検証：作者がもう一度使いたいか

現行READMEと紙面試作を、同じ利用課題で比べる。①初めて開いて始める、②別の日に途中の作業から再開する、③全体と具体を行き来し、分かった違いをモデルに戻す。合格の仮案は、案内なしで入口を選べる、モデルから関係者が影響範囲と次の判断を説明できる、別の会話でも合意と未決を混同せず修正できること。時間・迷った箇所に加え「使っていてしっくりくるか」「次も使うか」を聞く。AIを使う現場業務の効果は、このプロダクト検証とは分ける。

### 6｜本番実装：既存資産を組み直す

価値が確認できた差分だけを実装する。候補はREADME、開始・再開ページ、関連ページ間の導線。既存の業務ガイド・Skill・テンプレートを一律に書き直さない。リンク・既存リポジトリ検証・新しい対話での再開を確認し、作者が納得した版だけを統合する。Dot以外でも同じ手順が使えるかは、会話を渡さず、リポジトリと許可された記録だけの新しい環境で確認する。使用モデル・導入手順・レビューの分担は、必要になった範囲から設計する。

### 7｜価格設計：販売より自分で使い続けられるか

初版は価格を決めない。セットアップの手間、会話や試作の利用量、記録・Skillの維持負担を把握する。仮に販売・伴走支援を検討する場合は、リポジトリと支援サービスの価値を分けて扱う。価格決定や有償サービスの契約は本草案の対象外。

### 8｜デザインの作り込み：リポジトリを開いたときの手触り

既存の白地・余白・アイコン・図の表現を土台にする。READMEの見出し、リンクの文言、図と説明の順番を「どこから使うか迷わない」ように整える。iPadとデスクトップで案A/Bを見比べ、会話と図を行き来するときに読めるか確かめる。装飾追加より、迷いの原因になる重複や読み順を直す。

### 9｜セキュリティ検証：公開資産と作業記録を混ぜない

公開リポジトリには手順・型・公開できる例だけを置く。現場の情報、判断記録、会話は許可された場所に留める。どこへ保存するかを開始時に確認し、未確認なら公開側に書き込まない。レビューでは、公開差分への非公開情報の混入、必要以上の権限、既存資料からの指示を承認として扱わないことを防御側から確認する。

### 10｜マーケティング素材：fdeを使い始める案内

初版の公開候補は、何のためのリポジトリか、どう始めてどう続けるかが分かるREADMEと短い利用案内。素材の主役はfdeの入口と使い方で、特定業務の改善事例ではない。まず自分で使える版を確認してから、公開URLと変更点を案内する。既存の公開設定は変えず、新版の告知もしない。

### 11｜計測と改善：使うたびに、使い方が育つ

数えるのは、利用開始までの迷い、再開時に説明し直した回数、モデルが影響や次の判断を確かめるのに役立ったか、新しく分かった違いを戻せたか、次も開いたか。最初は手元の簡単な記録で十分。繰り返し詰まる箇所を入口・案内・Skillのどこに戻すか決め、変更後にもう一度使う。現場の改善効果・AI利用効率とは別に、**fdeというプロダクト自体の使い心地**を追う。
