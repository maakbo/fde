# fdeリポジトリをプロダクトとしてつくる
## PIVOT 11ステップの仮説草案 v0.7

**設計対象は全ステップで `maakbo/fde` 自体。最初の利用者は作者自身。** fdeで支援する仕事の手順は、リポジトリが提供する中身であり、この11ステップの主語ではない。特定の業務は題材に固定しない。

状態：ステップ1は合意済み。ステップ2は読み合わせ待ち、3〜11は影響を見渡すための草案。実装・効果測定・新版公開は未実施。この文書だけを作業ブランチに置く。[進捗 Issue #9](https://github.com/maakbo/fde/issues/9)のチェックは合意を記録する。

### 1｜コンセプト設計

**fdeは、自分が使いたくてつくる、人とAIで仕事を整え、育てるためのリポジトリ。**

同じ言葉を使っていても、組織や立場、役割、これまでの経緯が違えば、思い浮かべていることは違う。その違いが見えないまま話が進むと、合意したつもりでも、どこか噛み合わず、モヤモヤが残る。

でも、図を描くところから毎回手作業で始めたり、続きを別のAIに頼むたびに背景や判断を説明し直したりすると、話し合いの勢いが途切れる。

fdeを使うと、まだ整理できていない段階から話を始められる。fdeAIと一緒に、関わる人や組織、前後の仕事、受け取る情報と渡す情報、関わるシステムをたどる。要素を拾って名前をつけ、役割や関係、流れを図や言葉にし、関係者と見ながら直していく。違いをなくすのではなく、お互いの前提と影響範囲を確かめ、人もAIも、何を目指し、何を前提に進めるかを共有する。

そのうえで、何を変えるかを一緒に考え、小さく作って動かし、効果と使い心地を確かめる。広げるか、やり方を変えて試し直すか、見送るかは人が決める。実際に仕事を進めながら、要素の拾い方や名前、役割、関係、どこまで具体的に描き、どこを抽象化するかを見直し、モデルを磨いていく。判断の理由や次に活かせる知恵も、会話の外に引き継げる形で残す。

目指すのは、**仕事がうまく、心地よく進むように、自分が繰り返し開きたくなる道具**。まずは仕事に絞る。AIを使うこと自体や、やり方を一つに揃えることは目的にしない。

### 2｜仕様設計：fdeリポジトリのUXの5階層

**1. 戦略｜利用者のニーズと、つくり手の目標**

- **利用者のニーズ：** 仕事の進め方を見直したいとき、立場や経緯の違いから話が噛み合わなくても、関係者と「何が違うのか」「どこに影響するのか」を確かめたい。そのうえで、何を試すか、結果を見てどうするかを判断したい。日や担当、相手のAIが変わるたびに、前提や判断を一から説明し直したくない。
- **つくり手の目標：** fdeを、仕事を整え、育てるたびに使い直したくなる道具にする。一度の会話や図で終わらせず、仕事を進めながら理解を深め、試して分かったことを次の判断に活かせるようにする。説明し直す手間が減るか、自分から次の仕事にも使うかで確かめる。

対象となる状況とニーズは設計仮説。初期検証は作者自身が行い、他の人や組織への広がりは別に確かめる。

**2. 要件範囲｜初版で何ができるか**

1. まとまっていない相談や手元の成果から始め、必要な手順・型・作例を選べる。
2. fdeAIと仕事の要素を拾い、名前・役割・関係・流れを図や言葉にして直せる。どこまで具体化するかも見直せる。確認できたこと、立場ごとの見方、仮説、未決は分けて残す。
3. 人が決めた試行の目的、確かめる条件、実行してよい範囲を残し、試作と結果を対象の版に結びつけられる。
4. 後日や別のAIでも、結果と理由から続けられる。広げる、変えて試し直す、見送るの判断は人がする。

既存の六業務・Skill・成果物の型を使う。専用アプリ、独自の案件管理、自動実行基盤、既存ガイドの全面改稿は初版に含めない。

**3. 構造｜体験の流れと、情報のつながり**

「相談する → 図や言葉で整理する → 関係者と見直す → 小さく作って確かめる → 次を決める」が基本の流れ。途中から入っても、結果を受けて前提やモデルに戻ってもよい。六業務は順番に履修するものではなく、その時点で必要な作業を選ぶための地図にする。

情報は「対象と版」を起点に、立場ごとの見方と根拠、合意と未決、試行と観察結果、次の判断をたどれるようにつなぐ。再開はREADMEからでも手元の成果リンクからでもできる。公開リポジトリの道具・作例と、許可された場所に置く案件資料・判断は分ける。

**4. 骨格｜必要な情報と導線をどこに置くか**

READMEの上部に「何のために使うか」と「相談から始める」「前回から続ける」の入口を置き、六業務・Skill・型・作例への索引はその後に置く。作業中は、対象と版、見直す図や説明、いま決めることを近くに置く。再開時は「前に何をなぜ決めたか」「結果と未決」「次にできること／確認が要ること」を先に見せ、詳しい根拠はリンクでたどれるようにする。具体的な配置はステップ3で比べる。

**5. 表層｜どう見え、どう読めるか**

短い見出しと余白で読みやすくし、既存の図の表現を活かす。情報の状態は色だけに頼らず、「確認できたこと」「立場ごとの見方」「未決」などの言葉で見分けられるようにする。iPadのような狭い表示で図が読みにくいときも、要旨とリンクから内容を追えるようにする。

**検証の目安（仮）**

現行版と改訂案を同じ題材で比べる。案内なしで相談を始められるか、関係者の異なる見方を落とさずモデルを直せるか、会話を引き継いでいない別のAIが成果の版から再開し、合意・未決・実行許可を取り違えないかを見る。最後に、次の実際の仕事でも使いたいかを確かめる。fde自体の使い心地と、支援先の仕事が改善したかは分けて測る。

参考：[Garrett原著・第2章](https://jarrettfuller.com/tech/downloads/elements_ux.pdf)／[GOV.UKの年金サービス改善事例](https://designnotes.blog.gov.uk/2016/10/21/improving-the-check-your-state-pension-service-in-public-beta/)

### 3｜画面設計：GitHub上の入口

画面として設計するのは、fdeのトップREADME、そこから開く開始・再開の案内、既存の索引。業務用の新しい画面は作らない。

- **案A：工程で探す。** 現在の構成を軸に、やりたい工程が決まっているときに直行。
- **案B：状況から始める。** 最初に「まだ言葉になっていない」「前回の続きをやりたい」を選べる。六つの工程と作例は索引として残す。まずAとBをMarkdownで比べる。

```text
fde  /  人とAIで、仕事を整え、育てる
［話しながら始める］         何から手をつけるかも未定
［前回の続きを始める］       決めたこと・未決・次の一手を持っている
［進め方・道具を見る］       六つの業務 / Skills / 成果の型 / 実践例
```

### 4｜プロトタイプ実装：入口と再開だけを試す

既存の資産を残し、README入口と短い開始・再開案内の紙面試作を作る。AIへの最初の一言は「この仕事を、どうしたらもう少し心地よく進められるか、一緒に整理したい」。再開に渡す最小情報は「目的・合意したことと理由・根拠の版・未決・次にしたいこと」。前のチャットがない状態でも、その記録から再開できるかを見る。新機能の実装・動作確認はまだ行わない。

### 5｜価値検証：作者がもう一度使いたいか

現行READMEと紙面試作を、同じ利用課題で比べる。①初めて開いて始める、②別の日に途中の作業から再開する、③必要な図の描き方や手順を探す。合格の仮案は、案内なしで入口を選べる、別の会話で合意と未決を混同せず次の一手に進める、同じ前提の説明を繰り返さないこと。時間・迷った箇所に加え「使っていてしっくりくるか」「次も使うか」を聞く。AIを使う現場業務の効果は、このプロダクト検証とは分ける。

### 6｜本番実装：既存資産を組み直す

価値が確認できた差分だけを実装する。候補はREADME、開始・再開ページ、関連ページ間の導線。既存の業務ガイド・Skill・テンプレートを一律に書き直さない。リンク・既存リポジトリ検証・新しい対話での再開を確認し、作者が納得した版だけを統合する。Dot以外でも同じ手順が使えるかは、会話を渡さず、リポジトリと許可された記録だけの新しい環境で確認する。使用モデル・導入手順・レビューの分担は、必要になった範囲から設計する。

### 7｜価格設計：販売より自分で使い続けられるか

初版は価格を決めない。セットアップの手間、会話や試作の利用量、記録・Skillの維持負担を把握する。仮に販売・伴走支援を検討する場合は、リポジトリと支援サービスの価値を分けて扱う。価格決定や有償サービスの契約は本草案の対象外。

### 8｜デザインの作り込み：リポジトリを開いたときの手触り

既存の白地・余白・アイコン・図の表現を土台にする。READMEの見出し、リンクの文言、図と説明の順番を「どこから使うか迷わない」ように整える。iPadとデスクトップで案A/Bを見比べ、会話と図を行き来するときに読めるか確かめる。装飾追加より、迷いの原因になる重複や読み順を直す。

### 9｜セキュリティ検証：公開資産と作業記録を混ぜない

公開リポジトリには手順・型・公開できる例だけを置く。現場の情報、判断記録、会話は許可された場所に留める。どこへ保存するかを開始時に確認し、未確認なら公開側に書き込まない。レビューでは、公開差分への非公開情報の混入、必要以上の権限、既存資料からの指示を承認として扱わないことを防御側から確認する。

### 10｜マーケティング素材：fdeを使い始める案内

初版の公開候補は、何のためのリポジトリか、どう始めてどう続けるかが分かるREADMEと短い利用案内。素材の主役はfdeの入口と使い方で、特定業務の改善事例ではない。まず自分で使える版を確認してから、公開URLと変更点を案内する。既存の公開設定は変えず、新版の告知もしない。

### 11｜計測と改善：使うたびに、使い方が育つ

数えるのは、利用開始までの迷い、再開時に説明し直した回数、必要な手順が見つかったか、次も開いたか。最初は手元の簡単な記録で十分。繰り返し詰まる箇所を入口・案内・Skillのどこに戻すか決め、変更後にもう一度使う。現場の改善効果・AI利用効率とは別に、**fdeというプロダクト自体の使い心地**を追う。
