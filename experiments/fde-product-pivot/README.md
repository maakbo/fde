# fdeをプロダクトとして育てる
## PIVOT 11ステップを一周した仮説レビュー v0.1

**まず読み合わせたいこと：仕事を「見える化」で終えず、当事者と変えることを決め、小さく試し、効果を見て次を決める。仕事がうまく、心地よく進むよう、人とAIがその循環を続けられるようにする。**

- **プロダクト**：GitHubの `maakbo/fde`。一連の進め方、AIの手順、成果の型、追試できる例を持ち運べる。最初の利用者は、現場に入るリポジトリ作者自身。仕事の担当者と、成果を受け取る人は一緒に判断する相手。
- **今回の境界**：最初は仕事。祝い事など個人の活動や、環境・自然に関わる活動にも応用できる余地は残すが、初版の検証範囲には含めない。「仕事」は対象の言い換えで、fdeの名前を置き換える話ではない。
- **今の状態**：対話で合わせた方向＋以下は意思決定用の仮説。GitHub mainを参照。架空ケースの状態分岐だけ実行済み。現場の試行・効果測定・本番実装・主ブランチ反映・新たなリリースは未実施。この文書だけを作業ブランチに保管。

### 今あるものを捨てない

[入口README](https://github.com/maakbo/fde/blob/main/README.md) と [仕事全体](https://github.com/maakbo/fde/blob/main/work/README.md) は、対象選定、要件、協働設計、実装、評価、運用改善の六つを既に結んでいる。[現場の進め方](https://github.com/maakbo/fde/blob/main/.agents/skills/discovery-facilitation/references/field-delivery-loop.md) には戻り先と運用への引継ぎがあり、[成果の共通条件](https://github.com/maakbo/fde/blob/main/work/references/artifact-contract.md) には根拠・版・未決・引継ぎがある。[CSV出力の例](https://github.com/maakbo/fde/blob/main/examples/field-delivery/csv-export/README.md) には独立受入や停止・旧版確認のローカル実績もある。**「循環を新設」ではなく、「初めての自分が、一件を対話から次の判断まで迷わず通れるか」を確かめる**。以下の一点案は、欠落の断定ではなく、既存資産を使って確かめる仮説。

PIVOTの11ステップは **fdeというプロダクトを育てる外側**。既存の六つの業務は **fdeを利用して現場の仕事を変える内側**。一対一に置き換えない。内側で繰り返し効いたやり方だけを、外側で手順やSkillに戻す。

### 1｜コンセプト設計

「テスト設計をAIで早くしたい」といった相談に、最初から万能なエージェントを渡さない。同じ仕事名でも、誰が何を受け取り、何が未決で、どこまで渡せば次の担当が動けるかは違う。仕事を知る人とその違いを図にし、**AIに任せるかも含めて**変更を選ぶ。試したあとにGo（限定展開）、Pivot（やり方を変え再試行）、No-Go（停止）を人が決める。保留は、証拠や権限待ちとして区別する。

最初の価値は「立派な図」でも「AIに任せた仕事量」でもない。**受け手が、どこまで合意済みか分かり、余計な聞き直しや手戻りなく次へ進めること。** 仕事の心地よさは、担当者の実感と受け手の負担を別々に聞く。

### 2｜仕様設計：UXの5階層

| 下から順に | 仮説 |
| --- | --- |
| 戦略 | 最初の利用者は話を聞くことに集中し、決定の根拠・渡す先・必要な次の一歩をその場で確かめられる。担当者にとって強みや大切にしたい仕事が削られない。 |
| 要件範囲 | 自由な相談 → 現行の小さな図 → 一件の変更案と合格条件 → 試行 → 人の判断 → 学びの引継ぎ。既存のIssue・Markdown・成果物で扱う。全社標準化、外部接続、自動展開、専用Web UIは初回の対象外。 |
| 構造 | 一件の継続記録を中心に、合意済み／仮説／未決を分離。各段階は同じケースID、根拠、版を持つ。目的のズレは対象選定、ルール不足は人の仕様判断、実装不備は設計・実装へ戻す。 |
| 骨格 | 会話の入口は一言。返すのは小さな図、未決と確認先、今できる一手。必要な人だけが比較、成果、検証根拠の詳細を開く。Skill名や様式の指定を利用者に求めない。 |
| 表層 | 白地と余白、短い日本語、既存の図の言語を維持。色だけで状態を表さない。読み合わせ用の図と、作業用の記録を混ぜない。実際の見た目はステップ8で検証。 |

### 3｜画面設計：GitHubでの読み合わせ

**A：工程を選ぶ入口**。既存の六つから必要な場所に直行できる。慣れた人には速いが、初回に「どこから？」となりやすい。  
**B：今の一件を開く入口**。既存の「相談から始める」と実践例を生かし、過去のケースを一件最後まで追える。初版はBを推す。Aは索引として残す。新しい画面を作る前に、READMEとケースへのリンクで比較する。

```text
住所変更のテスト設計  /  架空・読み合わせ用
今日そろえたいこと  テスト担当がどの条件を受け取れば着手できる？
現行の流れ          依頼 → 条件確認 → ケース案 → レビューへ
いまの状態          Bチーム：適用開始日の条件が未決
誰に確かめる        仕様を決める業務責任者（架空の役割）
次にできること      期待結果を合意する → 合意後に候補を作る
根拠と変更履歴      元資料の版・未決 → 試行結果 → 次の判断
```

### 4｜プロトタイプ実装：二つのチームで一周する

同じ「住所変更のテスト設計」を頼まれた架空の二チーム。実際の会社や担当者を表していない。

- **A**：入力条件と期待結果は業務責任者が合意済み。架空の仕様 `ADDR-v1` をもとに、AIが正常・必須項目不足・変更なしの候補を下書き。人が照合・承認してからレビュー担当へ渡す。
- **B**：利用者の要望だけ受領。いつ変更が有効になるか未決。AIは期待結果を作らず、「誰が、どの条件を決めるか」を返す。試作品の操作は、責任者の合意を架空入力として追加してから再開する。
- **共通**：設計者 → レビュー担当へ渡す内容は、根拠の版・候補・未決・人の承認。仕様が更新されたら古い承認で渡さない。渡し先への通信・書き込み機能は持たせない。

**この仮説レビューで実行したこと**：合成入力の状態分岐を小さな関数で確かめた。6ケースすべて期待と一致：未承認は下書き、同じ版の承認で受渡し可、仕様未決で保留、責任者なしで保留、旧版承認は下書きのまま、権限なしで停止。3候補の件数は定数で、ケースの生成・内容の正確さ、実際の権限制御、AI実行・人の受渡しをテストしたわけではない。製品コードは変更していない。次は [現行観察・委任・PoCの型](https://github.com/maakbo/fde/blob/main/templates/README.md) を参照し、同じケースを対話から新しい担当に渡せる状態を一件作る。

### 5｜価値検証：単に速くなったかで決めない

まずは同等の架空例で **現行の進め方・可視化だけ・可視化＋AI下書き** を比較する。練習効果を避けるため、同程度の二例を用意し順序を変える。小規模で因果は断定しない。リポジトリ作者、実務を想定した担当、次工程の受け手で確認する。実際の関係者を呼ぶ場合は参加と使用資料の許可を別に取る。

- **品質の必須条件案**：未決の補作・根拠のない期待結果・未承認の受渡しはゼロ。受け手が、次に何ができ、何ができないか言い直せる。
- **効果の目安案**：初稿速度ではなく、調整・修正を含み「受け取れる状態」までの時間。Aでは現行比20%短縮を探索の目安にする。Bは初稿が作れないことを失敗とせず、「必要な判断・判断者」を読み合わせで指せるかを見る。20%は実績でも採用条件の合意でもない。
- **使い心地**：「確認が減った／増えた場面」「仕事の良さが残った／削れた場面」「次の一件もこれで進めたいか」を担当者と受け手に別々に聞く。新しい入力の負担があれば計上する。
- **仮の判定**：品質と受取条件を満たし、負担改善が見えれば一チーム限定のGo候補。図だけで価値があるならAI生成を外すPivot。責任者不在・未承認は保留、重要な誤りや負担増が解けなければNo-Go。実用効果は未測定。

### 6｜本番実装：仕組みは小さく、判断は残す

Go後の最初の差分案は、既存READMEからの導線、合成ケース一件、必要ならケースの説明・期待・再現手順だけ。同じことをする新Skillや、重複する帳票は作らない。記録は `目的／根拠と版／同意したこと／未決と確認者／受入条件／結果と次の判断` を使い回す。

進行役は工程選択・引継ぎ、実装役はテストと小さな実装、別コンテキストのレビュアーは同一版で未決・承認・例外を反証。人は目的・合格・展開を決める。[既存のCSV例](https://github.com/maakbo/fde/blob/main/examples/field-delivery/csv-export/README.md) の分離方式を借りる。まず既存の検証コマンドとケース再現を回し、確認した版を残す。リポジトリ作者の受入と公開確認を分ける。

**持ち運べるかの確認**：Dotとの会話を渡さず、同じモデルで可能なら固定し、別のCodexでリポジトリと一言だけから再現。判断に要した再質問、見落とし、時間、使える場合は利用量を記録。モデル配役比較はその後。fdeには [Copilot向け配役の設計案](https://github.com/maakbo/fde/blob/main/.github/prompts/luna-first-autonomous-development-harness.prompt.md) があるが、この一件の運用実績ではない。AI-DLCの採否も、この段階で必須にしない。

### 7｜価格設計：販売価格は今は置かない

既存の公開リポジトリを使い、自分が使えるかが今回の目的。価格を決めず、`現状との差＝現状の総時間 − 試行の総時間` を担当ごとに出し、モデル利用・確認担当・維持・教育・再作業を費用として別記する。予算や担当の確認前に外部サービスへ申し込まない。将来有償化するなら、公開リポジトリと伴走支援の価値・費用を別に検証する。

### 8｜デザインの作り込み：情報より先に「いまの判断」が見える

比較用の二案は、A「六つの工程が入口」、B「相談と一件の追体験が入口」。見た目の参考は既存fdeの白地・細い関連線・既存アイコン、読みやすさは短い手順と余白。新しい配色やアイコンを先に作らない。**スマホのGitHubで30秒以内に「いまの状態」「誰に何を聞くか」「次へ渡すもの」を見つけられるか**を仮の基準に、短い文＋図と図中心を比較。説明がないと読めない場合は、見栄えより見出しと読み順を直す。実機確認は未実施。

### 9｜セキュリティ検証：実データを入れずに境界を確認

公開される例は合成データだけ。現場の資料・固有名・会話ログを個人の公開GitHubや未承認サービスへ移さない。公開差分は人が確認し、権限は必要最小限、試行に本番接続や更新権限を与えない。防御側のテストとして、参照許可がない場合、承認がない・旧版の場合、資料の中に手順変更を促す文章がある場合に、処理や共有が止まることを検証する。状態分岐の確認以外の実環境検証は未実施。運用で境界が守れなければ公開・導入を保留。

### 10｜マーケティング素材：伝えたいのは、1件の変化

初版はREADMEの説明と、合成事例を90秒で追える導入だけ。公開に進むなら、既存リポジトリの公開状態を変えるのではなく、確認済みの入口・例・再現手順を公開する。GitHub Projectを使うかは、未決・試行・判断の所在が既存Issueだけで足りるか見て決める。新版の告知・リリースはしていない。

> 現場で話を聞き、仕事の流れを一緒に描く。人とAIで一つ変えて試し、次に進むかを確かめる。まずは「同じ名前でも進め方が違うテスト設計」の例で、相談から判断までを追えます。

### 11｜計測と改善：結果を次の仕事へ返す

大がかりな分析を入れず、ケースごとに `入力の版／進め方／最初の図まで／受渡しまで／追加の確認と修正／未決の扱い／本人と受け手の実感／Go・Pivot・No-Go／次の仮説` を残す。実測していない値は空欄でなく「未測定」。個人別の成績表にしない。

- **ケースに返す**：Bで判断者が見つからなければ入口の聞き方に戻る。Aで確認負担が増えたら、候補生成ではなく根拠と照合の方法を見直す。
- **fdeに返す**：別ケースでも効いた改善だけをテンプレートやSkillの最小差分にする。その差分が新しい会話でも効くか同じ条件で取り直す。個別事情はケース内に留める。

### 次の読み合わせ

**私なら、今のfdeを作り直す前に、「同じ仕事名なのに渡せる条件が違う」一件で、入口から次の判断までを通す。** すでにあるCSV実践例が「決まった変更を安全に届ける」を扱うのに対し、今回の候補は「何が決まっていないかに、その場で気づける」が出発点。差はそこに絞る。

読み合わせで最初に合わせるのは、初版で示したい価値が **「未決に早く気づき、当事者が次の一手を決められること」** でよいか。その後、試す場面と合格条件を一緒に決める。実装、リポジトリ更新、現場の試行、公開はそれぞれ別の判断。
