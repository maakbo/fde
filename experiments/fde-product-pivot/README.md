# fdeリポジトリをプロダクトとしてつくる
## PIVOT 11ステップの仮説草案 v0.8

**設計対象は全ステップで `maakbo/fde` 自体。最初の利用者は作者自身。** fdeで支援する仕事の手順は、リポジトリが提供する中身であり、この11ステップの主語ではない。特定の業務は題材に固定しない。

状態：ステップ1は合意済み。ステップ2は読み合わせ待ち、3は最初の一枚を読み合わせる段階、4〜11は影響を見渡すための草案。実装・効果測定・新版公開は未実施。この文書と比較資料は作業ブランチに置く。[進捗 Issue #9](https://github.com/maakbo/fde/issues/9)のチェックは合意を記録する。

### 1｜コンセプト設計

皆さんのやりたいことが、より良くうまくいきますように。そんな願いを込めて、fdeを提供します。

同じ仕事に関わっていても、立場が違えば、見えていることや前提は違います。仕事が自分ごとにならなかったり、思うように進まなかったりするのは、誰かの意欲のせいではなく、仕事の仕組みや、互いの前提のずれに理由があることもあります。

fdeでは、AIの力も借りながら、自分たちの仕事を図と言葉にします。何のために、誰がどう関わり、誰に何を渡すのか。つながりを一緒に見ながら、互いの違いを理解し、仕事を進めるうえで大事な認識を合わせます。

そこで終わらず、今のやり方の良さを活かすことも、詰まっているところを小さく変えてみることも、仲間と一緒に考えられる。一人ひとりが納得して自分で動けて、仕事が心地よく流れ、その先の相手にちゃんと価値が届く。fdeは、そんなふうに皆さんの仕事が進むよう支える仕組みです。

**このリポジトリで提供すること**

fdeを使うと、まだ整理できていない段階から話を始められる。fdeAIと一緒に、関わる人や組織、前後の仕事、受け取る情報と渡す情報、関わるシステムをたどる。要素を拾って名前をつけ、役割や関係、流れを図や言葉にし、関係者と見ながら直していく。

変えることを選んだ場合は、小さく動かし、効果と使い心地を確かめる。広げるか、やり方を変えて試し直すか、見送るかは人が決める。実際に仕事を進めながら、要素の拾い方や名前、役割、関係、どこまで具体的に描き、どこを抽象化するかを見直し、モデルを磨いていく。判断の理由や次に活かせる知恵も、会話の外に引き継げる形で残す。

まずは仕事を対象とし、作者自身の利用から確かめる。AIの利用や、やり方を一つに揃えること自体は目的にしない。

### 2｜仕様設計：fdeリポジトリのUXの5階層

状態：読み合わせ用。案1を具体化しているが、採用は未決。次の5階層を、合意したコンセプトを体験に落とすための土台にする。

1. **戦略**：仕事に関わる人が、目的と自分の仕事のつながりを理解し、仲間と互いの違いを認めながら、自分で考えて動けること。図の出来や全員の同意より、日々の仕事が無理なく進み、受け手に価値が届くことを目指す。
2. **要件範囲**：整理されていない話や手元の資料から、関係と流れを図と言葉にできる。現場の言葉でその場で直し、直接影響する図や手順は根拠を残して揃える。似た箇所は提案に留める。人が、現行を続けるか、支援を足すか、変えて試すかを選ぶ。専用アプリや自動実行基盤は初版の前提にしない。
3. **構造**：相談する → 関係を見ながら話し、直す → 渡す側と受け取る側が意図と確認範囲を確かめる → 続け方を選び、仕事を進める → 結果をもとにまた考える。目的から仕事・業務・作業まで、粒度を分けて行き来できるようにする。
4. **骨格**：fdeを取得した環境でエージェントに普段の言葉で頼む。返答と作業成果では、いまの問い、小さな図、判断理由、影響、未決を近くに置く。Markdownと埋め込みMermaidの同じ版を、人も別のAIもたどれる。案件モデルは許可された作業場所に置く。READMEは案内で、作業を始める必須画面にはしない。
5. **表層**：現場の言葉、短い見出しと説明、一枚の図に一つの論点。仮説・確認したこと・立場ごとの見方・未決は色だけでなく文字でも分かるようにする。

**可視化の設計基準**：RDRAのエッセンスを借り、現場の言葉や実際の仕事から要素を拾い、名前と関係をモデルにする。同じ要素は図をまたいでも同じものとしてたどれるようにし、変更の影響と整合を確かめる。画面に載せるのは、その問いを話すのに必要な関係だけ。省いた詳細は別の粒度の図や説明に残す。「そうそう、これ」と現場の人が自分の仕事を指せることと、シンプルさを両方確かめる。

**確かめ方（未実施）**：仕事に関わる人の気づきが案や判断理由に残るか。受け渡しの双方が、相手の意図と確認範囲を自分の言葉で説明できるか。仕事の続け方を選べたか、受け手に価値が届いたかを、図の出来やツールの使いやすさとは分けて見る。

### 3｜利用者との接点設計

利用者向けのMarkdownと、AIエージェントとの対話を一つの体験として設計する。テーマのルートを起点に、ディレクトリで解像度を上げ、ページごとの問いに対して必要な関係だけを図にする。最初は、特定業務の例ではなく「fdeをつくり、育てる」という実際の活動を描く。

[ルートREADME：テーマコンテキスト図と業務設計](../../README.md)

中央は白い角丸四角に大きめの文字と余白、右上は枠を付けず太字と点線。右上の文言は合意済み。中央のテーマ名は「fdeを育てる」のまま据え置く。

「テーマ」は一緒に可視化する対象の名前。事業・仕事・プロジェクト・個別作業のいずれでもよい。ルートの一枚は、全員が知っておきたい背景と目指すゴールを共有する。中央にテーマ、左上側に主催者、左に価値を届ける側、右に受け取る側、右上に短い背景とゴールを置く。人・AI・外部システムなどは関わり方で配置し、必要なときだけグループ化する。配置で伝わる向きは矢印で繰り返さない。下の階層で分かったことを踏まえ、この一枚にも戻って直せるようにする。

GitHubのトップREADMEや開始・再開の案内も接点だが、別の比較課題として保留する。

### 4｜プロトタイプ実装：入口と再開だけを試す

既存の資産を残し、README入口と短い開始・再開案内の紙面試作を作る。AIへの最初の一言は「この仕事を、どうしたらもう少し心地よく進められるか、一緒に整理したい」。再開に渡す最小情報は「目的・合意したことと理由・根拠の版・未決・次にしたいこと」。前のチャットがない状態でも、その記録から再開できるかを見る。新機能の実装・動作確認はまだ行わない。

### 5｜価値検証：作者がもう一度使いたいか

現行READMEと紙面試作を、同じ利用課題で比べる。①初めて開いて始める、②別の日に途中の作業から再開する、③必要な図の描き方や手順を探す。合格の仮案は、案内なしで入口を選べる、別の会話で合意と未決を混同せず次の一手に進める、同じ前提の説明を繰り返さないこと。時間・迷った箇所に加え「使っていてしっくりくるか」「次も使うか」を聞く。AIを使う現場業務の効果は、このプロダクト検証とは分ける。

### 6｜本番実装：既存資産を組み直す

価値が確認できた差分だけを実装する。候補はREADME、開始・再開ページ、関連ページ間の導線。既存の業務ガイド・Skill・テンプレートを一律に書き直さない。リンク・既存リポジトリ検証・新しい対話での再開を確認し、作者が納得した版だけを統合する。Dot以外でも同じ手順が使えるかは、会話を渡さず、リポジトリと許可された記録だけの新しい環境で確認する。使用モデル・導入手順・レビューの分担は、必要になった範囲から設計する。

### 7｜価格設計：販売より自分で使い続けられるか

初版は価格を決めない。セットアップの手間、会話や試作の利用量、記録・Skillの維持負担を把握する。仮に販売・伴走支援を検討する場合は、リポジトリと支援サービスの価値を分けて扱う。価格決定や有償サービスの契約は本草案の対象外。

### 8｜デザインの作り込み：リポジトリを開いたときの手触り

既存の白地・余白・アイコン・図の表現を土台にする。READMEの見出し、リンクの文言、図と説明の順番を「どこから使うか迷わない」ように整える。iPadとデスクトップで案A/Bを見比べ、会話と図を行き来するときに読めるか確かめる。装飾追加より、迷いの原因になる重複や読み順を直す。

### 9｜セキュリティ検証：公開資産と作業記録を混ぜない

公開リポジトリには手順・型・公開できる例だけを置く。現場の情報、判断記録、会話は許可された場所に留める。どこへ保存するかを開始時に確認し、未確認なら公開側に書き込まない。レビューでは、公開差分への非公開情報の混入、必要以上の権限、既存資料からの指示を承認として扱わないことを防御側から確認する。

### 10｜マーケティング素材：fdeを使い始める案内

初版の公開候補は、何のためのリポジトリか、どう始めてどう続けるかが分かるREADMEと短い利用案内。素材の主役はfdeの入口と使い方で、特定業務の改善事例ではない。まず自分で使える版を確認してから、公開URLと変更点を案内する。既存の公開設定は変えず、新版の告知もしない。

### 11｜計測と改善：使うたびに、使い方が育つ

数えるのは、利用開始までの迷い、再開時に説明し直した回数、必要な手順が見つかったか、次も開いたか。最初は手元の簡単な記録で十分。繰り返し詰まる箇所を入口・案内・Skillのどこに戻すか決め、変更後にもう一度使う。現場の改善効果・AI利用効率とは別に、**fdeというプロダクト自体の使い心地**を追う。
