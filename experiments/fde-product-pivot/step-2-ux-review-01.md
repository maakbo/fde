# fde Step 2｜案1「仕事を話しながら、目的とつながる形にする」

2026-11-23 JSTの読み合わせを反映した案1のたたき台。合意済みのStep 1はそのまま。案1は「可視化の入口が近い」という手応えで、まだ採用ではない。以下はプロダクト設計案。実装、Step 3、検証結果を含まない。

## 1. 戦略｜誰が何のために使うか

**問題意識**：仕事が自分ごとにならず、いい仕事につながらないとき、それは一人ひとりの意欲や能力のせいとは限らない。仕事の目的が見えない、立場ごとに前提がずれている、自分で考えて動く余地がない。仕事の構造や仕組みが、そうさせていることもある。

**fdeが提供する体験**：仕事に関わる人たちが、AIと一緒に、自分たちの仕事を関係性ごと図と言葉にする。何のために、誰が何を受け取り、どう関わり、次に何を渡すのか。同じ図を指しながら前提のずれを確かめ、仕事に必要な認識を合わせる。違いまで全部揃える必要はない。

**その先にある価値**：見えたことを土台に、AIの力も借りながら、今のやり方を活かすか、詰まりをほぐす工夫を試すかを、自分たちで決めて仕事を進める。一人ひとりが納得して動ける。仲間と同じ目的に向かっていると感じられる。そして、誰かの無理に頼らず仕事が心地よく流れ、相手に価値が届く。fdeは、そのための仕組み。

- **利用者のニーズ**：経営・責任者は、目指す価値や制約が日々の仕事にどうつながっているかを、現場の実態に照らして判断したい。現場の人は、自分の仕事が何に届くか、大切にすること・自然に出る強み・興味・少し背伸びして伸ばしたいことが、役職の枠を越えてチームの目的とどこでつながるかを見つけ、自分で関わり方や続け方を選びたい。チームは、違いがあるままでも互いの持ち味を活かし、自分たちで共有の目的に向かいたい。進行役は、どちらかの言葉で一方を上書きせず、双方が「この描き方なら自分たちの仕事だ」と言える素材を育てたい。
- **プロダクトの目標**：可視化や認識合わせで終わらず、関係者が納得して仕事を進められるか、受け手に価値が届くかで確かめる。今の方法がしっくりくるなら、その理由を確かめて続けることも成功。
- **つくり手のこだわりと、使う人が得る価値**：つくり手が名前や関係、粒度をしっくり整える手触りは、道具づくりの基準。参加者やチームにとっての価値は、それとは別に、自分たちで動ける余地と仕事が無理なく流れることにある。チームをまたぐときは、受け渡しに必要な理解だけを共有し、違いがあっても認めて残す。

## 2. 要件範囲｜何を扱えるか

- 依頼された手段をそのまま結論にせず、人とAIで「この仕事で実現したいこと」と「うまくいったと分かること」を確かめる。暫定モデルを見て出た違和感や別案を、目的と判断理由に結び付ける。共感や発言は強制せず、依頼どおりに進める、別案を試す、現行を続ける、どれも選べる。
- fdeをcloneしてエージェントに参照させ、荒い話、現物、許可された参照から始められる。利用者に工程名や帳票を選ばせない。現場で実際に使う言葉を残し、既存の記法・Skill・型で暫定像をすぐ返す。
- **案件ごとのモデルの上位に、その組織／仕事の目的と目標を置く。** その下で「仕事 → 業務 → 作業」を、扱う範囲に合う粒度でフォルダ・ディレクトリに整理する。上と下、前と後、受取側と渡す側は関係をリンクでたどる。共有fdeリポジトリのトップに全案件の目的を集める話ではない。
- 名前、役割、関係、流れ、粒度をその場で直せる。一箇所の訂正に対し、直接つながる図や記述を洗い出し、確かめた範囲を一緒に直す。似た箇所は理由を添えて**提案**し、別現場や別の意味を確認なく置き換えない。変更理由・影響・未確認と確認先は消さない。
- 手渡す側が「誰のどんな必要から、この成果を用意したか」を、受け取る側が「何の意図で、実際に何をどこまで、なぜ確かめたか」を、自分の言葉で返せるようにする。その仕事に必要な範囲だけ共有する。役職以外の持ち味・関心などは本人が話したい範囲で扱い、必須プロフィールや評価項目にしない。
- モデルから「現行を続ける／支援を受けながら進める／変え方を試す」へつなぐ。どれも目的・判断者・許可範囲を残す。実行は人やAIが分担し、人の判断は代作しない。

## 3. 構造｜会話とモデルをどう行き来するか

「実際はどうしている？」→ 一つの問いに対する小さな図 → 当事者が言い直す → 必要なら親や子のモデルへ移る → 影響を確かめ、続け方を人が選ぶ → 実際に使った結果から戻って見直す。全部を一度に聞かず、組織の目的から現場へも、現場の違和感から上位目的へも戻れる。

**対話の例（架空。案件を固定しない）**

> 現場：「ここで『確認済み』って言うときは、現物を照らし合わせたって意味です。」 \
> 責任者：「私は、相手に公開してよいところまで進んだと思っていました。目的は、相手が安心して次に進めることです。」 \
> FDE＋AI：「この図は『現物を確認する』から『公開を決める』までに絞ります。二つをいったん『現物照合済み』『公開承認済み』に分けます。受け渡しの図と公開の手順は影響がありそうです。別部署の同じ言葉は意味が確認できるまで直しません。この線は実際に誰から誰へ渡りますか？」 \
> 現場：「照合の結果は責任者に渡します。公開する担当は別です。」 \
> FDE＋AI：「その関係を反映しました。二つの図と本文に同じ理由を残し、別部署の使い方は未確認にします。」

- **変えずに続ける道**：実際の現場では照合・承認が既に分かれ、責任者と公開担当も迷わず受け渡していた。**仕事の方法は変えない。** モデル上の曖昧な言葉だけを直し、続ける理由を残す。必要なら人とAIが、許可された照合の準備や引継ぎを支える。担当を増やすのでなく、たとえば差分を読むのが好きで、説明の仕方も練習したい人が、本人の希望で一件だけ説明を引き受けてもよい。引き受けなくても不利益はない。次の仕事で迷いが出たら、その場面を同じモデルに持ち帰る。
- **変えて確かめる道**：照合だけで公開してよいと誤読する事例があった。人が「照合だけでは公開操作に進めない」を条件に、仮データで小さく試す。通常例と差し戻しを観察し、現場の負担や相手への価値も見る。続行・条件を変えて再試行・見送りを人が判断し、結果から名前や関係、上位目的の捉え方に戻る。本番操作の承認は別。

**追加のやりとり：互いに受け取った意味を言い返す（架空）**

> 渡す側：「公開担当が、照合済みのものと承認待ちのものを取り違えないように、結果をまとめました。古い版を出さないため、公開用の版と原本の項目が一致するところまでを見ました。」 \
> 受け取る側：「私は、公開してよいと決めるための材料だと受け取りました。古い版を出さないために原本と照合したんですね。項目の一致は確認済み。公開の可否はまだ確認されていないので、先へ進めません。照合を実際にどう進めるかは、こちらと同じでなくて大丈夫です。」 \
> 現場の人：「照合で違いを見つけるのが好き。次は、受け取る人に分かる説明も一件だけやってみたいです。」

言い返しはテスト案で、堅い復唱ルールではない。相手が言い返せない時は、言葉や境界をモデルへ戻して直す。現場の人の三つ目の発言は本人が選んだ関わり方で、責任や権限の移譲を意味しない。

## 4. 骨格｜何をどこで確かめるか

会話の返答では「いま一緒に考える問い」「小さな図か短い説明」「訂正候補」を先に見せる。**一図一論点**を守り、他の粒度は横に並べずリンクで開く。チームをまたぐ受け渡しでは、成果の隣に「誰の何のため」「実際に見た範囲」「次にできること／まだできないこと」を短く置く。各チーム内の手順や人の関心は、外に必要がなければ載せない。例えば案件内で、上位の目的・目標 → 仕事「公開して相手に渡す」→ 業務「公開の可否を決める」→ 作業「現物を照合する／承認する」をたどり、必要な前後関係へ横断できるようにする。これは置き方の原則で、全案件の固定階層やStep 3の画面配置ではない。

訂正前に「今回直す／同じか確認する／触らない」を示す。確かめた変更は対象の版とID、変えた理由、反映した見方、未決につなぐ。Markdown本文と内包Mermaidを版管理し、Mermaidを図の唯一の編集元とする。人とAIは同じ意味・対象版へ戻れ、構造化表現が必要なら同じ記録から得る。一方だけを手直しする二重管理はしない。共有fde側は方法・記法・型・共有可能な作例、案件の記録は許可された場所に置く。

## 5. 表層｜どんな見え方・手触りか

現場の言葉を先に、小さい図・短い見出し・既存の記法と余白を使う。「現場の言い方」「仮の表現」「確認したこと」「未確認」を文字で区別し、赤緑やチェック印だけで意味を伝えない。直した直後は小さな差分を返し、図が見づらい場でも読み方とリンクで追える。経営向けの要点と現場の詳しさは出し分けるが、元の意味と版は一つ。全員がGitHubを自分で操作する必要はない。本人の言葉は関わり方を話すきっかけとして扱い、人を採点する一覧・配属表・評価ダッシュボードにはしない。チーム間の違いは「共有が必要」「違っていてよい」「解消まで止める」と見分けられる言葉で示す。

## 読み合わせと検証の目安（未実施）

- **目的のつながり**：経営側・現場側が同じモデルから「誰へのどんな価値に、なぜこの仕事が必要か」を自分の言葉で指せるか。図が一致しているだけで合格にしない。
- **一緒に考えた結果が残るか**：問い合わせ対応の「対応済み」を題材に、「返事を送った」と「相手が困りごとを解消して次に進めた」の違いを、担当者と受け手の視点で確かめる。その気づきが、やり方を続けるか、変えて試すかの判断に活きるかを見る。
- **その場の修正**：関係者の一言で正式・暫定を区別したまま直接影響をたどれ、複数の図と本文に矛盾なく反映できるか。根拠のない類似箇所は提案に留まるか。
- **二つの出口**：現行で目的を満たす場面では、改善案を無理に作らず、続ける理由と必要な支援を言えるか。変える場面では、何が分かれば続け方の判断が変わるかを試行前に言えるか。
- **持続するか**：しばらく運用して、当事者が意義と自分の役割を言え、自分で続け方を選べると感じるか。届け先に観察できる価値があるか。モデル作成速度や技術品質だけで代替しない。
- **相互に読み返せるか**：一件の成果を別チームへ渡し、渡し手は誰の何のためか、受け手は意図・実確認範囲・理由・未決を、補足なしで言い返せるか。外に揃える必要のない手順は違うままでよい。安全に関わる未決があるときは、一致しない状態を明記して進めないか。本人が関わり方を選べ、選ばない自由も残るかを別に確かめる。
- **同じ意味で再開**：前の会話がない別の人／AIが、権限内で目的、前後の関係、変更理由、未決を復元できるか。照合と承認を混同しないか。機密を共有側に足さずに再開できるか。

## 10案に共通して適用する読み合わせの前提

[既存の10案](step-2-ux-options.md)を比較する際は、以下を全案の前提とする。案2〜10の個別本文は、順に読み合わせるためそのまま残す。

1. 「合意した」「変更に着手した」を最終の成功にしない。組織・仕事の目的へのつながり、働く人が発揮したい力と納得、自分たちで選んで続けられること、届け先への持続的な価値を共通の物差しにする。つくり手の造形・モデリングの手触りとは分け、参加者・チーム内・チーム間の価値をそれぞれ確かめる。
2. 目的・目標から仕事／業務／作業をたどる案件内の階層と、案件ごとの境界・横断関係を共通の設計条件にする。GitHubの見栄えやREADMEのナビを各案の差にしない。
3. 一箇所の訂正で直接影響のある見方を直し、類似箇所は提案に留め、理由と未決を保存する。手渡す側と受け取る側が互いに意味を言い返せるか、どこまで共通理解が必要かを確かめる。違いが残るとき、誰が何を確かめるかを隠さない。安全に関わる未決を保留のまま実行してよいとはしない。
4. 持ち味・興味・伸ばしたいことがチームの目的とつながる機会をつくる。ただし本人が開示・参加を選ぶ。スキル採点、人事配属、全員一律、成果競争にはしない。
5. 現行を続けるか、小さく変えて試すかを全案で等しく扱う。必要な支援はどちらにも足せる。案の比較は誰のどの瞬間を一番支えるかで行い、案1の決定やStep 3へ進む根拠にはしない。
