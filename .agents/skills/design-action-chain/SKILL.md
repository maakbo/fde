# 処理の成果をつなぎ、失敗時の戻り先を決める

成果は[共通の成果形式](../../../guides/field-work/references/artifact-contract.md)と、この作業が参照する型の必須項目を保つ。既存記録への追記でも同じ項目を引き継ぐ。

## 入力

対象業務/成果の受取者、現行と変更案、起動・委任契約、根拠/版/許可、成功条件と実装制約。
前段の判断を再利用し、不足があっても許可内の下書きを返す。接続や送信の権限を作らない。

## 手順

1. 最後に受取者が何を開き、確かめ、判断できればよいかを具体化する。既存Flowの作業IDに、必要な処理を対応付ける。業務図だけを実行仕様にせず、製品利用と開発チームへの支援を区別する。
2. 取得/抽出・変換/生成・分類/保存・登録/人への確認や通知を、今回必要な成果が変わる境目で分ける。APIという名前で読取/書込を混ぜず、固定規則・通常ツールで足りる所へモデルを必須にしない。入力/処理/出力の三工程へ無理に押し込まない。
3. 各アクションに、実行役、入力の所在/ID/版と確定度、許可操作、出力/保存先の準備と利用権限/受取役、完了を確かめる方法を置く。抽出/生成結果は候補として原資料/期待へ照合し、形式だけで意味や権限を保証しない。情報不足は元の入力/判断者へ戻す。
4. 出力を次の入力へ結び、必要な前処理/参照/検証が終わる順に並べる。利用準備完了の通知は成果を保存し参照できることを確認してから。着手/進捗の通知なら、未完成である意味を明記する。人への通知、review待ち、人の承認、業務完了を別の状態にする。
5. 各失敗を取得不可、根拠不足/矛盾、出力不適格、保存失敗、通知失敗、確認者不在等へ分ける。止める後続操作、保持する成果/版/状態、返却先、再試行できる箇所と上限を置く。通知だけの再試行で下書き生成や書込を繰返さず、旧版の成果を新版の完成品として流さない。
6. 起動契約の仕事ID/版/権限を引き継ぎ、二重通知と別の依頼が同じ仕事かを判定する。途中/保存済み/完了不明を区別し、再開前に成果と副作用の実状態を確認する。処理後に記録が失われる故障や並列実行は、対応していなければ未検証。ログだけで一度限りの実行を保証しない。
7. 別workflowへ渡すなら、成果ID/版/利用可能状態/受取役/許可を接続する。異なる起動や失敗責任は必要なら分け、常に巨大一本/複数化とはしない。人の確定や外部登録を伴う部分は委任契約と照合する。
8. 通常一件と、入力不足・保存失敗・通知失敗後の再開・重複/旧版・未許可操作等の重要な条件で、下流へ何が渡るかを追う。実装を実行した結果と設計だけの追跡を区別し、必要な所だけ修正/再試行する。受取者の確認/修正/待ちを含む観測は既存Pilotへ渡す。

## 成果と完了

[既存workflow記録](../../../templates/workflow-brief.md)へ、処理の入力→成果→次の受取・確認と失敗/再開を残す。
次の実装担当が何を作り、どの証拠で完了/失敗を判断するかを説明できる。外部接続/実行器/モデル/本番と、机上・ローカル試行の未実施を分ける。
起動はdesign-trigger-contract、操作の権限はdefine-delegation-boundary、役割はpartition-agent-rolesの成果を再利用する。全体進行はworkflow-design-facilitation、実装受渡しはprepare-implementation-handoffへ。
