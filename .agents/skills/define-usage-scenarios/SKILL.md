# 利用場面の定義

## 入力

選んだ業務の目的/対象と版、現行の入力→行為→成果/受取者、具体的な依頼・出力の使い方、既存の要件/未決。全Discoveryや全要件定義の作り直しを要求しない。担当役の想定、本人の発言、観察、合意を分ける。

## 手順

1. 今回定義する使う場面を一つ選ぶ。仕事の全体目的、対象業務と開始/終了を参照し、作業や製品利用者の業務と混ぜない。出力を直接操作する人のほか、確認/承認/引継ぎで受け取る人を確認する。想定役は実任命や利用許可ではない。
2. 各役に「どんな時に何を受け取るか」「根拠をどこまで見られるか」「それを見て何を判断/実行するか」「不足/誤りなら誰へ何を返すか」を聞く。抽象的な『使いやすさ』は一件の具体例へ。年齢・性格・所属等を根拠なく作らず、利用条件に関係する経験やアクセスの差だけを扱う。
3. 短い利用場面の案を返し、通常例と重要な例外で訂正を受ける。本人不在の机上作業なら仮説と確認先を残し、回答や合意を捏造しない。直接利用者の便利さが、確認者/下流へ負担や欠落を移していないかも確かめる。
4. ニーズごとに必要な振る舞い/品質へつなぎ、要件IDと根拠の版を置く。機能、非機能、守る制約、検証が必要な仮定を分ける。同じ内容の二重記入は参照で済ませる。『RAGを使う』等の方式候補は要件へ混ぜず、正当な既存制約なら根拠を示す。
5. 要件から状況/入力→観測結果/許容しない結果という条件IDへつなぐ。誰がどの根拠で確認するかを添える。入力に挙げた重要例外それぞれに、観測結果と戻り先が対応するか確かめる。数値が無ければ観測可能な定性条件を使え、未知の閾値はTBDと測り方/確認先へ。人の評点との一致を真実・公平性そのものとせず、棄権や例外を消して数値を達成しない。
6. 受取者/入力/仮定/根拠の版が変わる別例を当て、変わるニーズ/要件/条件IDと残るものを示す。重要な仮定が崩れたら該当する受付/採用/操作を保留して目的や業務設計へ返し、無関係な準備まで一律停止しない。変更後も旧合格を自動継承せず影響条件を再確認する。

## 成果と完了

[業務要件定義](../../../templates/definition-brief.md)の利用場面6列、要件対応6列、確認条件5列を使う。同じIDの既存欄を参照してよい。**この作業だけなら**目的/対象/版/状態、利用場面→要件→確認条件、未決/次の受渡しが必須で、費用・全業務フロー・全要件一式を要求しない。

別担当が『この出力を誰が何に使うために、この要件があるか』を追え、重要例外の返却先と未確認が分かれば案として完了。現場確認や開始承認は別の状態で残す。原理/例は[利用場面と要件](../../../work/planning/references/usage-and-requirements.md)。全体の要件定義はdefinition-facilitation、図の対話はbusiness-flow-facilitation、測定設計はdesign-trial-successへ必要な時に渡す。
