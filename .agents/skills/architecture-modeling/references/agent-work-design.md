# 任せる仕事を、実行できる設計へつなぐ

Definitionで合意した「何ができればよいか」を受け、誰が何を使い、何を返し、
どう確かめるかを決める。構造のContextやFlowは必要な問いにだけ使う。

1. **条件を引き継ぐ。** 目的、入力、通常／例外、合格条件とID、制約、未決定、
   決定者を読み直す。未決定仕様は仮実装で確定させず、影響する範囲を止める。
2. **最小の方式を比べる。** 人、通常コード、既存システム、AIの解釈・生成・
   実行を操作ごとに分ける。モデル・直接参照／検索／追加学習・CLI/API/MCP・
   単一／複数agentを、必要性と負担から選ぶ。選ばなかった方式の理由も短く残す。
3. **設計意図を渡す。** 目的→条件ID→設計の選択と理由→変更箇所→検証ケースを
   対応させる。既存の規約・データ契約・エラー・副作用・権限を確認し、処理手順だけを
   渡さない。構造境界はArchitecture、順序と返り先はFlow、知識の適格性はKnowledgeへ。
4. **一回の作業を定義する。** 担当、入力の正本と版、起動、許可情報・環境・操作、
   変更対象、返す差分・理由・実行結果・残件を記録する。質問・停止・失敗・再開・
   復旧先を定める。読取・編集・実行・merge・本番操作の権限を一括にしない。
5. **実装の前に確認方法を決める。** 条件から通常・例外・権限拒否・副作用のケースを
   選び、何を独立に確認するかを決める。実装者が期待を変更してテストだけ通すことを
   防ぐ。机上／実行コード／モデル／現場試行のどの証拠を得るか明示する。
   再送や重複防止が受入条件なら、呼出し側の識別子発行・保持・再利用と、状態の
   有効範囲・期限も確かめる。同じ入力を渡す単体テストだけでは、その前提を検証できない。
6. **作業して返す。** 許可された範囲で調査・実装・テスト・修正し、実際のコマンド、
   環境、入力と版、結果、未実行、制限を返す。返却を受けた担当が条件・保守性・
   残るリスクを判断する。新しい仕様判断はDefinitionへ、誤った根拠はKnowledgeへ戻す。
7. **試行判断へ渡す。** [AI Pilot Evaluation](../../ai-pilot-evaluation/SKILL.md)で
   品質・定着・効果と残件を判断する。合格しても、実行していない接続・永続化・
   負荷・障害復旧・本番導入が成立したとは扱わない。

手順の実行条件・値・分岐・再開を具体化する時は[Workflow Design](../../workflow-design-facilitation/SKILL.md)、
担当へ渡す情報の選別は[作業の文脈](task-context.md)を使う。

記録は既存Issueや設計メモでよい。少なくとも「条件／設計と理由／担当と権限／
実装・ケース／実際の結果／未解決」が追えるようにする。

指示・例、受取側の出力形式、構造/意味/実行の検証と入力・出力の制御は
[prompt-and-output-contract.md](prompt-and-output-contract.md)で具体化する。
