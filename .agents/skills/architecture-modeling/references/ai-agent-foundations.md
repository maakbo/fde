# AIエージェントを仕事に入れるための基礎知識

[実装・テストの協働で試す](https://github.com/maakbo/fde/blob/main/examples/system-development/implementation/agent-assisted-flow.md)。仕組みを理解し、選択肢を比較し、人とAIの分担を説明するための知識。具体的な作業例や確認方法と結びつけて、実務の判断に使う。

## 1. 生成AIの得意さと、確かめる必要がある理由

機械学習はデータから傾向を学ぶ方法。その一種である深層学習は、多層のニューラルネットワークを使い、文章や画像などの特徴を学ぶ。教師あり学習は入力と正解の組、教師なし学習はデータ内の構造、強化学習は行動に対する報酬を手がかりにする。業務での「分類・生成」という処理の性質と、これらの学習方法は別の分類である。

LLMは文章をトークンという単位で扱い、文脈に応じて次のトークンを生成する。その仕組みで要約、説明、コード生成などもできるが、生成された説明が実際のソースや業務仕様に合うかは別途確かめる。存在しないメソッドや根拠のない仕様の補完は、もっともらしい出力の失敗例になる。事実、仮説、好みや評価も分ける。「保守しやすい」なら、誰がどこを理解しやすくなるのかまで確かめる。

**開発で使う時:** 設計書の読解、変更箇所の候補、テスト観点の作成を任せる。根拠の文書位置・実在する定義・呼出し元を示してもらい、コンパイル、テスト、レビューで確かめる。コードの説明が自然であることだけで採用しない。

入力に含められる量には上限がある。指示、参照資料、会話、出力などに使える量はモデル・実行環境で異なる。長く入れば理解や網羅性が保証されるわけでもない。トークンは費用にも関係するため、今回の変更に必要な仕様・コード・制約・期待結果を選ぶ。ただし短くするために例外条件を捨てない。足りない情報を推測させる代わりに、不明として返させる。

**モデル選択:** 単純な整理は軽量モデル、複雑な影響調査は強いモデルという仮説を置ける。同じ代表例で品質、所要時間、費用、人の修正負担を比べて決める。処理名だけでモデルを固定しない。

「作る・使う・任せる」という見方は、AIを作ること、個別作業の支援、目標に沿った業務遂行という違いを説明する入口になる。三つは併存する。AGI・ASIは汎用性や人を超える能力を論じる長期的な概念として読み、定義や実現時期を今回の設計前提にしない。身体性と知能の関係も未決着の議論として扱う。

## 2. エージェントは、考えた後の結果も見て進める

説明やコード案を返す一往復の支援から、目標を分け、情報を読み、道具を使い、結果を観測して次を決める進め方へ広げられる。たとえば「チェック処理を書いて」から、「既存の責務を確認し、合意した条件を満たす差分を作り、テストを実行し、未解決と共に返して」へ依頼を変える。

| 設計するもの | 開発作業での中身 | 欠けた時に起きること |
| --- | --- | --- |
| 推論・計画 | 影響調査、変更案、結果からの修正判断 | 決めた手順以外の状況に対応できない |
| 参照する情報 | 有効な仕様、既存コード、決定、失敗履歴 | 一般論で埋めたり、前回の判断を失ったりする |
| 実行手段 | 検索、ファイル編集、ビルド、テスト | 提案の後の操作が人に残る |

「頭脳・記憶・手足」は、この三つを点検する比喩として使う。すべての仕事で永続記憶や外部更新が必要という意味にはしない。保存資料と今回渡す文脈、モデル自体への学習を区別する。

**分担の考え方:** 調査、実装、検証を分けると、情報が足りなかったのか、変更を間違えたのか、確認を漏らしたのかを追いやすい。役割ごとの入力、出力、合格条件、失敗時の戻し先を決め、統括する側が全体の目的と現在地を持つ。別エージェントは独立確認、専門文脈、権限分離が必要な時に使う。分担による引継ぎ漏れと管理費用も比較する。同じcheckoutを複数の実装役が同時編集しない。

反応型は一往復の応答、支援型は人が採否を判断、協働型は合意範囲の判断・実行を分担、自律型は目標から実行・修正まで委任する、という語彙で話せる。名称だけでは権限は決まらない。ローカルでの差分作成・テスト、仕様の確定、PRのmerge、本番反映を別の操作として扱う。人の介入位置は業務の影響と権限に合わせ、設計時から決めておく。

## 3. いつ動くかと、どこまで任せるか

直接依頼、決めた時刻、出来事の検知という三つのきっかけがある。開発なら、影響調査の依頼、夜間の結果整理、PR更新後の差分確認に置き換えられる。人が課題を登録した後に自動で始まる処理は、登録イベントをきっかけにしている。

起動が自動でも、仕様判断やmergeまで自動とは限らない。同じエージェントが複数のきっかけで動いてもよい。まず日常の仕事に自然につながる一場面を選び、毎回の転記や別画面への移動を増やさない。同じ依頼を重複処理しない識別子、実行済みの状態、再開位置も決める。最後の三点はfdeでの運用への補足である。

## 4. AIに考えさせるところと、規則で実行するところ

手段を選ぶ手がかりは、入力形式、文脈判断、例外の種類と頻度。RPAは定型の画面操作を再現する手段で、画面変更や入力不良への対応が要る。API、スクリプト、既存機能でも同じ目的を達せるなら比較する。

開発では仕様の曖昧さの整理や影響調査にAIを使い、フォーマット、ビルド、テスト、数値の範囲チェック自体は規則とコードで実行する組合せがある。自然言語でも固定の分類規則で足りる場合はある。反対に定型帳票でも読取誤りや業務判断は残りうる。入力形式だけで採用を決めない。

## 5. MCPは、使える道具を共通の方法で接続する

開発エージェントが課題、コード、文書、CI結果へ触れる時は、既存連携、CLI、API、MCPが候補になる。MCPではホストとなるAIアプリ内のクライアントが、情報や操作を提供するサーバーとやり取りする。ツールの一覧・説明・入力形式を取得し、実行できる。

M×Nは、複数モデルと複数ツールを個別につなぐ負担を考える説明である。共通インターフェースにそろえると連携の再利用を狙えるが、実装数や費用が必ずM＋Nになる保証ではない。変換、認証、テスト、運用は残る。MCPは接続仕様であり、どのツールを選ぶか、どう文脈を渡すかはホスト側の実装にも依存する。

**設計担当へ渡す:** 現在と追加予定の接続先、必要な読取・更新操作、モデル変更の予定、既存の開発・ワークフロー環境、認証と運用担当を整理する。課題の読取と、本番DBの更新を同じ権限にしない。少数のローカル操作が既存CLIで足りるなら、MCPサーバーを先に作る必要はない。

## 6. 価値は、作った量より仕事が前へ進んだか

定量面は、着手からレビュー可能になるまでの時間、手戻り、見逃した欠陥、確認工数など。定性面は、利用者が迷わない、開発者が変更理由を説明できる、レビュー担当が安心して引き継げる、といった変化。相手の関心に合わせて説明するが、都合よく効果を作らない。

TCOには導入、資料整備、API等の利用、確認、監視、保守が含まれる。短縮時間は、余力の創出と実際の支出減を区別する。同じ対象期間の便益と費用が揃えば、`ROI = (便益 − 費用) / 費用 × 100`で見ることができる。金額化できない価値とリスクも判断に残す。費用・算式の記入は[見立ての記入欄](../../../../templates/agent-feasibility.md)を必要な時だけ使う。

## 7. 失敗を、運用のどこで拾うか

| リスク | 開発での現れ方 | 確かめること |
| --- | --- | --- |
| 信頼性 | 存在しないAPI、誤った仕様、自己都合のテスト | 原資料・実在する定義・期待結果と照合する |
| 利用定着 | 指示や確認が増え、人が直接直すより重い | 使わない理由、修正時間、日常作業との接続を見る |
| 管理不明 | 誰の指示で、何を読んで変更したか分からない | 目的・管理者・権限・版・変更結果を追えるようにする |
| セキュリティ・倫理 | 資料内の命令で権限外操作、漏えい、不公平な判断 | 読む資料を命令権限と混同せず、入力・出力・実行権限を組み合わせて制御する |

リスクは連鎖する。誤りが多くて使われなくなり、放置され、管理者や設定が分からなくなる場合もある。小さく試し、担当者、観測方法、止める条件、引継ぎ先、再開条件を一緒に決める。コード生成と実行が成功しても、業務の正しさと公平性は別に確認する。

## 8. 技術の変化を、選べる手段に変える

| 見方 | 手段と使いどころ | 確認する条件 |
| --- | --- | --- |
| 実行へ広げる | API・MCPで道具を呼ぶ、ブラウザで既存画面を操作する | 必要操作があるか、API等で足りるか、画面変更や権限に耐えるか |
| 専門性を補う | 検索・RAGで該当資料を渡す | 必要箇所と例外を取れているか、版が正しいか |
| 振る舞いをそろえる | 追加学習で望む応答や処理を学ばせる | 十分な事例と評価があるか。頻繁に変わる仕様の参照を代替できると考えない |
| 相手に合わせる | 経験や役割に合う説明を出す | 個人情報を増やさず、説明量を調整できるか |
| 入力を広げる | 画像・音声等を扱う | 画面や図が実際に必要か、文字や構造化情報で足りるか |
| モデルを選ぶ | 強い推論、規模拡大、小型・軽量・ローカル実行 | 品質、時間、総費用、運用・情報管理が合うか |

フィジカルAIは現実の設備操作まで実行範囲を広げる話として知っておく。今回のソフトウェア改修では対象外だが、設備と接続する業務へ広がれば別途検討する。大きいモデルなら必ず正しい、小型・ローカルなら無料、画像なら正確に読める、といった前提は置かない。

技術名を覚えた後は「どの入力・どの判断に効くか」「品質・速度・総費用は合うか」「今の性能で使えるか」を一件で試す。検索で情報を補うことと、追加学習で振る舞いを調整することは目的が違い、組合せる場合も評価が要る。
