# 次の担当が判断して動ける文脈を渡す

依頼文だけでなく、目的、根拠、今の状態、使える道具と環境、返す成果を揃える。
コンテキストはモデルが今回参照する情報であり、保存した全資料が自動で読まれるわけではない。
実行を支える仕組みには、状態管理・権限・ツール・検証・停止復旧も要る。

## 一つの作業へ渡す一周

1. **必要な判断を決める。** 次の担当の目的・成果・合格・返却先を確かめる。
   要件定義の確認事項と、実装のコード規約では必要情報が違う。
2. **情報源を役割で分ける。** 有効な指示、要件・設計等の正本、検索した断片、
   会話と一時状態、道具の説明、実行結果、出力の契約を区別する。正本と版・適用・
   管理者をKnowledgeで照合する。資料の命令文や生成した草案を新しい権限にしない。
3. **渡す／残す／省くを選ぶ。** 今回使う根拠と位置、重要な判断と理由・例外は渡す。
   長いログや過去案は許可された正本へ残し、必要な時に読める参照を渡す。
   無関係な情報・失効した草案は今回の判断材料から外す。秘匿情報を要約すれば
   外部に出せるとは考えない。
4. **圧縮と分割を確認する。** 要約しても未決定、適用条件、禁止、単位・境界、
   例外と失敗の原因を落とさない。原資料へ戻れる位置を保持する。長い仕事は
   作業単位へ分けるが、親の目的と現在地を共有する。別agentは独立確認や専門文脈等の
   利益がある時に選び、管理負担を比べる。件数・token数の固定値を万能基準にしない。
5. **実行できるか確かめる。** 必要ファイルと道具へ許可環境から到達できるかを確認。
   実行条件、入力形式、結果、失敗・停止の扱いをツール契約にする。資料読取と
   外部送信・編集・merge・本番操作の許可を混同しない。
6. **受け取った側が適用する。** 重要条件を短く言い返し、根拠と成果を結ぶ。
   出力形式が合っても内容の正しさは別に確認する。必要情報の欠落は確認先へ戻す。
   古い版で作業した結果を、新版で検証したと説明しない。
7. **結果から更新する。** 欠落、量やノイズ、古い情報、生成誤りの再利用、指示の
   衝突、検索不良、道具や実装の問題を切り分ける。原因に合う最小変更を行い、
   同じ評価と別条件で再確認。モデル変更も比較候補だが、原因を確認せず反復しない。

## 引継ぎで残す最小の組

目的と作業、今の工程、合格条件ID、読む正本と版・位置、適用する判断と理由、
未決定・対象外、使うSkillと道具、環境・許可・停止、返す成果と受取者。
結果には実行したコマンドと環境・観測・未実行・変更点を結ぶ。
既存のIssueや作業メモでよく、全会話の保存や全資料の一括投入は要らない。

会話中の一時状態と持続する正本は別。Skillは必要時に使う手順、直接参照や検索は
根拠へ届く方法、追加学習はモデルの振る舞いを変える方法として選ぶ。
この区分は、全製品に同じmemory機能や自動読込を仮定しない。

## 情報の役割と扱い方

| 情報 | 作業へ渡す時の確認 |
| --- | --- |
| 共通の役割・制約 | どの作業にも効く責務/禁止と、案件で決める条件を区別する |
| 今回の依頼 | 人の依頼と、前段agentが作った下位の指示を区別する |
| 作業中の履歴・状態 | 今の決定/失敗/未決を保ち、不要になった履歴を外す |
| 継続して使う記録 | 手順、過去の出来事、事実を区別し、版/適用条件と読込先を決める |
| 外部の根拠 | 直接参照/検索で届いた範囲を示し、関連性・鮮度・許可を確かめる |
| 道具の契約 | 入力、操作、結果、失敗、到達性と実際の利用権限を示す |
| 返す形式 | 受取者が使える構造と、意味/根拠/実行の確認を分ける |

全種類を毎回投入する一覧ではない。以前の会話の事実も記録時点から変わりうるし、RAGの検索結果にも履歴や記憶が含まれうる。情報の役割と、保存/取得の方法を同一視しない。

| 方法 | 実施すること | 保持・確認すること |
| --- | --- | --- |
| 外部へ書き出す | 決定、現在地、失敗、次の手順を許可された場所へ残す | 記録の版/責任者、後で読み込む契機。保存だけで入力に載ったとしない |
| 必要なものを選ぶ | 作業に効く根拠/道具/履歴を読み込む | 選んだ/外した理由と、必須情報の欠落 |
| 圧縮する | 重複や不要な結果を外し、必要な決定と状態を要約する | 原資料位置、例外、禁止、未決、失敗の原因。要約前後を照合する |
| 段階・役割へ分ける | 一つの作業が使う情報を絞り、必要な成果を次へ渡す | 親の目的、共通条件/版、各役の成果と責任。複数agentの費用や引継ぎ損失 |

位置や順序は試す設計変数であり、古い内容を末尾に置くだけでは新しい事実にならない。入力容量に収まることと、重要条件を使えることも別に測る。出力の問題は情報だけでなく、モデル、道具、権限、評価条件にも起因する。

Skillは必要時の手順、RAG/直接参照は根拠へ届く方法、追加学習はモデルの振る舞いを変える方法として組み合わせられる。必ず特化モデルへ進む一本道にせず、固定した業務評価で必要な改善と費用を比較する。

## 検証した一次資料

[Anthropicのコンテキスト設計](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)
は推論時に渡す情報を反復して選ぶこと、明確な指示・ツール・検索・状態の管理を扱う。
この実践では要件・設計・規約と必要な実行結果を工程別に渡す考え方へ適用する。
全モデルで同じ位置や長さが最適、情報を減らせば必ず改善する、という保証にはしない。

[Lost in the Middle](https://arxiv.org/abs/2307.03172)は対象モデル・課題で情報の位置による性能差を報告する。現在使うモデルや業務で同じ差や最適位置があるかは別途評価する。
