# 変更案を担当者が使う一件の流れへ具体化し、人とagentの役割・例外・成果を設計する

## 開始入力

目的と現行、比較した改善案、許可/制約、受取者と望む成果。
今ある事実から仮説/下書きを返し、不足を優先して確認する。実際の権限・合意・観測を代作しない。

## 実行

1. 目的と守る条件、変更してよい範囲を置き、理想案/期限内案/現行維持を区別する。
2. 担当者が始めて結果を使うまでを具体的な場面で書く。入力、処理、確認、返却、登録を分け、確認内容と時点を示す。
3. 通常/情報不足/例外/担当不在を通し、人とAIの許可、止める操作、継続する仕事、戻り先を置く。
4. 現行に変更案を混ぜず別の版にする。現場の具体例/訂正を受け、操作負担や責任の抜けを直す。
5. 各変更が品質/利用/業務成果へどう影響するか仮説と観測を分ける。効果額/実承認/稼働を物語から作らず差分分析へ渡す。

## 成果と完了

[作業の記録](../../../templates/field-work/process-change-record.md)の必要な欄を使う。
使う一件で開始/役割/受渡し/完了/例外が説明でき、変更案と現状/実決定が分かれる。
原理や手法の違いが判断に必要な時だけ[業務分析の判断](../../../guides/field-work/references/work-analysis-methods.md)を読む。
不一致や新条件は該当作業/判断者へ戻す。全様式の記入を開始条件にしない。
