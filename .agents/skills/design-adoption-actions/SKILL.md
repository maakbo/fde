# 定着施策の設計

## 入力

対象業務/変更案/受取者、本人の発言と具体例、既存の許可/役割/支援・評価条件、未決事項。実本人が不在なら仮説と提案から始め、納得や習熟を代作しない。

## 手順

1. 誰のどの仕事をよくしたいか、既存の条件/版と今回の準備許可を引き継ぐ。支援する一作業と親の目的・受取者を示し、不要作業の除去/統合/順序/簡素化や人・既存手段・AIの比較について、既存の判断と根拠を参照する。未検討なら未決としてDiscovery/業務設計へ返し、AI利用そのものを目的にしない。新しい選定帳票や全体再設計を要求せず、許可済みの施策案の準備は進める。作業の入力→確認→次の受取者までを範囲にし、開発チームと製品利用者の業務を混ぜない。聞取り不足はclarify-adoption-conditionsへ同じ記録で返す。
2. 発言/事例と原因仮説を分け、必要性/役割への疑問、参加の懸念、やり方、実行の能力/時間/アクセス、継続の支援のどこを確かめるか選ぶ。『AIに無理』という発言にも技術/仕様上の根拠を聞く。否認/抵抗/受容は問いを考える補助で、人の固定ラベルや必ず進む順番にしない。
3. 原因に対応する施策を比較する。必要性なら対象の課題/目的と根拠、役割不安なら変わる仕事/未決を本人と確認、知識なら説明/練習、資料/品質なら原資料や設計の修正、時間/権限なら実際の資源判断へ。研修や励ましで全てを解決せず、担当/資源/実施条件と次に確かめる行為を置く。雇用/待遇/回復を保証しない。
4. 小さく試す範囲は、意味のある成果を短期間で確かめられ、受取者が理解でき、失敗を検出/戻せるものを選ぶ。簡単な成功例だけで代表性や重大例外を省かない。既存の成功条件/上限/停止条件を引継ぎ、仮説→方法→実施→観測→修正/再試行へつなぐ。負担増は学習・確認・誤り等の原因を分け、品質/権限違反や上限超過を『適応の谷』で免除しない。判断は既存Pilotへ、基準変更は理由/決定者/版へ返す。
5. 『この業務イベントが起き、必要条件がそろえば、この役がこの作業をする』という使いどころを設計する。入力/版/許可、依頼内容、返す成果/受取者、保存先、確認/訂正、相談/手動代替、締切までの負担を結ぶ。出来事がない/資料が遅い/確認者不在なら何を進め何を待つかも置く。人が選んで使う計画とソフトウェアの自動起動を区別し、後者が必要な時だけdesign-trigger-contractへ渡す。
6. 実物または架空例で通常→条件不足→別条件の受渡しをたどる。本人による実行を確かめる時はrehearse-ai-assisted-workを使い、代行と支援を残す。予定と実施済み、AIによる文書適用と実本人の能力/同意、練習の成立と現場効果を分ける。
7. 相談/働きかけは、対象者が使える接点、目的、伝える材料、担当、頻度/容量、返ってきた声の記録先を決める。既存のレビュー会・短時間相談・文書/オンライン・対面等から選び、配布数/接触回数/満足度を定着の証拠にしない。実データの持込みを要求せず、保護対象と許可を確認する。全員へ同じ研修/対面/毎日利用を課さない。
8. 異議/不明/失敗へ『具体例と困った点を教えてほしい』と返し、誰が根拠を確認し、入力/資料/手順/Skill/支援のどこを直し、いつどの条件で試し直すかを決める。人格への非難や不利益を避ける提案と、守る品質/権限基準を両立させる。無言/好意的反応/失敗報告ゼロだけで心理的安全性を断定しない。観測、残る負担、使えない理由、次の判断者を既存の評価記録へ渡し、継続/修正/待ち/停止/別手段を選べる状態にする。

## 成果と完了

[体制・定着計画](../../../templates/team-adoption-brief.md)の「定着施策と使う場面」を使い、施策6列と業務イベント6列を保つ。既存の支援/評価/練習記録をIDで参照し、同じ値を複写して別管理しない。原因仮説と支援の関係、実施資源/未確認、条件不足時の戻り先、声を受けて直す経路と次の観測が別担当にも追えること。施策案を作っただけで導入済みとしない。
背景/選択肢は[定着を支える方法](../../../work/operations/references/change-support.md)。推進機能の体制はdesign-adoption-support、職務/育成はredesign-work-role、効果の測定/判定はdesign-trial-success/ai-pilot-evaluation/decide-trial-next-stepへ同じ対象を渡す。
