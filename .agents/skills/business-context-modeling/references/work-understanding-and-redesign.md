# 一件の仕事から、変え方を考える

「AIを入れると速くなりそう」から一歩戻り、誰の何を良くするのかを確かめる。[システム改修の相談から試す](../../../../examples/system-development/work-improvement.md)。

## 仕事の意味と、作業の手順を行き来する

目的を持つ仕事、その成果を生む活動、具体的な操作では、見たいものが違う。「改修を届ける」「影響を調べる」「呼出し元を検索する」を同じ粒度で並べると、改善対象がぼやける。現場で使う呼び名を残し、今はどの成果・責任・操作を話しているかを合わせる。名称だけで固定した階層を作らない。

まず入力、変換、出力（IPO）で一つの活動を説明する。「依頼と現行仕様から、変更条件と影響範囲を整理する」なら、速さだけでなく、入力不足や出力の使いやすさも論点になる。質の悪い入力を後工程の頑張りで補っていないかを見る。

## 現行は、一件の実際から確かめる

担当者に「標準手順を教えて」だけで終わらず、「最近の一件を、受け取ったところから一緒にたどらせて」と頼む。取り締まりや担当者の評価が目的ではなく、次の人も進められるように判断を理解したい、と伝える。

- **始まり:** 何を、誰から、いつ・どこで受け取り、何が揃えば始めるか。
- **操作と情報:** どの資料・画面・コードを見て、何を確かめ、何を作ったか。手順書と違った箇所はなぜか。
- **判断:** どの手がかりで分けたか。迷った例、通常と違う例、他の担当者なら変わる判断はあるか。
- **終わりと引継ぎ:** 誰へ何を渡し、何を満たせば完了か。不足したら誰へ戻るか。本人が不在なら誰が判断できるか。

Who / What / When / Where / Why / Howを聞き漏らしの点検に使う。毎回すべて質問する台本にはしない。実演・手順書・成果物を照合し、観察できた事実、本人の説明、自分の仮説、未確認を分ける。録画や実データの持出しを前提にしない。共有が難しければ匿名化した例や再現操作で確かめる。

作業時間と待ち時間も分ける。開始・終了だけでは、考えていたのか、返答待ちなのか分からない。一件は発見の入口であり、頻度や平均の証拠にはならない。通常例に加え、例外・差戻しを見てから対象範囲を広げる。

## 変える前に、残す理由も調べる

BPRは、今ある仕事の存在理由や役割分担から組み直す考え方。小改善は、今の枠内で手間や間違いを減らす進め方。規模の大きさだけで良し悪しは決まらない。変えられない制約があれば、目指す流れ、制約、当面変える範囲を分け、小さく確かめる。

ECRSは、不要な仕事を磨く前に問い直す順序として使える。

| 観点 | 仕事に向ける問い | 判断に必要なこと |
| --- | --- | --- |
| Eliminate / なくす | この出力は誰が何に使うか。なくすと何が困るか | 利用先と責任者、契約・統制・品質上の必要性を確認する |
| Combine / まとめる | 同じ根拠を別々に集め、転記していないか | 統合後も責任と必要な独立確認を保てるか |
| Rearrange / 順番を変える | 後で判明する不足を、着手前に分かるようにできるか | 前へ移す判断に必要な情報が、その時点であるか |
| Simplify / 簡単にする | 残る操作や説明を減らせるか | 例外や証跡を落とさず、受取者が使えるか |

理由が分からない工程は調査候補。不要だと決めない。価値を直接生む仕事、重複や手戻り、必要な統制を見分けるが、分類だけで廃止しない。削除にも移行・教育・監視の負担がある。規則が明確なら通常コードや既存システム、文脈の読解ならAI支援、責任を伴う採否は権限を持つ人、と候補を比べる。単純な繰返しであることだけではAIを選ばない。

現行（As-Is）、目指す状態（To-Be）、その間の変更と確かめ方をつなぐ。現行に「AIで半減するはず」を混ぜない。新しい事実が出たら、現行の理解も目標も更新する。一度で全体を確定する手順にはしない。

## 見たい問いで、表し方を選ぶ

| 今、分からないこと | 選ぶ見方 | 見えることと限界 |
| --- | --- | --- |
| この仕事は何を成果に変えるのか | IPO | 入力→処理→出力。担当や受取者は別に確認する |
| 誰から受け、誰が結果を使うのか | SIPOC | Supplier / Input / Process / Output / Customer。提供者と受取者は社内の人やシステムも含む。二次利用者は追加で確かめる |
| 何をどこまで分ければ任せられるか | HTA（階層的タスク分析） | 目標を下位作業へ分け、順序・条件・完了を補う。分割だけで人とAIの担当は決まらない |
| どこで渡し、待ち、差し戻すのか | フロー／担当別のレーン | 順序・担当・判断・戻り先。関係全体を一枚へ詰め込まない |

全部を一式で作る必要はない。短い文章や表で問いが解ければそこで止める。SIPOCの情報を既存のActor・Information・Systemの関係表に持てるなら再利用する。HTAの細かな操作を、すべてBusiness Contextの業務ノードへ持ち込まない。関係はContext、順序が争点ならFlowという既存の区別を保つ。担当別表示が必要でも、担当欄の表から試せる。

## 最初の変更を選ぶ

欲しい成果への効き方、情報と規則の揃い具合、失敗の影響と戻しやすさを比べ、「今試す／証拠を集めてから／今回は扱わない」と理由を残す。簡単な作業から着手しても、ボトルネックに効かなければ成果にならない。

変更後は、誰が何を受け取り、何を判断し、どこへ返すかまで説明する。工程数やAI利用回数で成功を判断せず、待ち、手戻り、受取者の確認負担、品質を同じ範囲で比較する。期待値と実測を分け、改善しなければ入力・分担・選んだ対象へ戻る。
