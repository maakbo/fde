# 必要な資料を対象・版・適用条件・権限で区別できる属性を設計し、作成更新の手順へ組み込む

## 入力

対象業務と受取者、許可された資料/実データの例、現在の手順と分かる範囲の制約。
不足を明記し、今ある根拠から返せる下書きを進める。実在の機微情報原本の収集や外部投入を既定にしない。

## 手順

1. 誰がどの判断のため、どの資料と何を区別するかを一件で置く。全社の既存データ移行を開始条件にしない。
2. 資料/断片の安定ID、原資料の位置、版/有効状態、対象業務/環境、所有者、利用範囲などから必要な属性を選ぶ。各属性に意味/型や語彙/値の根拠/欠損時の扱いを置く。知らない版・承認・所有者を埋めない。
3. 同名異版、環境違い、未承認新版、権限外資料で参照条件を試す。更新日だけで現行とせず、欠損や矛盾はその判断を保留し根拠管理者へ返す。確かな部分の下書きは続ける。
4. 属性は絞込みや照合を支えるが、タグを付けただけでアクセス制御や検索品質が実装されたとはしない。利用許可は根拠と実装側の強制を分け、許可されない情報を検索/プロンプトへ出さない。
5. 今後の作成/更新時に誰がどの原資料から属性を設定・確認するか、旧版/訂正/利用先への反映を決める。名前統一や項目分割は原意と既存ID/参照を保つ変更案とし、原本を上書きしない。
6. 小さな一件で属性の欠落/矛盾を見つけて記録を直し、別の一件で再試行する。元資料の確認、検索索引/権限/配備更新と実測は未実施ならそのまま残す。

## 成果と完了

[作業の記録](../../../templates/field-work/data-processing-record.md)を必要な部分だけ使う。
属性の目的/定義/根拠/不明/更新担当と、正しく区別できた例・失敗・訂正が追える。新規更新と必要な過去整備を分け、全移行を強制しない。
背景は[情報と処理を分ける](../../../guides/field-work/references/data-and-processing.md)。
