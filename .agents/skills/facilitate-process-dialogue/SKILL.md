# 業務の関係と手順を図で返し、担当者の具体例で訂正して反映する

## 開始入力

対象業務/問い/読者、現行か変更案か、根拠のある関係者/情報/作業と担当者の説明。
今ある事実から仮説/下書きを返し、不足を優先して確認する。実際の権限・合意・観測を代作しない。

## 実行

1. 何を確かめる図か、境界/状態/粒度を一つずつ置く。変換ならIPO、供給/受取ならSIPOC、分解なら目標木、関係ならContext、順序/役割ならFlowを選び、全部を必須にしない。
2. 元の言葉からactor/business/information/external systemを整理し、未観測は未観測とする。関係者/情報×業務の対応から同じ粒度のContextを作る。
3. Flowは選んだ一つの親業務IDを展開する。担当/順序/分岐/受渡し/戻り/完了はFlowと説明へ置き、Contextの線を時間順にしない。
4. 図と短い説明を返し「この一件なら誰が何を受け、ここでどう返すか」と具体例でたどってもらう。実回答がなければ聞く問いと仮説までを返す。
5. 訂正を根拠付きで図と説明へ反映し、変わった業務境界や責任は親図へ戻す。再確認の実施/未実施を区別し、合意を捏造しない。
6. Mermaid等の表現は利用環境の規約で作り、ソース検証と実描画の確認を区別する。使えない描画環境でも表/言葉で訂正を進め、画像が確認済みと報告しない。

## 成果と完了

[作業の記録](../../../templates/field-work/process-dialogue-record.md)の必要な欄を使う。
図を返す→具体例/訂正→反映/再確認が追え、ContextとFlowの親子/状態が明確。実参加者の確認がなければ仮説である。
原理や手法の違いが判断に必要な時だけ[業務分析の判断](../../../guides/field-work/references/work-analysis-methods.md)を読む。
不一致や新条件は該当作業/判断者へ戻す。全様式の記入を開始条件にしない。
