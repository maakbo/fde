# 改善対象の選定

## 入力

親の目的/望む変化と受取者、現在の流れ/困り事、候補IDと根拠/版、ECRS等の見直し、量・人手/待ち/手戻り、情報/許可/資源/リスクの既知と未確認。全てが揃わなくても比較案を作り、不足を0や実現不可と決めない。既知の不足（今週の確認時間0分など）と、値や担当が未確認の項目も分ける。

## 手順

1. 今回選ぶ改善範囲と、次に何を判断するかを置く。開発者の要件/設計/実装/レビューの仕事と、製品利用者の仕事を分ける。親業務の目的と入力→成果/受取者を保持し、既存の観察/図/候補をIDで参照する。新しい一式のDiscoveryや全フォームを要求しない。
2. なくす/まとめる/順番/簡素化、役割/情報/通常ツールの改善を先に候補へ含める。目的/統制/利用先が不明な工程を不要と決めない。既存判断がなければ仮説として比較し、実施や合意を代作しない。
3. 一件の作成/処理、人手、機械、待ち、確認/訂正、下流の成果を分け、何が全体の目標を制約するかを根拠から考える。最大の工数/件数や簡単に作れることだけでボトルネックを確定しない。範囲/単位/期間/対象機会を合わせ、資料が少ないなら仮説と追加観察へ。件数×一回の時間はその工程の工数であり、経過時間や改善効果ではない。
4. 候補ごとに、人/ルール/既存システムとAI補助を比較する。言語/非構造化情報や文脈判断があることはAI候補の理由だが、実現/有用性の証拠ではない。固定した検索/集計/定型確認は通常手段も検討。混在する業務は操作を分ける。誤りの重大性、検出漏れ/偏り、確認者の正本/技能/時間/拒否権、停止/回復、データの利用条件を選定時から扱い、後工程任せにしない。秘密情報/対人/物理操作だから全てのAI補助を一律除外せず、許可環境と今回任せる操作を確認する。
5. 効果の大きさ×実現のしやすさを、既存候補表の効果/実現可能性へ根拠付きで置き、リスク/AI適合性も併せて比較する。効果には誰の負担/待ち/品質/価値か、実現にはデータ/接続/能力/時間/許可/維持を示す。効果の大きさ、実現条件の充足、根拠の確かさを混ぜない。情報が詳しいだけで効果Highとせず、根拠の状態は別に添える。High/Medium/Lowは判断理由と基準を添え、不明はTBD。実現の難易度を使うなら軸の向きも示す。根拠のない点数/重み/合計順位を作らず、権利/品質/許可の条件を高い効果で相殺しない。
6. 一つの対象、または選定を変える不足を確かめる観察を選び、他候補を先にしない理由と見直し条件を返す。短期で確かめられ、相手に意味があり、戻せる範囲は初期候補になり得るが、成功しやすい定型例だけで全範囲を代表させない。AIが不要なら通常の業務改善を選べる。選定案を組織の承認/本番/支出許可にしない。
7. 対象/対象外、望む変化、選択理由/根拠、仮の手段、重要判断/例外、未決と確認先、次の受渡しを同じ記録へまとめる。Definitionが必要ならdefinition-facilitationへ、根拠不足なら最小の聞取り/measure-workload-and-waitへ返す。次の担当が何を確かめると選択を変えるかを具体化し、製品/プロンプト/RAGの詳細へ飛ばない。既存許可内の準備は進め、未決依存の操作だけ待つ。

## 成果と完了

[業務課題・改善候補の整理](../../../templates/discovery-brief.md)へ候補比較7列、量/優先順位を使う時の参照6列と、最初の対象または観察/対象外/見直し条件/次工程を残す。既存の現状・観測・ECRSは該当ID/箇所を参照して再利用できる。目的/現状/根拠を省略した理由不明の順位だけにしない。
選定前後で同じ対象/目的が追え、別担当が選択と不足を説明できること。使う観点の理由や限界は[改善対象の比較](../../../work/discovery/references/target-selection.md)。全体進行は[Discovery](../discovery-facilitation/SKILL.md)、自動化の構成を詳しく選ぶ時はcompare-automation-optionsへ渡す。
