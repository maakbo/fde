# PoC検証の実行

## 入力

試す不確実性/対象と対象外、要件と合格条件ID/版、設計/入出力契約、評価入力と期待、許可環境/操作、確認者、反復/時間/費用の上限。既存の計画と成果を使い、欠測/未合意/権限不足を作らない。設計だけでも返せる部分と、実行できる範囲を分ける。

## 手順

1. 今回減らす不確実性を一つ置く。試作品という成果物、実現性を判断するPoC、最小でも利用価値を届けるMVPを区別し、名称だけで準備済みにしない。成功条件の不足はdesign-trial-success、対象/責任の変更はDefinitionへ差分を返す。
2. 入力/正本と版、期待する振る舞い、評価者/判定規則、実行物/指示/モデル/設定を試す前に記録する。通常・境界・不足・少数でも重大な例外を目的から選び、調整用と別条件を分ける。件数/比率を例から固定せず、専門担当の不一致や正解未確定は確認待ちにする。
3. 必要な機能だけを作る。人/通常コード/AIを操作ごとに選び、用意済み出力の再生はモデル生成試験と区別する。装飾は省けても、重大な失敗の検出/停止/返却は省かない。許可情報と保存/削除、外部接続/認証/操作、既存業務への影響を確かめ、隔離の実態と未検証を残す。ローカルやテストデータという名だけで安全と認定しない。
4. 実行して入力・対象版・出力/エラーと実施範囲を保存する。構造、根拠/意味、操作権限を別に照合し、必要な人の確認を処理に組み込む。誰が何を見て判断/訂正/拒否できるか、時間/アクセス/能力、不在時の待ちや返却を定める。生成者の自己申告や模擬の役割設定を、人の実確認/認証にしない。対象が変わった時に旧確認を流用しない。確認記録自体の欠落/型不正も、処理が落ちず返却できるか試す。
5. 条件ごとに期待と実際、未達/欠測/未確認、失敗段階/影響を残す。許容しない失敗を平均や速度で相殺しない。時間なら起終点/分布/失敗を示し、平均だけから全件の期限遵守を主張しない。品質が通っても実利用や効果は別の観測として残す。
6. 原因仮説を資料/検索/指示/契約/実装/確認体制/仕事への適合へ分け、根拠から最小の修正を選ぶ。人の訂正は条件/例/指示/コード等の所有者へ戻し、記録するだけでモデルが学習したと扱わない。複数変更の影響や、合格させるための基準変更を隠さない。
7. 変更箇所/理由/版と保持した条件を示し、同条件の退行と別条件で確かめる。調整に使った集合での改善は未知入力への一般化ではない。上限に達したら成功まで回さず、証拠待ち/停止/別手段も返す。重大失敗や許可喪失では早めに止め、合格を必ず繰り返す終了規則にしない。
8. 条件別の結果と未測定、実装済み/未実装、使える範囲を既存の試行記録へ戻す。判断案はdecide-trial-next-stepへ引き継ぎ、続行/修正/待ち/停止/方向変更の理由と、次の実操作の許可を分ける。全工程をやり直さず、結果を判断できる確認者へ返す。

## 成果と完了

[PoC計画・評価](../../../templates/ai-trial-brief.md)の実行記録、ケース5列、修正再試行6列を使う。今回の対象/条件/版/許可、実行と観測、必要な確認、修正/同条件と別条件、限界/次の受渡しが追えること。この作業だけで実現場の効果や全体計画の全欄を埋める必要はなく、未測定と取得先を残す。

完了は必ずしも合格ではない。確認した条件と残る不確実性から、次の担当が進める範囲と戻り先を説明できればよい。全体進行はai-pilot-evaluation、原理と運用への境界は[検証と学習](../ai-pilot-evaluation/references/operational-learning.md)。HITLは確認の工程、フィードバックループは実行・評価・改善の循環であり、同義ではない。
