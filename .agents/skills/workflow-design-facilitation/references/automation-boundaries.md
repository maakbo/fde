# 自動化を、任せる行為ごとに選ぶ

都度の相談、用途に合う指示と知識を揃える支援、決めた処理を連鎖するワークフロー、
目標に合わせて次の行動を組み立てるエージェントは、仕事に合わせて組み合わせられる。
外部接続があるから自律型、対話型だから実行不能、という分類はしない。
製品名や段階の名前ではなく、誰が順序・判断・操作を決めるかを確かめる。

| 選ぶ形 | 有用な場面 | 残る負担・境界 |
| --- | --- | --- |
| 都度相談 | 依頼や進め方を探索する | 必要な根拠と期待を毎回確かめる。初期費用ゼロとは限らない |
| 用途別の指示・知識 | 同じ考え方や作法を繰り返し使う | 資料の版・権限・評価が要る。設定しただけで再現性は保証されない |
| 固定の手順と分岐 | 入力、条件、次の処理を事前に定められる | 通知、待機、再試行、人への返却も設計できる。例外や責任は自動では明確にならない |
| 範囲を限定した計画・実行 | 調査や実装の途中結果から次の手を選ぶ必要がある | 道具と権限、費用、時間、止める条件、検証・引継ぎを制御する |

システム開発なら、担当者の仕様判断、エージェントの調査・実装、通常ツールのビルドと
テスト、担当者のレビューを組み合わせる。一段ずつすべて経験することを条件にしない。
小さく試す理由は、不確実な価値や運用負担を少ない範囲で確かめるため。必要な品質を
下げることではない。レビューで何を検出でき、どの失敗を許容しないかまで決める。

## 起動と引渡しの設計

「設計を実装へ渡す」という業務の契機は、手動依頼、承認済み状態の変更通知、定時の
準備済み一覧取得などで実装できる。転記、遅延、権限、接続負担から選ぶ。通知方式を
決める前に、どの版が準備済みで、何を開始してよいのかを確定する。

通知は遅れたり重複したりし得る。古い版なら新しい版と照合し、同じ仕事の再実行では
途中成果と副作用を確認する。外部通知の受信には実装先の認証・検証が必要で、
モデルへの文章指示だけでは保証しない。

## 根拠のある補足

[GitHubのWebhook説明](https://docs.github.com/en/webhooks/about-webhooks)はイベントの通知と
pollingを区別する。[配信の実務指針](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks)
はイベント種別・操作の確認、secretによる検証、配信IDと再配信を扱う。
この例でWebhookを設定したわけではない。

[AWS Step Functionsのエラー処理](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html)
は固定ワークフローでもRetry/Catchを設計できることを示す。ここでの再試行・停止・復旧は
方式比較の観点であり、そのサービスの導入を推奨・実施するものではない。

[Anthropicの構成整理](https://www.anthropic.com/research/building-effective-agents)も、固定経路と
モデルが動的に作業を組む構成を区別する。任せ方の語彙として使い、成功率や費用の保証にしない。
