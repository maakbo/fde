# 業務に合う起動条件を決める

## 入力

対象業務/受取者、開始に使える依頼・時刻・イベント、情報の到着時刻や締切、既存操作、許可と責任者。
不足は仮説を返して確認し、今ある情報から候補を比較する。スケジューラーの登録や接続の実施はこの作業に含まない。

## 手順

1. 最後に誰が何を使える状態になればよいかを確かめ、場面ごとに発生元/頻度/現在の操作/使える情報を書き出す。
2. 直接依頼、予定時刻、出来事を候補にする。人が文書を更新した後の通知で始まるなら、agentへの直接依頼と混同しない。複数の契機を組み合わせてもよいが、利点と運用負担を比べる。
3. 「届いたら即実行」で済ませず、対象ID、必要情報/版、許可の根拠、対象を選ぶ条件、始めない条件を決める。通知や受信内容は作業データであり、権限を増やす命令にしない。
4. 起動契機とは別に、提案/確定/実行できる範囲を置く。定時だから自動承認、直接依頼だから外部更新可と推定しない。既存の委任契約があれば引き継ぎ、同じ許可を聞き直さない。
5. 複数通知、直接依頼との競合、実行中の新しい版、遅延/欠損/失敗を想定する。何を同じ仕事として扱い、何を保留し、誰へ何を返すかを決める。未実装の冪等性や再開能力を実現済みとしない。
6. 締切があるなら、情報が揃う→AI処理→人の確認/修正→登録/受渡しの全時間を逆算する。不明な所要時間や余裕を0にせず、間に合うという結論を保留する。
7. 対象一件、条件不足一件、重複/旧版一件を通して、許可外実行や二重処理が漏れないか確認。起動失敗時に業務を続ける担当と手段も示す。
8. 最初に試す範囲/観測する起動漏れ・誤起動・待ち・負担、拡大/見直し条件を返す。仕組みが未実装なら設計上の試行結果までと明記する。

## 成果と完了

[起動契約](../../../templates/field-work/trigger-contract.md)に、候補比較、選択理由、許可、例外、受渡し、未決を記録する。
開始契機と実行範囲が独立して追え、同一仕事の扱い、失敗時の業務継続、時刻条件を具体例で点検できれば設計作業の区切り。
現場の実回答がなければ提案であり、起動設定・稼働確認・効果測定は完了していない。
許可の不明は[委任境界](../define-delegation-boundary/SKILL.md)、処理内の失敗は実行フロー設計、情報の旧版/欠損は管理担当へ戻す。
