# プロンプト設計

## 入力

一つの対象作業/期待成果、要件と確認条件ID、許可された根拠/版、受取者と出力契約、既存指示/例/観測があればその版。未決があっても影響しない下書きは進める。現場の合意、実モデル性能、実行権限を補作しない。

## 手順

1. 受取者が何を判断するかから、今回AIへ任せる範囲と必須条件を置く。人/定型処理で扱う部分、AIを使う候補理由を既存の比較から参照し、AIが必要か不明なら候補の机上試行に留める。入力選別はdesign-task-input、機械受渡しはdefine-data-handoffの既存記録を使う。
2. 役割、目的、対象、根拠/版、作業指示、禁止/未決時の返却、受取側の形式を区別した短い指示案を作る。資料/ユーザー記入/例の内容と上位指示を明確に区切る。区切りや禁止文はアクセス制御・ツール権限の強制ではない。
3. 単純な指示で足りるかをまず確かめ、誤りの観測や必要な粒度から例/判断規則を足す。例は入力と期待出力を対にし、必要な通常/不足/矛盾/拒否/境界を選ぶ。全分類や一定件数を常に要求しない。例と評価用の別入力は分け、例自体も根拠へ照合する。異なる資料や項目の値を誤って矛盾の正解例にせず、正本に反する例で仕様を変更しない。
4. 事例からルールを抽出するなら条件→判断→根拠→例外という候補にし、経験者の実際の思考/正式規程と呼ばない。write-conditional-knowledgeへ確認状態を戻す。確認者不在は未確認の候補のまま。新しい指示は重み学習や永続的技能獲得ではない。
5. 条件照合が必要なら作業を分け、根拠位置・条件ID・簡潔な結論理由・不足を成果に求める。内部思考の全文を要求しない。段階的な説明、Few-shot、長い指示を万能な品質向上策とせず、利用モデル/環境の現行指針と比較で選ぶ。
6. 指示/例/入力/出力契約の版と使った環境を記録し、同じ条件と例にない条件へ適用する。形式、根拠/意味、範囲/操作許可を別に確認する。欠落や空のmetadataも根拠として返せるか、本文引用だけを必須にして表現不能にしていないかを確かめる。モデル自身の確信度や合格フラグを独立検証にしない。未実行/欠測、提供された誤答、実AIの文書適用、実製品モデル評価を分け、時間/費用/品質の改善は測っていなければ未測定にする。
7. 不一致の原因に応じ指示/例/契約/原資料/要件へ戻し、変えた箇所と保持した条件、再試行の結果を残す。再生成は必要な時だけ回数/費用/終了条件を定め、許可外の出力を実行しない。完成は採用候補と根拠/限界、次の確認先まで。運用開始や本番接続の承認へ格上げしない。

## 成果と完了

[渡す情報と出力の根拠](../../../templates/field-work/context-and-evidence-record.md)の指示案/例/候補比較を必要な範囲で使い、出力契約は既存IDへリンクする。この作業だけなら目的/対象/根拠版/許可、指示本文/例または不要理由、条件ID/結果/実施区分/未決/次の受渡しが必須。全情報棚卸や全体の品質診断は要求しない。

別担当が要件→指示/例→出力→確認結果を追えること。技法/形式/制御の使い分けは[指示・出力・制御](../architecture-modeling/references/prompt-and-output-contract.md)。出力の不一致はverify-output-evidence、入力の原因比較はdiagnose-context-quality、実装へはprepare-implementation-handoffへ必要な範囲を渡す。
