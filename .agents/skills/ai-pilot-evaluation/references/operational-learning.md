# 検証から限定運用へ渡し、変化に合わせて学び直す

試作、PoC、運用は成果物の大きさではなく、何をどの条件で確かめたかで区別する。
prototypeは問いを試すための試作、PoCは不確実な実現性を判断する検証、MVPは最小でも受取者に
利用価値のある範囲。sandboxは隔離した検証環境、pilotは許可環境・限定した実利用者の
仕事で確かめる運用試行。架空仕様のローカル実行をpilot実績とは呼ばない。

## 合否と修正を一周させる

1. Definitionの条件、評価ケース、正本・実行物と版、評価者、許可範囲を引き継ぐ。
   典型例だけでなく境界・少数だが重大な失敗・情報不足を、目的に合う構成で選ぶ。
   異なる条件を残し、例や指示を調整したケースだけで一般化を判定しない。
2. 実際に実行した証拠と期待を比較する。品質、使う人の受渡し、業務効果を分ける。
   人の確認を処理へ挟むHITLと、結果から方法を更新するfeedback loopは別の役割。
3. 構造不正、根拠不適格、検索不良、解釈・判断、実装、受取側の不適合へ原因を分ける。
   形式は出力契約、根拠はKnowledge、仕様はDefinition、方式はDesign、体制は
   Team Adoptionへ戻す。症状だけでモデルや指示を繰り返し変えない。
4. Goは確認した範囲の次の試行へ進む判断。No-Goは今の案で進めない判断。
   Pivotは対象・方法の変更案へ戻す判断。権限がない場合の証拠待ちも区別する。
   指標の一部が良くても、許容しない失敗や未成立の権限は通過させない。
5. 修正、根拠、影響する条件、同条件と別条件の結果を記録する。合格させるためだけに
   閾値や期待を変更しない。業務上妥当な要件変更なら決定者・理由・影響とともに
   Definitionを更新し、新条件で評価し直す。

## 限定運用を判断できる引継ぎ

既存Issueや運用記録に必要部分を残す。全項目の新規文書を先に要求しない。

| 決めること | 受取側が確かめること |
| --- | --- |
| 対象と開始 | 利用者・仕事・環境・対象版・開始判断者、今回試す仮説と対象外 |
| 実際の接続 | IDと取得・操作権限、送信/保存/削除、負荷、例外、監視と費用 |
| 人の受渡し | 実行・確認・停止・再開の担当、相談先、時間、教育と代替担当 |
| 判定と観測 | 条件別品質、対象機会と利用理由、総負担・待ち・下流成果、baselineと観測窓 |
| 止め方 | 発動条件、止める操作、保留中の仕事、手動代替、対象への連絡、状態復旧と再開確認 |
| 更新 | 指示・モデル・正本・索引・手順の変更担当、版、影響範囲、再試行と戻す版 |

停止はアプリを落とすだけではない。処理途中の仕事と、誤った成果を渡された受取者を
どう扱うかも定める。接続や状態を伴う復旧は実環境で試すまで未検証。
品質の劣化、使われない理由、負担の移動、権限変更を観測し、短期の品質と
遅れて出る下流成果を別の期間で確認する。未観測の長期効果を短期結果で埋めない。

## 同じ仕事を広げる時と、別の仕事へ広げる時

- Rollout: 同じ機能・手順を別の利用者やチームへ広げる。受取側の権限、能力、
  負担、支援時間、データ差、既存ルールを確かめ、限定して再試行する。
- Scaling: 別業務・新機能・処理量や性能の拡張。目的、入力、許可、合格条件、
  接続や状態が変わるかを調べ、該当するDiscovery/Definition/Designへ戻す。

人数や期間だけで進む順番を固定しない。合格した一件を横展開の証明にせず、
各段の対象、根拠、未確認、開始・停止・再判断を残す。

## 現場の経験を、次の人が使える知識へ

SECIの共同化・表出化・連結化・内面化は、人とAIの仕事でも学びを見直す観点になる。
自動でモデルが学習する仕組みとは異なる。

1. 一件を一緒にたどり、担当者が何を見て判断・修正したか聞く。
2. 状況、根拠、条件、例外、判断理由を言葉にし、本人へ返して訂正してもらう。
3. 採択する管理者が正本・Skill・指示・例・評価ケースのどこを直すか決める。
   既存との矛盾・権限・索引や複製への影響をKnowledgeで確認し、版を更新する。
4. 次の人が別条件で適用し、誤りを見抜いて返せるか試す。説明を読んだだけで
   習熟とせず、実施していない人の能力や同意を代作しない。

効果がない、許可がなくなる、維持負担が上回る場合は縮小・停止や別手段も選ぶ。
学習ループの成果は文書数ではなく、次の仕事に必要な判断と確認が改善したかで見る。


## 次に減らす不確実性を選ぶ

品質、仕事への適合、実際の効果は違う問い。現在の条件と観測を照合し、どの不足を次に確かめると判断が変わるかを一つ選ぶ。技術が未確認なら必要な入出力を小さく試し、確認負担が問題なら実際の受取者が原資料と結果を行き来する場面まで試す。どの試行でもUIを削る、または常にモデルを作り直すとはしない。終了/代替も選択肢とし、投入済みの工数だけで続けない。

条件は観測前に置く。対象を広げたら元の得点を新しい範囲の実績へ流用せず、追加の条件/例を定義して試す。事後の閾値変更で以前の失敗を合格にしない。条件の正当な変更は理由/決定者/版を残して再評価する。Goは確かめた次の作業の範囲に限り、運用開始や支出とは別の判断。

通常の開発にも課題/仕様の不確実性はあり、方法論の名前だけで何が分かっているかを決めない。[Scrum Guide](https://scrumguides.org/scrum-guide.html)は複雑な問題への経験主義と検査・適応を示し、[d.school](https://dschool.stanford.edu/tools/design-thinking-bootleg)にもTestのmodeがある。[Lean Startup](https://theleanstartup.com/principles)は学習とBuild-Measure-Learnを重視する。これらを案件固有の判定条件や権限の代わりにせず、必要な実践として組み合わせる（2026-11-01確認）。


## 最小の試作で省かないもの

見た目や対象数を絞っても、少数の重大な誤り/権限外/確認不能時の停止を後回しにしない。sandboxという環境名は接続・データ・権限の隔離を証明しない。実データか架空かだけで開発/本番の段階を断定せず、誰のどんな仕事へ、何を許可して影響させたかを確かめる。

専門家の訂正は検証可能な候補で、不一致なら判定規則と根拠へ戻す。類似語を同一視したり、評価軸を加える変更は単なる表現修正とは限らず、対象の条件を確かめる。同じ評価例へ繰り返し合わせた改善は、残しておいた別入力や運用条件で再確認する。

技術合格でも次に必要な人の確認や接続許可がないなら、進む範囲を準備へ限定できる。No-Goでも使える知識を残し、Pivotなら新しい対象/方式/費用の条件で評価し直す。合格するまでの反復や段階移行を自動化しない。

2026-11-04に[NIST AI RMF CoreのMEASURE 1.3/2.1/2.5](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)で、独立した評価、試験集合/測定/道具の記録、検証条件を超える一般化の限界を確認。特定の件数や合格率、個別試作の安全性をこの資料から認定しない。
