# 選んだ業務の成果を子目標と作業へ分け、順序・条件・受渡しを具体化する

## 開始入力

親業務と成果、入口/受取者、現行または変更案の根拠、判断と例外。
今ある事実から仮説/下書きを返し、不足を優先して確認する。実際の権限・合意・観測を代作しない。

## 実行

1. 親業務が何を受け何を返すかを置き、達成に必要な子目標を分ける。子は同じ広さで、親の成果へつなぐ。
2. 子作業の入力/根拠/出力/判定/担当候補/不足時の戻り先を定義する。各質問やクリックへ自動分割しない。
3. 子をどの順/条件/並行で行うかの計画を別に示す。木の上下を時間順や組織階層と混同しない。計画を元の一件の時刻/前後関係へ照合し、後段にまとめた記録作業などが前後を逆転させていないか確かめる。review後に記録を更新し直す必要は、根拠/実回答がなければ未確認として残す。
4. 一件を実行/受渡し/検証できる切れ目なら分解を止め、複数agentの必要性は別に比較する。
5. 通常/不足/差戻しを通して漏れを探す。子が親の目的や責任を変えたら上位へ戻って境界/名前を訂正する。

## 成果と完了

[作業の記録](../../../templates/field-work/work-grain-record.md)の必要な欄を使う。
親→子と実行計画が追え、各作業の成果/判定/戻り先が具体的である。
原理や手法の違いが判断に必要な時だけ[業務分析の判断](../../../guides/field-work/references/work-analysis-methods.md)を読む。
不一致や新条件は該当作業/判断者へ戻す。全様式の記入を開始条件にしない。
