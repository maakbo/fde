# 導入懸念への回答

## 入力

相手の問い/判断したいこと、対象業務と変更案、資料/版・観測/許可、既存の評価・情報経路・費用・役割記録。問い1つでも始め、5分類全部の記入を要求しない。

## 手順

1. 一作業と親の目的/受取者、現在の範囲/許可を引き継ぎ、誰が今何を判断したいかを聞く。開発支援と製品AI、下書き準備/限定試行/外部接続/支出/本番を分ける。選定や代替手段の根拠が未検討なら未決と適切な業務設計へ返し、許可済みの回答案準備は進める。
2. 相手の言葉を短く言い換え、誤りの影響、仕事での再現、情報の扱い、費用と価値、判断/責任などの論点を分ける。専門用語の質問でも、守りたい品質/不利益/判断時点を具体例で確認。単なる抵抗や、説得して解消すべき障害と扱わない。典型5分類以外の使いやすさ/現場負担等も対象から落とさない。
3. 使える根拠を実物で照合する。対象/版/期間/条件と、実測/架空記録/提案/契約未提示を分ける。未確認を未実施/不存在/不合格へ変えず、根拠のない否定も避ける。根拠にない数値、未確認の契約・権限・役割・本番品質を足さない。関連する既存記録のID/箇所を参照し、必要な不足だけ担当作業へ返す。

| 論点 | 回答に必要な確認と戻り先 | 言い切らないこと |
| --- | --- | --- |
| 誤り | 誤りの種類/重大性、同じ境界の現行比較、検出/訂正/停止/代替。design-trial-success/define-delegation-boundary | 人も間違うからよい、平均精度が高い/人が確認するから安全 |
| デモと仕事 | 入力/版/例外/実接続/確認時間/負荷等の差、何を減らす検証か。ai-pilot-evaluation | 一律の件数/期間で結論、デモ合格が本番保証、PoC成功が必須 |
| データ | 入力→検索/モデル→出力/記録/保存削除の経路、利用条件/契約/実制御/操作許可。prepare-governance-review | マスキング/学習不使用/社内処理だけで利用可。共同reviewが承認や適法の証明 |
| 費用と価値 | 同じ対象/期間の全費用と純便益、測定/仮定と感度、次の検証判断。prepare-investment-decision | 作成時間の余力が現金削減、品質だけで年間ROI確定、予算獲得のための架空便益 |
| 判断と責任 | 提案/決定/実行/確認/停止/更新の役と実権限、確認者の資料/能力/時間。define-delegation-boundary/prepare-governance-review | AIへ責任移転、ボタンを押した人が全責任、HITLで従来と同じ法的責任と断定 |

4. 相手へ渡す回答を『今言える結論→今回の根拠/仕事の例→条件・限界→次に確認すること/判断してほしい範囲』で短く作る。例えば『下書きだけを対象にできますが、根拠照合と確認者の条件は未確認です。まずこの一件で、何を見て訂正できるか確かめる案です』など、事実に合わせる。安心させる表現で重大な未達や増える確認作業を隠さない。技術名は相手の判断に必要な分だけ説明する。
5. 不確実でも検証の案は具体化する。確認する仮説/ケース・根拠/判定規則/対象外、必要な情報・資源/担当、期間/上限の根拠またはTBD、結果に応じる次の判断を置く。既存の試行・費用・相談・委任記録を参照し、ここで5分野を再設計しない。原本/担当不在なら許可内の架空例や照会案の準備を続け、未決に依存する操作だけ待つ。
6. 回答案を相手の判断に照らし、『どの点がまだ不明ですか』『この条件で何を決められますか』と確かめる。実際に対話できた時だけ理解/訂正/合意/未回答を記録する。AI代理や文書reviewを本人の理解にしない。条件/版が変わったら以前の答えのどの部分が変わるか明示し、元の根拠を保持する。
7. 次の受取者へ、回答と根拠/限界、必要な確認/担当・時点、今進める準備/待つ操作を返す。質問者の納得、資料完成、共同reviewを開始許可・法的判断・費用効果へ格上げしない。送信や実会議はこのSkillだけでは許可しない。

## 成果と完了

[体制・定着計画](../../../templates/team-adoption-brief.md)の「懸念への回答」の6列表と、相手へ渡す短い回答を使う。既存の『残る問い』欄は同じ回答IDを参照し、二重の回答台帳にしない。問い/回答の対象版、根拠、未確認/影響、次に何を確かめ誰が判断するかが追えること。回答で専門的な判断を代行しない。
背景は[難しい問いを次の判断へ変える](../team-adoption-facilitation/references/operating-and-measures.md)。使う人の懸念を条件にする聞取りはclarify-adoption-conditions、支援施策はdesign-adoption-actionsへ同じ対象で渡す。
