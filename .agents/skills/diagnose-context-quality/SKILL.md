# AI出力の原因分析

## 入力

対象業務/受取者、期待条件、実際の出力と実行時の入力、参照資料の版/許可、道具の実行結果、評価条件。
実際に渡した入力がなければ、保存資料だけで原因を断定せず、確認方法と仮説を返す。

## 手順

1. 使う人と受取者へ「どこが使えず、何が変わればよいか」を具体例で確かめる。再現用の入力・出力・根拠・実行条件を同じID/版で固定する。機微情報の新規収集や外部投入を既定にしない。
2. [出力照合](../verify-output-evidence/SKILL.md)で、誤った主張、落ちた条件、形式違反、許可や実行済みの飛躍を特定する。原因の推測と、観測した誤りを分ける。
3. 必要情報が実際の入力へ届いたか、旧版/矛盾/無関係な履歴/生成誤りが混ざっていないか、指示と根拠を区別できるか、道具が成功したかを追う。モデルの能力、道具の実装、正解条件の誤りも候補に残し、全てをコンテキストのせいにしない。
4. 原因候補ごとに支持する証拠、反証/不足、確かめる最小変更を並べる。例えば参照版の差替え、欠落情報の読込、不要履歴の除外、指示/形式の具体化、要約の再作成、作業の分割。検索のどの段階が悪いかは[evaluate-retrieval-evidence](../evaluate-retrieval-evidence/SKILL.md)へ、モデル候補は比較作業へ返す。
5. 期待と重要条件を変えず、まず一つの変更を試す。入力/モデル/道具/評価対象/実行条件の変化を記録し、一緒に変えた要素があれば効果を単独原因へ帰さない。必要情報を落とした短い入力を改善と呼ばない。
6. 同じ評価と別条件で、条件の充足、根拠、危険な誤り、確認・修正の負担、容量/費用/時間を必要な範囲で比べる。モデル呼出しがなければ入力案の比較にとどめ、実エージェントの一適用を製品/モデル全体の性能評価へ広げない。作成役と実施範囲を記録し、今回のAIによる文書生成と、評価対象モデルの別呼出し・性能比較を区別する。AI作業を人手の作成と誤記しない。
7. 改善/退行/未判定、残る仮説、戻す作業、次の検証を返す。採用する変更だけ[入力設計](../design-task-input/SKILL.md)、原資料の管理、道具/実装、Skillへ戻す。再現入力・期待・誤りを次の評価へ残し、未検証の生成メモを確定知識へ再投入しない。

## 成果と完了

[入力と根拠の記録](../../../templates/field-work/context-and-evidence-record.md)の入力表・主張表・比較確認を使う。観測した誤り→原因仮説→変更→同じ条件/別条件の結果→反映先が追え、未確定の原因と次の確認者が分かる。
業務の合格や運用開始はこの作業だけで決めず、[試行評価](../ai-pilot-evaluation/SKILL.md)へ結果と限界を渡す。
