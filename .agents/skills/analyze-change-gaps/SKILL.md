# 現行と変更案の差から、必要な情報・役割・許可・実装・検証の変更を特定する

## 開始入力

対象と版の揃った現行/変更案、目的、制約、根拠と未決。
今ある事実から仮説/下書きを返し、不足を優先して確認する。実際の権限・合意・観測を代作しない。

## 実行

1. 同じ業務/成果/範囲を比較しているか確認する。現行の不確実さはそのまま残す。
2. 追加/削除/統合/順序/担当/判断/情報/受渡しの差を変更IDへ対応させる。
3. なぜ変えるかと、必要なデータ整備/役割と許可/接続/実装/教育/運用を分け、担当/依存/未決を付ける。
4. 通常と例外で新しい受渡しが成立するか、各変更の受入例を具体化する。図に矢印を足しただけで接続済みにしない。
5. 期限内にできるものと条件が必要なものを段階化し、次の担当へ何を作り何で確かめるか返す。現場の決定は実回答があるものだけ記す。

## 成果と完了

[作業の記録](../../../templates/field-work/process-change-record.md)の必要な欄を使う。
差分IDから理由/必要変更/依存/確認先/受入例へ追え、実装/導入の未実施が分かる。
原理や手法の違いが判断に必要な時だけ[業務分析の判断](../../../guides/field-work/references/work-analysis-methods.md)を読む。
不一致や新条件は該当作業/判断者へ戻す。全様式の記入を開始条件にしない。
