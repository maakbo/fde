# 現場で必要な外部接続の情報・操作・権限・変更予定を整理し、方式比較と実装へ渡す

## 開始入力

対象業務と成果、現在の委任契約、使える情報/外部システム、現在と将来の変更についての説明。
不足があっても、明示された情報から作れる仮説/下書きを先に返し、未確認を分ける。

## 実行

1. どの作業で何を受け取り何を返す必要があるかを、相手の仕事の言葉で確認する。接続自体を目的にしない。
2. 接続先を現行/承認済み追加/構想/不明に分け、読みと更新・削除・送信を別操作にする。対象情報、範囲、版、管理者、利用許可、保管/削除の必要条件を記す。資格情報は収集しない。
3. 追加予定、モデル切替、実行環境やワークフローツールの現状/変更予定を確認し、確定と希望を区別する。分からない時は未確認として現在の範囲を設計する。
4. 手作業の受渡し、既存連携、個別API、共通プロトコル等を必要に応じて比較候補へ。機能/認証/権限/提供元/変更影響/保守/費用の根拠を求める。数だけで方式を選ばず、MCPが判断や承認の代わりになるとは説明しない。
5. 具体方式や製品の対応を採用判断へ使うなら、公式仕様の版/確認日と対象環境を確認する。未確認なら候補比較と検証課題を返し、導入済みとしない。
6. 通常の読み取り、許可外更新、古い版/欠損/接続失敗を一件ずつたどり、どの操作を止め、誰が業務を続けるかを示す。
7. 実装担当へ目的、操作ごとの範囲と許可、方式を決める材料、最初に作る/試すものと期待結果を渡す。設計案の受渡しと、接続設定/認証/稼働を区別する。

## 成果と完了

[接続要件](../../../templates/field-work/connection-requirements.md)。MCP等を比較する場合だけ[方式の前提](../../../guides/field-work/references/connection-options.md)を読む。
接続IDから業務の必要性・操作・権限・変更条件・未決が追える。未許可接続を実施せず、実装者の最初の確認/試行が分かる。
入力/前提が変われば該当行へ戻す。許可や実回答が必要な事項をagentが代作しない。
