# 処理結果を次の担当やシステムへ渡す項目・型・根拠・未解決・拒否条件を定める

成果は[共通の成果形式](../../../work/references/artifact-contract.md)と、この作業が参照する型の必須項目を保つ。既存記録への追記でも同じ項目を引き継ぐ。

## 入力

対象業務と受取者、許可された資料/実データの例、現在の手順と分かる範囲の制約。
不足を明記し、今ある根拠から返せる下書きを進める。実在の機微情報原本の収集や外部投入を既定にしない。

## 手順

1. 生成側、受取側、対象作業と許可操作を確認する。下書きの作成、内容の承認、システム登録を別にする。
2. 必要最小限の項目と必須/任意、型/単位、識別子/版、許容値の原資料、未知/未解決の表し方、契約版を決める。出典IDが何の来歴を表すか、各項目とどの根拠が対応するかも明示する。根拠がなければ候補/未決にし、業務値や許容範囲を捏造しない。
3. JSON等を使う場合、構文を読めること、型/必須/追加項目の契約に合うこと、原資料と意味が合うこと、操作が許可されることを別に確認する。空値・文字列化された数値・余分な項目・根拠のない確定を扱う。必要ならJSON Schema等を実装担当の候補へ。
4. ID/版/時点/単位や参照先が元資料と対応するかを確認する。形式が合っていても未決を承認済みに変えず、根拠が不足する判断や許可外操作を受取側で止める位置を決める。
5. 不適合の項目、理由、原資料/契約/生成のどこへ戻すかを返す。必須の版や単位が不明で契約に未知の表現がなければ、受理用データを捏造せず、別の下書きに根拠と未決を残す。実装上の再実行や重複登録が関わるならdesign-trigger-contract/prepare-connection-requirementsへ接続し、文書だけで対策実装済みにしない。
6. 通常、構文/型違反、意味の不一致、許可不足を入力に応じて照合し、訂正後に同条件と別条件を試す。契約下書き、机上照合、実バリデータ/接続の動作、現場の効果を分けて返す。

## 成果と完了

[作業の記録](../../../templates/field-work/data-handoff-contract.md)を必要な部分だけ使う。
必要項目・版・意味/根拠・不明・拒否/返却が受取側に伝わる。形式/意味/権限の検証範囲と、実装していない部分が明確。
背景は[情報と処理を分ける](../../../work/design/references/data-and-processing.md)。
