# 変数・条件分岐の設計

## 始める条件

選んだ業務、変わる条件と判断者、処理の入出力、根拠と許可、実装担当への受渡し先。
未確認があっても設計案を返し、業務上の閾値・承認者・既定値は作らない。

## 手順

1. 担当者に「同じ処理でよい例と、変える必要がある例」を聞く。処理・受取者・許可・成果が実際に変わる条件から変数を選び、関係の薄い属性では枝を増やさない。
2. [ワークフロー設計書](../../../templates/workflow-brief.md)の値の表へ、名前、意味、入力/外部取得/前処理の出所、型・単位・許容値、取得時点/版、保持範囲/権限、利用先を置く。既存のデータ契約を参照し、未指定・null・空文字・false・0を業務上区別する。既定値の指定がない必須値の未指定を、他の情報があるという理由で正常扱いしない。推定値は確定値に変えない。
3. 二つの処理を選ぶ分岐、分類ごとの担当/処理への振分け、各項目を通す/除く選別を使い分ける。選別は集合に対する処理なので、除外理由と全件除外時の業務を決める。経路の数は記法の目安であり、特定製品の実装制約にはしない。
4. 条件の表へ判定式と単位・境界、優先順、進む先/出力、判断者、不明/矛盾、再開を記す。条件が重なったら先勝ち・複数実行・確認待ちのどれかを業務上決める。未知カテゴリを既定経路へ通すのは、その処理に必要な情報と許可が成立する場合だけ。
5. 正常な対象外、必要情報なし、入力不正、許可不足、取得/保存等の失敗を別にする。止める操作、保持する成果、返す項目と理由、担当者の代替手順を示す。通知先を書いただけで通知や復旧の実装済みにせず、返却経路そのものが使えない場合も止まる場所を残す。
6. 実装前に通常の各経路、閾値の直前/一致/直後、false/0、未指定/不正型、未知、重複条件、全件除外、取得失敗から必要な確認ケースを作る。手順5で挙げた該当する例外経路には確認IDを対応付け、許可不足・保存後の失敗・返却経路の失敗も必要な範囲を確かめる。実行しない経路は理由と未検証を残す。次の担当が期待経路・残る成果・起こしてはいけない操作を先に言えるようにする。
7. 実装結果を同じ条件へ照合し、別条件でも経路と除外理由を追う。誤分岐は判定条件、情報不足は取得元、無断操作は委任/実装へ戻し、直した箇所と再試行の証拠を残す。

## 成果と完了

共通の[成果形式](../../../work/references/artifact-contract.md)を保ち、既存ワークフローの値/条件の表と「分岐の実装確認」へ記録する。実装者が判断材料と出所、選ぶ経路、除外・失敗の戻り先、境界ケースを説明できれば設計の受渡しができる。

処理の順序/保存/再開は[アクション設計](../design-action-chain/SKILL.md)、項目の意味/許可は[データ契約](../define-data-handoff/SKILL.md)を再利用する。業務での使い分けと例は[変数と条件分岐](../../../work/design/references/variables-and-branches.md)。設計上の追跡、実コードの実行、実モデルの分類、本番の接続・効果は分けて返す。
