# 業務の情報を部分ごとに見て、取得・計算・解釈・操作の担当を決める

成果は[共通の成果形式](../../../work/references/artifact-contract.md)と、この作業が参照する型の必須項目を保つ。既存記録への追記でも同じ項目を引き継ぐ。

## 入力

対象業務と受取者、許可された資料/実データの例、現在の手順と分かる範囲の制約。
不足を明記し、今ある根拠から返せる下書きを進める。実在の機微情報原本の収集や外部投入を既定にしない。

## 手順

1. 対象業務の入口から受取者が使うまでをたどり、各場面で必要な情報・所在・利用許可を挙げる。未提供は候補/未確認として分ける。
2. 実際の中身を見て、固定した項目/型、自由記述や画像、キー/タグの構造を部分ごとに記録する。同じJSONのIDと自由記述、PDFの表と本文を一分類へ潰さない。本文未提供なら仮分類とする。
3. ID照合、計算、意味解釈、生成、登録/送信を別の処理にする。正確な照合/計算は既存機能・決定的処理を候補にし、曖昧な文章の解釈は人/LLMを品質比較の候補にする。
4. APIは取得/操作の接続面であり、LLMやパーサと排他的な分類ではない。必要項目の取得→解釈→検証→許可された操作を組み、全データの投入/AI化を既定にしない。
5. 各処理に必要な版/単位/鮮度/権限、期待出力、照合先、欠損時の戻り先を付ける。文章があるだけでLLMを必須にせず、簡単な検索/規則/現行維持も比較する。
6. 通常、同じ形式に別種類の内容がある例、情報不足の一件を追い、誤った担当や境界を直す。結果を方式比較/接続要件/受渡し契約へ渡し、実接続や品質を検証済みにしない。

## 成果と完了

[作業の記録](../../../templates/field-work/data-processing-record.md)を必要な部分だけ使う。
場面→情報の部分→必要操作→担当候補/理由→確かめ方/不足時がつながる。採用確定と未比較を分け、形式の名前だけの表で終えない。
背景は[情報と処理を分ける](../../../work/design/references/data-and-processing.md)。
