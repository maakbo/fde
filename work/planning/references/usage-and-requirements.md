# 利用場面から要件へ

要件は機能の一覧から始めるより、「誰が出力をどう使って次を判断するか」から始めると必要な情報が見える。設計担当が不足を直すための一覧と、レビュー担当が依頼を受け付けるための根拠一覧は同じではない。開発担当が受け取るなら、受付済みという表示だけで実装を始めてよいと誤解しない状態表示も要る。

人物像の目的は想像上の年齢や性格を豊かにすることではなく、利用条件と判断を具体化すること。直接操作しない確認者/引継ぎ先も含め、必要な時に根拠を見られるか、訂正や拒否ができるかを確かめる。

| 分けるもの | 判断の問い | 設計レビュー受付の例 |
| --- | --- | --- |
| 機能 | 何ができる必要があるか | 資料ID/版の不足と対応する依頼箇所を示す |
| 非機能 | どの質/水準が必要か | 出力から根拠の資料と版を追える。時間の目標は現行観測後に決める |
| 制約 | 守らなければならない条件か | 受付を設計承認や実装開始許可として扱わない |
| 仮定 | 真だと考えているが確かめる必要があるか | 担当者が同じ版の資料を見られる。崩れれば該当判断を保留してアクセス/版を確認 |

合格基準は必要な業務上の振る舞いから逆算する。数値だけにせず「版が不明なら不明と根拠を示し、受付可能にしない」のような観測可能な定性条件も使う。時間ならデータ取得、処理、人の確認/訂正、返却までの起終点を決める。モデル応答時間だけでは仕事が間に合うか分からない。

合格基準、試行開始に必要な準備、継続観測する指標は用途を分けてつなぐ。合格した一回だけで将来の入力や変更を保証せず、版と対象を残して影響箇所を再確認する。専門家との一致率は比較対象との一致であり、正しさや公平性の全てではない。少数の属性差替えテストや特定項目の除外だけで偏りがないとは判断できない。棄権の削減も、根拠が足りない出力を強いる目標にはしない。

全体を一人で完全な仕様にする必要はない。担当者が具体例で訂正でき、業務責任者と実装側が未決と達成条件を同じ意味で扱える案を返す。[利用場面の定義](../../../.agents/skills/define-usage-scenarios/SKILL.md)から[業務要件定義](../../../templates/definition-brief.md)へ同じIDで残す。

利用場面の仮定、要件の関係者理解、条件の変化に伴う再確認は、[NIST AI RMF Core のMAP 1および継続的なMAPの考え方](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)とも照合できる。個別案件の適合性や合格をこの枠組みだけで認定するものではない。
