# 工程をまたぐ受渡しと変更

各工程の担当者は、成果物の作成・確認・承認と、次の担当が受け取ったことの確認を別々に行います。[開発・運用の全体](README.md)にあるすべての工程に共通する、人手での調整です。

## 成果物を渡す

作成者は文書を共有フォルダ、ソースをGitで版管理し、レビュー対象の版を指定します。確認者は指摘と処置を記録し、承認者は対象版と承認日を残します。作成者と受取者は会議やメールで次を確認します。

| 確認すること | 渡す側が示すもの | 受け取る側が行うこと |
| --- | --- | --- |
| 対象と目的 | 対象機能・工程、何に使う成果か | 自分の作業範囲と対応するか確認する |
| 版と所在 | 文書版、ソース版、配置対象、参照先 | 指定版を開けるか、旧版が混ざらないか確認する |
| 判断の根拠 | 要件と設計、テスト項目の対応、決定理由 | 自分が確認すべき条件と結果をたどる |
| 確認と承認 | レビュー・テスト結果、承認者と対象版 | 未確認と合格を区別し、必要な承認があるか確認する |
| 残件と制約 | 未決・不具合・未実施、担当・期限、利用制限 | 着手を妨げる残件を伝え、受領または保留を返す |

担当不在、閲覧不可、版の相違、必要な環境の不足はPMへ連絡し、着手を保留します。PMは担当者や代行者・日程を調整します。無回答を承認にしません。

## 指摘を戻す

| 見つかったこと | 人が判断すること | 戻る先と再確認 |
| --- | --- | --- |
| 文書の記載不足・不整合 | 作成者と確認者が、単なる記載か仕様の変更かを区別 | 作成工程で修正し、指摘元が再確認 |
| 設計と違う実装・動作 | 設計担当・開発担当が原因と影響を調べる | 実装・単体へ戻し、影響する結合・総合・受入を再実行 |
| 合意済み要求そのものの変更 | 業務責任者・顧客IT担当・PMが必要性、費用、日程、品質影響を判断 | 要件または設計へ戻し、承認後に下流の文書・コード・テストを更新 |
| 外部会計側の接続不良・日程未確定 | 両側担当が原因と実施可能日を調整 | 外部結合を保留し、両側の条件が揃ってから再実行 |
| 本番切替の失敗 | 導入責任者が計画上の停止・切戻し条件を確認 | 利用を止めて旧環境へ戻し、原因対処と再計画・開始判断 |
| 運用中の問合せ・障害 | 運用担当が影響・緊急度と手順内の対応可否を判断 | 手順で対処、必要なら保守へ。改修は承認後に開発工程へ |

変更依頼には、理由、元の版、影響する要件・設計・コード・テスト・運用手順、見積り、決定者を記録します。承認されるまでは合意済み版を維持し、着手できない部分を保留します。承認後は新しい版を配布し、受取側が差分と再確認範囲を照合します。

## 全工程に並行する管理

PMは計画・進捗・費用・課題・変更を管理します。各責任者はレビュー予定と確認時間を確保し、構成管理担当の役割を持つ人が文書・ソース・環境の版を照合します。テスト担当は上流の要件・設計から試験を準備し、運用担当は要件・基本設計時から運用性、移行、復旧を確認します。

作業時間、承認待ち、修正・再テストの時間は区別して記録できる対象ですが、この架空例には実測値を置いていません。手順と現場の実態の違い、待ちの原因、担当による判断差は、次の業務観察で確かめます。
