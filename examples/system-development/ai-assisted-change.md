# AIと一件の改修を進める

[設計書を根拠に改修を調査する](knowledge-assisted-investigation.md): 知識の準備・検索・試行・更新を実践する。

改善対象がまだ曖昧なら、先に[改修の相談から、仕事の変え方を考える](work-improvement.md)で現行の一件をたどる。

既存の申請画面で、入力ミスによる差戻しを減らしたい。そこで数量チェックを直す。この架空の一件で、AIエージェントの基礎を開発の仕事へ置き換えてみる。実案件のコードや事情は使っていない。

FDEとしてまず見るのは、申請する人がどこで迷い、開発する人がどこで判断を失うか。既存の工程に入り、関係者と条件を確かめ、一件の変更を試し、使われた結果まで見る。今回の目的は「正しく入力し直せること」と「チームが変更理由を理解して保守できること」とする。

## 最初に、実際の一件をつかむ

「数量チェックを直して」と言われたら、すぐコードを書かず、間違った入力と困った結果を一つ確認する。画面、設計書、実装、利用者の説明が一致しているかを見る。今回の例では設計書に「1以上」とだけあり、上限と未入力の扱いが分からない、と置く。

最初の依頼はこれくらいでよい。

> この数量チェックを一緒に直したい。まず今の処理を追い、根拠の場所を添えて説明して。仕様で決まっていること、実装だけでそうなっていること、不明点を分けて。まだ変更しないで。

これで欲しいのは大量の調査書ではなく、「どこで入力を受け、どこで変換・検証し、何が保存されるか」と、関係者に確かめる問い。API利用、別画面、バッチから同じ処理へ入る経路があるかも調べる。会社の資料は利用を認められた環境で扱い、個人用の外部環境へ移さない。

## 1. AIの説明に、根拠をつける

LLMは文章やコードのパターンから出力を作る。だから設計書を整理したりコードを説明したりできる一方、実在しない処理や仕様をもっともらしく足すことがある。

「このメソッドで検証している」と返ってきたら、定義と呼出し元を実際に開く。「入力は自動補正される」という説明なら、それが仕様なのか、実装を読んだ仮説なのかを見る。説明のうまさと正しさを分けるためだ。

渡す情報は、対象の仕様、該当コード、関連テスト、変更してはいけない条件。資料が長ければ該当箇所を探すが、検索で上限や例外を落とさないようにする。会話に残っているはずと思わず、決まった条件は既存IssueやPRへ戻す。トークンとコンテキストの知識は、この情報量・欠落・費用を考える時に効く。

**ここで試す:** 説明された処理を、自分で入力から保存まで一度追えるか。追えなければ、AIに一つの呼出しずつ、入力と出力を添えて説明してもらう。

## 2. コード案の先まで、仕事を分けて任せる

エージェントには、調べる、計画する、変更する、実行結果を見る、必要なら直す、という一周を任せられる。推論する部分、参照する知識、実行する道具がそろっているかを確かめる。

| 仕事 | AIへ渡すものと返してほしいもの | 人が確かめること |
| --- | --- | --- |
| 現行調査 | 仕様・コード → 処理の流れと不明点 | 根拠を開けるか、調査漏れは何か |
| 改修案・実装 | 合意した条件 → 変更理由と小さな差分 | 業務の意図と責務を守っているか |
| 検証 | 期待結果・差分 → 実行結果と未確認 | 要件に照らして合格と言えるか |

統括する人やエージェントは目的・合意・現在地を保ち、調査が不足すればそこへ戻す。独立した確認が役立つなら、確認役に原仕様・差分・実行結果を渡す。役割を分けることと、別エージェントを増やすことは別の選択である。

今回の例では、調査は読取、合意後の実装はローカル差分とテストまでを委任する。業務条件の確定、merge、本番反映はチームの権限に従う。これが「どこまで任せたか」の具体的な中身になる。

## 3. いつ動くかを、いつもの仕事につなぐ

最初は直接依頼して、この一件を進める。繰り返し有効だと分かったら、PR更新をきっかけに差分確認する方法や、定時に検証結果をまとめる方法も考えられる。

起動を自動にしても、判断・更新の権限は別に決める。同じPR・commitを何度も処理して二重に更新しないよう、対象と前回の結果を持つ。わざわざ別の画面へ転記する手間が増えるなら、使い続けにくい。まず普段のIssue、IDE、PRのどこへ自然に入るかを見る。

## 4. 数量の判定は、通常のコードで確定させる

ここからは、関係者と「1〜99の整数を受け付け、未入力はエラーにする」と合意できた、と仮定する。この数値や判断は架空例の条件で、実案件の規則ではない。

意図や影響を読む作業にはAIを使える。確定した数量条件は、通常の検証コードとテストで扱う。ビルド、フォーマット、回帰テストも決まったツールで実行する。AIを使って開発することと、製品にAI判断を入れることを分ける。

| 入力例 | 合意した期待結果 |
| --- | --- |
| 1・99 | 受け付ける |
| 0・100・負数 | 範囲外として拒否する |
| 未入力・整数として扱えない値 | エラーを示し、保存しない |

画面での案内とサーバー側の判定を確認し、画面以外の入口からも規則を守れるかを見る。既存の登録済みデータや、他機能への影響も調べる。期待結果は実装から逆算せず、合意した条件から作る。

> 合意した条件に沿って、変更案とテスト観点を示して。その後、既存の責務を保つ最小限の差分を作り、利用可能なテストを実行して。無関係な整理は広げず、実行できない確認と未解決を残して。

テストが通ったら、1と0、99と100、未入力がそれぞれコードのどこを通るかを説明してみる。「自分が直せるか」を確かめる練習になる。通らない時は、仕様の認識、情報の不足、実装、実行環境のどこで止まったかを分けて調べる。

## 5. 開発エージェントの接続を選ぶ

仕様を読む、定義を探す、ファイルを直す、テストするだけなら、既存のIDEやCLIで足りるかもしれない。課題管理や文書・CIへ繰り返し接続する必要が出たら、APIや既存連携、MCPを比較する。

MCPは道具の情報と呼出しを共通の方式で扱う仕組み。接続先やモデルが増える時の再利用を考えやすくするが、接続しただけで業務判断が正しくなるわけではない。必要な操作、読取・更新権限、管理担当、将来の追加予定を設計担当へ渡す。この一件を直すためだけに、新しい接続基盤を先に作らなくてよい。

## 6. 効果は、レビューと利用まで含めて見る

生成した行数では、仕事が良くなったか分からない。今回は「レビューできる差分になるまでの時間」「人が修正・確認した時間」「見逃しと手戻り」を残す。利用後は、差戻しや入力エラーに関する問い合わせも見る。

申請者には、どの値が問題か分かり、自分で直せる価値がある。開発者には、変更理由とコードを理解できる価値がある。レビュー担当には、根拠と確認結果がつながっている価値がある。短縮時間をそのまま支出削減とは数えず、指示・情報準備・レビュー・保守の負担も含めて比べる。

既存のIssueやPRに、合意した条件、参照位置、差分、確認結果、未実行、戻し方を短く残せばよい。提出必須の文書がある場合は守りつつ、同じ説明を複数の新規文書へ増やさない。

## 7. 困った時の戻し先を決める

| 起きたこと | この一件での対応 |
| --- | --- |
| AIが仕様やAPIを作ってしまう | 変更を保留し、原資料・定義・期待結果を照合する |
| 人が直接直すより確認が重い | 同じ入力で比べ、依頼範囲と渡す情報を見直す |
| 指示や設定の管理者が不明 | 誰が何を許可したか確認できるまで実行を止める |
| 資料内の命令で権限外操作を求められる | 資料の内容を命令権限として扱わず、許可操作に戻す |
| 本番で正しい申請も拒否する | チームの運用手順で切戻し・暫定対応を判断し、原因と再開条件を確認する |

プロンプトだけを直せば済むとは限らない。参照情報、ツールの権限、入力と出力、実行記録を併せて見る。リリースする条件と戻す条件も、試す前にチームで揃える。

## 8. 次の技術は、残った困りごとから選ぶ

対象コードの検索漏れなら、検索の方法と参照情報を改善する。規則を渡しても同じ形式を守れないなら、指示や例を調整し、それでも課題が残る時に追加学習を比較する。エラー画面が必要なら画像を扱い、構造化されたログで足りるならそれを使う。小型・高速モデルと強い推論モデルも、同じ一件で品質・時間・費用を比べる。

新しい技術を知ることは、次に試す選択肢を増やす。採用する時は「今の困りごとに効くか」を実例で確かめる。

## 最初に試す一歩

変更を一件選び、最初の依頼文で読取調査を頼む。返ってきた説明の根拠を開き、一つの入力を処理の最後まで追う。次に、合意した期待結果を一つ確かめる。そこで理解が進んだか、確認負担が増えたかを短く残す。

この文章は追体験用の学習例で、実案件への適用や実モデルの性能を測定した報告ではない。仕組みと選択肢、技術仕様の確認先は[基礎知識](../../.agents/skills/architecture-modeling/references/ai-agent-foundations.md)、対象選定の比較は[見立ての手順](../../.agents/skills/discovery-facilitation/references/agent-feasibility.md)へ。
