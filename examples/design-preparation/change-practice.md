# 設計業務への定着支援

受注一覧に日付検索を追加する、架空の開発チームからの相談です。AIで基本設計の下書きを作る案がありますが、設計担当は「仕様にない翌日扱いが入っていた」と話しています。同じ担当は、要件整理の支援なら試したい一方、誤りを指摘すると責められそうだとも感じています。

レビュー担当は入力研修を受けています。しかし困っているのは、仕様の正本が見つからず、レビュー時間もないことでした。管理者からは「初期の遅さは適応の谷だから続けよう」「成功例1件と満足度で全展開したい」という案も出ています。

FDEは、それぞれの言葉を原因の仮説と分け、必要な支援と業務に組み込む場面を設計しました。以下は架空資料へのAIによる文書適用で、実社員の合意、心理状態、習熟や現場効果を測った結果ではありません。

[相談と条件](change-intake.md) / [定着施策の設計](../../.agents/skills/design-adoption-actions/SKILL.md) / [導入・運用改善](../../work/operations/README.md)

## 困り事に合う支援を選ぶ

| 困り事 | 支援案と、まだ確認が必要なこと |
| --- | --- |
| 日付の条件を誤った下書き | 元の下書きと要件・仕様の版を照合する。技術や資料の問題を、否定的な態度とは決めつけない |
| 正本が見つからず、確認時間がない | 正本の所在・アクセス・確認枠・代替担当を確かめる。入力研修を増やすだけでは解消しない |
| 指摘すると責められそう | 具体例と困った条件を受け、人格ではなく根拠と仕組みを確認する経路を提案する。発言だけで心理的安全性は断定しない |
| 初期の負担増 | 学習、確認、訂正、待ちを分けて観測する。品質や週60分の総支援枠を免除せず、回復する時期も約束しない |

[定着施策案](change-record.md)には、選んだ支援、必要な担当・時間、観測、止める条件を残しました。まず設計の下書き準備という一作業を扱います。作業を減らす・まとめる・簡素化する検討と、人や既存手段との比較記録はないため、その判断は業務設計へ返しています。許可された施策案の準備は進められます。

小さく試す案は定型だけでなく、日付境界の確認も含めました。簡単な例の速さや満足度を、重大な条件の合格や全チーム展開へ置き換えません。

## 要件を受け取った後の仕事へ組み込む

使いどころは「SEから承認済みの変更要件が届き、必要な仕様の版と確認条件がそろったら、設計担当が下書きを依頼する」という計画です。

返す成果は根拠と未決を含む案。レビュー担当が照合し、設計担当が訂正してから開発担当へ渡します。保存先、実担当、レビュー時間と開始判断は未確認です。これは人が使う場面の設計で、自動起動の設定ではありません。

要件が来なければ依頼する機会はありません。仕様が遅い時は版と所在の確認、確認者が不在なら代替と期限の判断へ返します。従来の方法へ戻す場合も、必要な仕様と人の確認は省けません。

## 相談を、修正と次の確認へ戻す

木曜午後の既存レビュー会や、文書・オンラインの短い相談を接点の候補にしました。複数拠点やリモートで働く役がいるため、全員の対面研修は前提にしていません。準備と練習を合わせた週60分の枠は、実担当と配分の確認が必要です。

失敗メモには、起きた条件、仕様の版、誤り、困った点を残す案です。共有の保護と扱いを確認し、原資料・依頼・照合手順・Skill・支援のどこを直すか決め、再試行へつなぎます。場を設けただけで、本人が安心して報告できるようになったとはしていません。

## 条件が変わった時の判断

別条件Cでは、金曜夕方に要件だけが届き、仕様の版も確認者も不足しました。受領と照会の準備はできますが、仕様依存の下書きやレビュー完了には進みません。管理者の録音・外部送信・自動保存の追加要望も、今回の許可とは別です。

別条件Dでは、架空の練習記録に定型ケースの速さと満足の声がある一方、日付境界の誤りが未訂正でした。既存の品質条件を保持し、未確認の設計を渡さず、原因照合と訂正・再試行の判断へ返しています。成功紹介で未達を隠したり、学習が進んだことを品質の代わりにしたりしません。

[別条件への適用結果](change-forward.md)に、進める準備、待つ操作、必要な判断を残しました。今回作ったのは施策と受渡しの計画です。担当・資料・時間・評価方法を整えた後、本人が一件を行う練習と、品質・全負担・実際の使われ方を確かめる段階へ進みます。
