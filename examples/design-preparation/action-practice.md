# 準備済みの要件から、レビューできる下書きを届ける

注文日範囲検索の要件がそろったら、基本設計の下書きを作ってレビュー担当へ渡したい。
毎回IDを転記し、生成されたファイルを探してから依頼する手間を減らす相談です。
今回は、確定要件の読取から下書き保存と受渡し記録までを、小さく動かしました。
架空の開発チーム・要件による演習です。製品の検索機能へAIを組み込む話ではありません。

[設計業務の全体](README.md)／[今回の入力](action-intake.md)／[任せ方を選んだ例](automation-practice.md)

## 「何が起きたら始めるか」と「どう届くか」を分ける

自然な契機は、SEが対象要件を準備済みにしたことです。最初の試行では、設計担当が
そのIDと版を指定して手動で開始する案を選びました。
毎朝9時の起動は時刻帯・休日・対象期間が未決。状態変更通知は将来の候補ですが、配信方式は未決です。
どちらも、今すぐ設定したことにはしていません。

状態変更という出来事と、Webhookなどで通知が届く仕組みは別の設計です。
イベントだから必ず即時、一回だけ届くとは置きません。直接依頼と別の通知で配信IDが違っても、
同じ要件ID・版の仕事なら、既に作った成果を確かめて返す必要があります。
起動を受け付けたことを、下書き完成や人の承認とは扱いません。

## 下書きが開けてから、レビュー可能と記録する

独立実行役に[処理をつなぐSkill](../../.agents/skills/design-action-chain/SKILL.md)と
[起動条件のSkill](../../.agents/skills/design-trigger-contract/SKILL.md)、生の入力を渡しました。
戻ってきた設計は、処理名を並べるだけでなく、何を次へ渡すかを揃えています。

| 処理 | 次へ渡す成果 | 確かめること・失敗時 |
| --- | --- | --- |
| 起動を受け付ける | 対象ID・要件版・許可された操作 | 準備済みと現行版を確認。旧版/許可外なら進めない |
| 必要項目を検査する | 元の根拠IDと本文、未決事項 | R03の権限条件などが欠けたら、生成せずSEへ返す |
| 下書きを作る | 対象・条件・例外・権限・未決を含む候補 | 型と原要件の対応を確認。R04の日付解釈は確定しない |
| 保存し、読み戻す | 保存済みの下書きと版・内容ハッシュ | ファイルが存在し、期待する内容を読めるか。失敗時は準備完了にしない |
| 受渡し記録を作る | ローカルoutboxのreview_ready | 保存先と対象版を指す記録。人への実送信・レビュー・承認とは区別 |

「着手しました」という進捗通知は、下書き完成の通知と意味が違います。
今回のreview_readyは、保存した下書きを開ける状態に限りました。
ローカルでの読み戻しは、実際のレビュー担当がその保存先へアクセスできる証明ではありません。
その確認は実環境で別途必要です。

## 保存失敗と、受渡し記録の失敗を分けて動かす

独立実行役が作った[標準Pythonの小さな実行例](action-lab/run_trial.py)を使います。
本文は固定の架空要件をテンプレートへ転記します。LLMによる生成品質を測ったものではありません。
保存・読み戻し・内容ハッシュ・ローカルoutboxは実ファイルで実行しています。
通知サービス、Webhook受信器、スケジューラーはありません。

| 条件 | 実行で確認した結果 |
| --- | --- |
| N：準備済みの現行版 | 下書きを保存・読戻し、outboxに一件。人の確認待ちの状態 |
| D：同じ仕事へ別の配信IDで再依頼 | 既存成果を返し、outboxは一件のまま |
| M：権限条件R03が欠損 | input_waiting。下書きを作って仕様を補わない |
| S：保存直前に失敗を注入 | save_failed。レビュー可能の記録は作らない |
| F：保存後、outbox書込直前に失敗 | 下書きは保持。再開時にハッシュを照合し、outboxだけ記録する |
| O：v0の依頼だが現行はv1 | stale。旧版で下書きを作らない |
| X：確定版へ反映し外部送信する依頼 | denied。演習の許可範囲へ戻す |

Fでは、再開前後で下書きの内容と更新時刻が変わらないことも別に照合しました。
一件の保存失敗で業務全体を止めず、止める後続と返却先を決めるための試行です。
ただし障害注入は書込直前の固定位置です。書込途中の破損、保存後の記録喪失、並列実行、
実送信の二重処理まで保証してはいません。単純な記録ファイルだけで一度限りの実行を実現したとは呼びません。

## 新しい場所から実行し直す

公開前に、最初の実行例が試行フォルダの事前作成に依存している点が見つかりました。
公開版では出力先を初期化し、指定がなければ一時ディレクトリを作る形へ修正しました。
既存の出力先へ黙って上書き・混在させません。Skillにも保存先の準備と利用権限を戻しています。

```bash
python3 examples/design-preparation/action-lab/run_trial.py
```

出力JSONのdraft_pathから、実際に保存した下書きを開けます。同じフォルダにoutbox.jsonと
観測結果observations.jsonが残ります。保存先を選ぶ場合は`--output`へ新規のディレクトリを指定します。
公開版は、準備済みの試行フォルダを使わずに再実行して、上の条件を確認しています。

## 別の版と、別の仕事へ渡す時

v2の要件は、v1とは別に検査します。v1の完了やレビューをそのままv2の確定根拠にしません。
v2の本文は未提示なので、今回その実行結果はありません。

別workflowが週次の設計準備状況を集計するなら、対象ID・要件版・成果ID・保存/確認待ちの状態を渡します。
review_readyはレビュー完了数へ入れず、人が返した結果と対象版が確認できる時だけ完了として数える案です。
今回は人の結果記録も週次集計も未実装で、実際の完了数は出していません。

実施済みなのは、独立agentの起動/処理設計、固定本文のローカル下書き作成と保存・受渡し記録、
失敗/再開/重複等の実行と公開前の修正・再試行です。
実チケット接続、送信、専用モデル評価、人のレビュー、現場効果は未実施です。
次は実装担当へ正本の取得先、成果の置場と権限、レビュー結果、排他・永続化の未決を渡します。
