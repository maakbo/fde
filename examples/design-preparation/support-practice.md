# 開発チームのAI導入体制

二つの開発チームが、受注管理システムの開発にAIを使おうとしています。Aチームは日付検索の設計下書きを自分たちで作りたい。BチームはCSV出力のテスト案を作りたいものの、何の資料を渡し、どこを確認すればよいか分かりません。

共通の支援候補はプラットフォーム担当です。ところが相談は週5件・各30分という見積りに対し、支援枠は全体で週60分。以前は全下書きを共通担当の確認待ちにして、現場のレビューへ渡す前に滞留した経験があります。

FDEは、どの機能を共通で支え、各チームが何を自分で進められるかを整理しました。以下は架空の状況とルールへのAIによる適用です。実際の組織の任命・支援受付・能力・合意を確認した記録ではありません。

[相談とルール](support-intake.md) / [推進体制の設計](../../.agents/skills/design-adoption-support/SKILL.md) / [導入・運用改善](../../work/operations/README.md)

## 三つの案を、仕事と支援量から比較する

| 体制案 | この条件での判断 |
| --- | --- |
| 共通担当が全案を作り確認する | 業務知識と支援量が必要。前回の確認待ちに戻るおそれがあり、現在の枠で全件を扱える根拠がない |
| 各チームだけで完結する | Aの裁量は保てるが、Bが資料や確認方法で困る状態を解消できない |
| 共通条件と限定相談を支え、案は各チームで作る | 今回の暫定案。Aは必要な相談だけ、Bには最初の入力・確認を支える案を置く。実際の受付・配分は確認が必要 |

[体制と支援の記録](support-record.md)には、比較、責任分担、相談時の入力、返す成果、受取者、不在や枠不足の戻り先を残しました。見積りを掛けた150分と枠60分の差は90分ですが、実測した不足時間ではありません。人数や組織名から、全件対応や応答期限を約束しません。

今回のルールでは、架空仕様から未承認の案を作る準備は各チームで進められます。例外や新ツールを決める権限は未確認です。支援候補というだけで、プラットフォーム担当へ決定権を与えていません。

## 現場へ、次に使える入力を渡す

Bには[テスト案づくりの入力案](support-request.md)を作りました。目的、テスト案を作るきっかけ・頻度・工数、受け取る仕様、根拠と期待を照合する判断、作る成果、レビュー受取者を整理します。CSVの項目・形式・出力条件は、別の製品仕様として確認します。

Bの作業の仕様・工数・頻度は未確認のまま残し、製品のCSV仕様なしに具体的なテスト期待を作ってはいません。

## 支援枠がなくなった時も、受渡しを決める

別条件では今週の共通枠が0分になりました。各チームの許可内の資料整理・未承認案の準備は続け、共通相談は保留し、代替・優先度・資源の判断へ返しています。支援候補の不在を、全作業の停止や新しい自動承認へ変えていません。

新ツールの希望は、現場の案づくりとは別に、例外を決める人と追加許可の確認へ返しました。保護対象のない架空の失敗メモには、適用条件と未測定を添える案を作っています。共通候補の「成功例だけ共有」という発言を、既存ルールの変更とは扱いません。

[別条件の結果](support-forward.md)に、続ける準備、待つ操作、次の受取者と未決を記録しています。実際の共有やツール導入は行っていません。

## 次の判断

管理者と候補担当が受付範囲・配分・能力・代替を確認し、組織側が共通ルールの例外と開始を決める人を特定します。Bは許可された架空仕様の版とレビュー受取者を揃え、根拠付きのテスト観点を作る練習へ進めます。

今回の成果は体制案と支援の引継ぎです。実際の支援が使えるか、待ちや重複が減るか、Bが自分で確認・訂正できるかは、現場で別途観測する必要があります。
