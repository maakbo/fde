# 開発の改善対象を選ぶ

架空の開発チームが、受注管理システムの機能追加で、品質を保って設計を開発へ渡すまでの遅れと負担を減らしたいと相談しています。管理者は「基本設計をAIに作らせたい」と考えていますが、SEは資料の版不足やレビュー枠の待ちも気にしています。

FDEは、作成時間だけで対象を決めず、設計作成・根拠対応・レビュー受付を比較しました。以下は架空の記録へのAIの文書適用です。現場の実測・同意・効果を確認した記録ではありません。

[相談と記録](discovery-intake.md) / [改善対象の選定](../../.agents/skills/select-improvement-target/SKILL.md) / [課題発見・対象選定](../../work/discovery/README.md)

## 作成の人手と、仕事が進むまでの待ちを分ける

提供記録3件では、設計の人手は60〜120分、レビュー待ちは2〜4営業日でした。1件には資料の版不足でレビュー依頼が戻ったとの記述もあります。

ただし、待ちの開始・終了や差戻しを含むか、レビュー枠の空きや他案件の状況は分かりません。長い待ちが見えても、その原因や短縮できる幅はまだ仮説です。3件の設計人手の合計270分・平均90分は、その作成工程の算術であり、経過時間や改善効果ではありません。

## AI以外の変え方も比較する

| 候補 | 今の根拠から考えたこと |
| --- | --- |
| 基本設計のAI下書き | 文章の読解は候補になるが、期待する作成短縮がレビュー・訂正・待ちを含む改善になるかは未確認 |
| レビュー依頼の受付整備 | 資料ID・版・未決・枠を揃え、重複チェックをまとめる案。既存テンプレートや通常のルールも比較できるが、待ち原因の確認が必要 |
| 根拠対応のAI補助 | 文脈対応は候補になるが、正本と確認者、見落としの影響、確認負荷を確かめる必要がある |

[比較と選定の記録](discovery-selection.md)では、効果と実現可能性に根拠が足りない箇所をTBDにしています。根拠を詳しく説明できることと、効果が大きいことは別です。リスクや許可の条件も、合計点に埋めていません。

最初に選んだのは、受付を変える実施ではなく、**レビュー依頼一件の資料・提出・戻り・受付・枠割当・レビュー開始をたどる観察**です。何が待ちを作るかを分ければ、受付整備、確認枠の調整、作成支援のどれを先にするかを選び直せます。今回作ったのは観察の問いと記録案までで、実人への聞き取りや実資料収集はしていません。

## 条件が違えば、対象も選び直す

別条件Cでは、別チームの待ちは各10分以下でした。一方、固定した確定項目を二つの表へ転記する人手が1件90分という記録があります。ここではAIによる全文作成を先にせず、二重入力をまとめ、既存ツールから二次表を作れるかを先に確かめる案になりました。二次表の利用先や統制も確認し、勝手に工程を削除しません。

別条件Dでは、文章の根拠対応にAIを使う案でも、確認者は今週0分、代替未定、正本アクセス未確認でした。見落としが設計・実装・テストの対象から落ちる可能性もあります。「最後に人が見る」だけで許容できるとはせず、今週の出力採用を選ばず、確認体制と正本を整えた後に再比較します。

[別条件の比較結果](discovery-forward.md)に、変わった根拠と選択、残る不足を記録しています。初期条件の待ちや判断を、別チームへそのまま移してはいません。

## 次の担当へ渡すもの

目的は、根拠と品質を保って開発へ渡すまでの遅れと負担を減らすことです。候補ID、選外理由、見直し条件、観察で知りたいこと、資料や役割の未確認を同じ記録で渡します。

観察で対象が絞れたら、業務要件定義で受付条件、未決の扱い、受渡し、品質と測り方を具体化します。ここで詳細プロンプトやRAGを先に決めたり、選定案を実行・支出・本番の許可にしたりしません。
