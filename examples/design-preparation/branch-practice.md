# 変更レビューの準備

受注管理システムの開発チームでは、機能変更の内容に合わせてレビューの担当と観点を決めます。APIの変更、画面の変更、データの変更では、確認する資料も相手も違います。互換性に影響する変更は、通常の変更より詳しく確認します。

FDEは、AIが変更内容を整理した後に使う判断材料と経路を設計します。「何となく重要そうだから詳しく見る」では、担当者が変わるたびに準備がぶれます。変更種別、互換性への影響、参照できる資料を明示し、どの担当へ何を渡すかを確かめます。

これは架空の開発例です。今回は、整理済みの入力から経路を選ぶ部分を通常のPythonで実装しました。AIによる変更内容の抽出・分類の品質は、この実行では測っていません。

## 担当者が判断できる材料にする

| 判断材料 | この例での使い方 | 不明な時 |
| --- | --- | --- |
| 変更種別 | API・画面・データのレビュー経路へ振り分ける | 汎用の担当へ黙って流さず、区分を確認する |
| 互換性への影響 | 影響がある場合は詳細レビューにする | 未判断と「影響なし」を区別する |
| 影響度の点数 | 架空の方針で4以上を詳細、未満を通常にする | 点数尺度と閾値を確認する。4は一般的な基準ではない |
| 資料の版・対象・利用可否 | 現行版で対象に関係し、利用できる承認済み資料だけを残す | 未知の属性や資料IDの衝突を担当者へ返す |

この例での`approved`は資料の状態、`allowed`は入力で与えた参照可否です。関数が権限を調べたり、変更を承認したりするものではありません。資料の承認済み状態から、コードの承認を導きません。

## 実装して確かめたこと

[実装](branch-lab/review_branch.py)は、選んだ経路とレビューの深さ、採用する資料ID、除外した理由、作業IDと版を返します。準備ができても人のレビュー待ちです。候補資料がすべて除外された場合や取得できない場合は、資料の確認・手動取得へ返します。

| 確認 | 実際の結果 |
| --- | --- |
| API・画面・データの通常入力 | それぞれのレビュー経路を返した |
| 点数3・4・5 | 通常・詳細・詳細となり、境界の4を含んだ |
| 点数0、互換性への影響false | 有効な値として通常レビューを返した。影響trueなら詳細となった |
| 未指定・null・文字列の数値・不正な真偽値 | 値を作り直さず、不正な入力として返した |
| 未知の区分・異なる担当への競合 | 勝手な既定経路を選ばず、理由を返した |
| 資料の許可・対象・状態・版の違い | 資料ごとの除外理由を返した。全件除外は準備完了にしなかった |
| 資料取得不能 | 作業IDと版を保ち、手動取得の必要を返した |
| 同じ入力を評価する前後 | 入力を変更しなかった |

[単体テスト](branch-lab/test_review_branch.py)の9メソッドをローカルで実行し、上の条件を確認しました。確認ケースの期待と禁止操作は[条件の記録](branch-intake.md)に対応付けています。

```bash
python3 -m unittest discover -s examples/design-preparation/branch-lab -p 'test_*.py' -v
```

## 別条件で見つかった点を直す

実装者とは別の確認役が、資料版v2・閾値7に変えた10ケースと同じ入力の再評価を実行しました。さらに取得状態を省略すると、契約に反して準備完了になることを発見しました。主担当も同じ入力で再現し、未指定を不正な入力として返すよう修正しました。

この失敗をSkillの必須値・既定値の扱いへ戻し、未指定時に経路もレビュー待ちも返さない確認を追加しています。修正前後の確認と未測定は[別条件の実行記録](branch-forward.md)に残します。

## 次の担当へ渡す

開発担当者は、準備結果と残った確認事項をレビュー担当へ渡せます。資料が不足する場合は資料の管理者へ、経路が競合する場合は担当分担を決める人へ返します。実際の送信、資料へのアクセス、人のレビューや承認はこの例では実行していません。

固定規則で表せる振分けにLLMを追加する必要はありません。AIが前段で抽出した値を使うなら、その値の根拠・型・確定度の確認を加えます。人の代わりにAIへ判断を任せる範囲は、別途合意する必要があります。

保存・送信の処理がない純粋関数なので、保存後の失敗、通知失敗、並行実行の安全性は検証していません。準備結果が現場のレビュー負担や品質を改善するかも未測定です。
