# 検索機能の設計レビュー

受注管理システムに、「取消済みの受注も、必要な時だけ検索できる」機能を追加します。設計担当は基本設計の下書きをAIへ任せ、レビュー担当が要件とAPI契約を確認します。

この架空例でFDEへ渡された相談は、下書きが「取消済みを常に除外する」となっている、というものです。今回の要件は「初期表示では除外し、利用者が明示的に選んだ時だけ含める」。FDEは指示を書き直す前に、AIへ何が渡された設定なのかを確認しました。

前回の入力と誤答は、分析用に提供した架空記録です。一方、以下の入力案・レビュー案・別条件の返却は、独立したAIエージェントがSkillを使って実際に作成しました。実際の製品モデルの変更前後を測った比較実験ではありません。

## 要件があることと、渡っていることを分ける

資料一覧には現在の要件v2がありましたが、前回の入力へ載せた設定なのは旧要件v1の本文でした。API契約v1は今回も有効です。単に番号が古いという理由で、全資料を新版へ差し替える場面ではありません。

FDEは、作業の依頼と許可、今回の適用版、要件R1〜R4、APIの真偽値と既定値、返す形式を分けた[入力案とレビュー案](context-output.md)を作りました。旧要件と別業務の請求資料は根拠本文から外し、使わない理由を残しています。

| 進めた作業 | 残った成果 |
| --- | --- |
| 提供された誤答を要件へ照合 | 常時除外、追加条件不要、承認済みという三つの不一致 |
| 必要情報と版を選択 | 要件v2、継続利用するAPI契約v1、版を選んだ変更メモ |
| 次の担当へ入力を構成 | 目的・禁止操作・根拠・条件・出力形式を分けたPACKET-1 |
| 二つの利用条件でレビュー案を作成 | 選択時は権限内の取消済みも候補、非選択時は除外。APIのtrue/falseとの対応案 |
| 未決と受取者を明示 | 画面方式、実際のAPI動作、権限仕様、承認者の確認は設計・レビュー担当へ |

[入力・根拠・比較の記録](context-record.md)には、選んだ情報、外した情報、誤りの主張、原因仮説、保持した条件を、既存の標準フォーマットで残しています。

## APIの新版が届いていない場合

別条件では、次のレビューで使うAPI契約がv2へ変わりました。資料一覧にはIDと版があるだけで、本文がありません。

[別条件の返却案](context-forward.md)は、要件から説明できる表示条件を下書きにし、API対応は本文待ちに分けました。旧契約の未指定=falseや送信値を、新契約の仕様として使っていません。設計担当から現行契約を受け取り、項目名・型・値・既定値を確認するところへ返しています。

必要な情報がない時でも、分かる範囲の設計は進められます。どこまで根拠があり、どの判断が止まっているかを受取者へ渡します。

## 試して直したことと、残る確認

今回の適用では、AIが実際に作成した文書を「人手で作った案」と記録する誤りもありました。作成役を訂正し、Skillへ「今回のAIによる作成」と「評価対象モデルを別途呼び出す性能比較」を区別する条件を戻しました。

要件の版差替え、版選択の根拠、承認状態、出力形式の明確化を同時に行っているため、どれか一つの変更が品質を改善したとは判断していません。原因仮説と、資料へ照合できた事実を分けています。

この例で確認したのは、Skillを使った入力案・レビュー案と、別条件での返却です。実APIのテスト、製品モデルの対照実験、入力トークン・費用・作業時間、現場での効果は未実施・未測定です。設計担当とレビュー担当は、原資料と実装を照合して次の工程を判断します。
