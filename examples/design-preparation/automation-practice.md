# 設計の下書きは任せる。仕様の確定は、誰が何を見て決めるか

受注一覧へ、注文日From/Toによる検索を追加します。SEから確定要件を受け、
設計担当が基本設計を作り、原要件をレビューしてから開発担当へ渡す仕事です。
毎回、要件IDを転記し、章立てを指示し直す。IDが漏れると、レビュー担当が根拠を探し直します。
まず、この繰り返しを減らしたいと考えました。

架空のチーム・要件による演習です。製品へAI機能を足す話ではなく、開発する人の設計業務へAIを入れる相談です。
[設計業務の全体](README.md)／[今回の入力](automation-intake.md)／[試す前の成功条件](success-practice.md)

## 今は、手動で始めて下書きと点検をそろえる

作る順序と章立ては決められます。原要件が矛盾した時にどちらを採るかはSEの判断です。
そこで[自動化の候補を比較するSkill](../../.agents/skills/compare-automation-options/SKILL.md)を使い、
次の形を比べました。独立した実行役に生の入力を渡し、選択理由と操作ごとの境界を返してもらっています。

| 候補 | 今の困りごとにどう効くか | 今回の選択 |
| --- | --- | --- |
| 人手と通常ツール | 章立てやID照合を固定できる。本文作成は人が行う | 比較相手として残す |
| 都度の相談 | 内容の探索には使えるが、再指示と転記が残る | 例外的な相談へ残す |
| 共通指示・章立てと固定ID点検 | 同じ根拠と形式を使い、漏れを点検して人へ返せる | まず試す。専用チャット製品の構築は必須ではない |
| チケットの限定読取と固定手順 | 主因が転記なら、許可された読取で減らせる可能性 | 別条件で比較。今は接続未実装 |
| 途中で調査順を選ぶagent | 参照先を途中結果で選ぶ必要がある時に役立ち得る | 今は必要性が未説明。範囲と上限を決めてから検討 |
| 確定版へ自動反映し送信 | 作成後の人の判断まで移す | 今の許可にはない。効果も未証明なので採らない |

今試すのは、設計担当が手動で開始し、共通の章立てと根拠IDで下書きを作り、
固定ルールでIDを照合して人へ返す範囲です。チャット、定時起動、外部接続の有無だけで
任せる判断の範囲は決まりません。全自動を終点にすることも、決まった段階を全部通ることも必要条件にしていません。

## 実際に作った下書きで、未決を残す

独立実行役は[基本設計の下書き](automation-lab/basic-design-draft.md)を作成しました。
原要件S1-v1の4項目を、次のように渡しています。

- R01：From/Toと、空欄の端はその側の制限なし。
- R02：両端指定でFrom＞Toなら、検索せず入力誤りを表示。
- R03：既存の参照権限を保ち、検索条件で閲覧範囲を広げない。
- R04：時刻・タイムゾーンの解釈はSEへ確認する未決事項。

この下書きは確定版ではありません。R04をもっともらしい値で埋めず、
各記述の根拠IDを添えて返しました。作成側とは別に原文と対応を照合し、
R03の権限条件とR04の未決が残っていることを確認しています。
レビュー担当の実回答や、設計の承認を得たわけではありません。

## 確認する人がいなくても、全部を止めない

[委任の境界を決めるSkill](../../.agents/skills/define-delegation-boundary/SKILL.md)で、
原要件を読む、下書きを作る、IDを点検する、原文レビュー、確定版反映・引継ぎを分けました。

原要件の参照と作業用下書き、ローカル点検は演習内で許可されています。
仕様の決定、確定版への反映、開発担当への送信はその許可に含みません。
人が確認するなら、原要件へのアクセス、照合する技能、時間、修正・拒否できる手段が必要です。
今回は今週の確認時間が未確認で、代理も指定されていません。

その場合、下書き整理と点検は続け、レビューと確定後の引継ぎを保留します。
不在を自動承認で埋めず、担当の確保を開発リーダーへ返す案です。
許可済みの準備へ、毎回新しい承認を増やすこともしません。

## 自信度と、実際に進めてよい条件を分ける

独立実行役は[模擬経路のコード](automation-lab/check_routes.py)も作り、ローカルで実行しました。
コードは固定のID集合・許可操作・ケース配列から経路を返す小さな例です。
下書きのMarkdownを解析したり、外部ツールを呼んだり、実行権限を強制するものではありません。
下書きの作成と原文照合は、このコードとは別に行っています。

| 入力した条件 | 実行で返った経路 | この条件で進めること |
| --- | --- | --- |
| N：既知の根拠IDと許可内の下書き | DRAFT_SCRATCH | 作業用下書きまで。確定・送信は含まない |
| H：自信度0.99でも存在しないR99を参照 | RETURN_MISSING_SOURCE | 根拠を確認へ返す。高い自信度で通さない |
| L：自信度0.25で、許可内の固定ID点検 | RUN_DETERMINISTIC_CHECK_PASS | 固定検査は実行できる。意味の正しさは別に照合 |
| X：自信度0.99で、無確認の確定版反映・送信 | DENY_OUT_OF_SCOPE | 許可外の操作を行わない |
| U：確認者不在、下書き整理は許可内 | DRAFT_SCRATCH_HOLD_REVIEW | 準備は進め、レビュー・確定は待つ |

```bash
python3 examples/design-preparation/automation-lab/check_routes.py
```

5条件は作成側とは別に再実行し、記事の結果と照合しました。
これは条件分岐の模擬実行です。実ツールの権限制御、根拠文書の意味の正しさ、
本番の承認・送信防止が実装できたことは証明しません。

## 条件が変われば、任せ方も選び直す

チケット読取と作業用出力だけが追加で許可された別条件では、転記を減らす固定経路を直接比較できます。
専門チャットを先に作る必要はありません。自動通知・更新・送信の許可は引き継がれません。
実際の接続は試していないので、維持負担や効果は未確認です。

途中の発見で次に読む資料を選ぶ必要が生じたら、動的調査も候補になります。
資料集合と許可道具、完了、反復・時間・費用の上限、矛盾・上限到達時の返却を定めます。
今回その上限は未決なので、無制限の調査を実行する案にはしていません。

原要件がS1-v2へ変わった別条件では、v1のレビューをそのまま確定根拠へ使いません。
変更点と影響する記述をv2で再照合します。追記された内容そのものは未提示なので補いません。
これら三つは、条件を変えた比較・追跡です。接続、動的実行、v2の実レビューは未実施です。

## 次に測るのは、引継ぎまでの仕事

下書きが作れたことだけで成功にはしません。根拠IDの対応、未決の扱い、重大な仕様追加、
受取者が照合できるかに加え、作成・点検・レビュー・修正・引継ぎの全人手と待ちを比べます。
許容時間や誤り率は未合意です。確認担当の時間・技能と判断条件をそろえて、次の試行へ渡します。

今回実施したのは、独立agentによる候補比較と委任案、架空要件の下書き作成、固定条件の模擬経路実行と再照合です。
専用の業務向けモデル評価、実システム接続、実担当者のレビュー、現場の効果測定、本番導入は未実施です。
