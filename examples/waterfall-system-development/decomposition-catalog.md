# システム開発 業務分解カタログ

これは Layer 2 の13工程を、Layer 3 の Business Use Case / scene と Layer 4 の Business Activity へ分解した初期仮説です。

名称は「作業をする」ではなく、入力された状態を何へ変える業務かが読めるように置いています。実務レビューで違和感が出たら、下位だけでなく親工程の境界・名称まで戻って直します。

---

## 1. 見積

### 1.1 開発範囲を見定める
- 依頼背景と期待成果を捉える
- 対象業務・対象システム・対象組織を区切る
- 対象内 / 対象外を明示する
- 制約・期限・契約条件を捉える

### 1.2 不確実性を見立てる
- 未確定要件を識別する
- 技術的不確実性を識別する
- 外部依存・調整依存を識別する
- リスクと見積前提を結びつける

### 1.3 開発規模と実現体制を構成する
- 機能・データ・IF・移行・非機能の規模を見立てる
- 工程別工数を組み立てる
- 必要スキルと役割を組み立てる
- 体制・要員・期間の整合を取る

### 1.4 費用と納期の成立性を整える
- 工数を費用へ変換する
- 調達・ライセンス・環境費を織り込む
- マイルストーンと納期を組み立てる
- バッファとリスク対応余地を織り込む

### 1.5 見積条件を合意可能な形にする
- 見積根拠を説明可能にする
- 前提・除外・変動条件を明文化する
- 見積レビューで矛盾を解消する
- 見積を提示し、次段階の判断材料にする

**Flow候補:** 情報不足 → 確認 → 再見積、リスク顕在化 → 前提変更 → 見積更新。

---

## 2. 要件定義

### 2.1 開発目的と要求境界を定める
- 解決したい業務課題を言語化する
- 期待する業務成果を定める
- 対象業務・対象利用者・対象システムを区切る
- 要件定義の完了条件を定める

### 2.2 現行業務と制約を理解する
- 現行業務の流れを把握する
- 業務ルール・判断条件を抽出する
- 現行データ・帳票・外部連携を把握する
- 現行課題・例外・手作業を把握する
- 法令・契約・組織上の制約を把握する

### 2.3 望ましい業務状態を構成する
- To-Be業務を構成する
- 業務責任と役割分担を定める
- 業務要件を構造化する
- 業務ルールの変更点を定める
- 業務上の受入条件を定める

### 2.4 システム責務と機能境界を定める
- 人が担うこととシステムが担うことを分ける
- 機能要件を整理する
- データ要件を整理する
- 外部IF要件を整理する
- システム境界と責任分担を定める

### 2.5 品質・運用・移行条件を定める
- 性能・可用性・拡張性などの非機能要件を定める
- セキュリティ要件を定める
- 運用・監視・保守要件を定める
- データ移行・切替要件を定める
- 障害時・例外時の業務継続条件を定める

### 2.6 要件を整合させ合意する
- 要件間の矛盾・抜け・重複を解消する
- 優先度とスコープを調整する
- 受入条件と要件を結びつける
- レビュー指摘を反映する
- 合意した要件をベースライン化する

**Flow候補:** 要求発見 → 要件化 → 矛盾検出 → 調整 → 再合意、変更要求 → 影響分析 → 要件更新。

---

## 3. 基本設計

### 3.1 利用者から見える振る舞いを構成する
- 画面・操作・状態遷移を設計する
- 入出力・帳票を設計する
- メッセージ・エラー応答を設計する
- 利用者権限ごとの見え方を設計する

### 3.2 業務情報をシステム情報へ構造化する
- 論理データモデルを構成する
- 業務概念とデータ項目を対応づける
- データの生成・更新・参照責任を定める
- 履歴・監査・保持要件を設計へ反映する

### 3.3 外部との契約を設計する
- API / ファイル / メッセージIFを設計する
- データ形式・コード体系を定める
- タイミング・順序・再送条件を定める
- 接続先との責任境界を定める
- 異常時の応答・復旧方式を定める

### 3.4 運用可能な外部仕様を構成する
- ジョブ・バッチ運用を設計する
- 監視対象と通知を設計する
- 権限・認証・認可方式を設計する
- ログ・監査方針を設計する
- 環境差分と設定管理方針を設計する

### 3.5 非機能要求を方式へ変換する
- 性能要求を構成・処理方式へ落とす
- 可用性要求を冗長化・復旧方式へ落とす
- セキュリティ要求を技術方式へ落とす
- 保守性・変更容易性を構造へ反映する

### 3.6 外部仕様を整合させる
- 要件との対応を確認する
- UI・データ・IF・運用間の矛盾を解消する
- 実現性レビューを行う
- レビュー指摘を反映する
- 基本設計をベースライン化する

**Flow候補:** 要件 → 外部仕様化 → 横断整合 → 実現性指摘 → 再設計 → ベースライン。

---

## 4. 詳細設計

### 4.1 外部仕様を内部構造へ分解する
- 機能をコンポーネント / モジュールへ分ける
- 各要素の責務を定める
- 内部依存関係を整理する
- 変更境界を意識して責務を再配置する

### 4.2 処理ロジックと状態変化を設計する
- 処理手順を設計する
- 条件分岐・状態遷移を設計する
- バリデーションを設計する
- トランザクション境界を設計する
- 並行処理・排他・再実行性を設計する

### 4.3 データ実装構造を設計する
- 物理データモデルを定める
- テーブル・索引・制約を設計する
- SQL / データアクセス方式を設計する
- データ量・性能条件を反映する

### 4.4 内部インターフェースを設計する
- モジュール間IFを定める
- API内部契約を定める
- 入出力・例外・戻り値を定める
- 依存方向と呼出し順序を整える

### 4.5 例外・ログ・復旧動作を設計する
- 例外分類と処理責任を定める
- ログ出力内容を定める
- リトライ・ロールバックを設計する
- 障害解析に必要な観測情報を定める

### 4.6 実装可能な設計へ整える
- 基本設計との対応を確認する
- 実装難易度と技術制約を確認する
- レビュー指摘を反映する
- 実装単位と単体テスト観点を整える
- 詳細設計をベースライン化する

**Flow候補:** 外部仕様 → 内部構造化 → 実装可能性レビュー → 責務再分割 → 詳細化。

---

## 5. 実装・単体テスト

### 5.1 実装可能な作業単位を準備する
- 対象設計と変更範囲を確認する
- ブランチ / 作業環境を準備する
- 依存関係とビルド条件を確認する
- 単体テスト観点を具体化する

### 5.2 設計を実行可能なコードへ変換する
- 業務ロジックを実装する
- データアクセスを実装する
- 外部 / 内部IFを実装する
- 例外・ログ・設定処理を実装する
- 必要な構成定義を更新する

### 5.3 単体で振る舞いを検証可能にする
- ユニットテストコードを実装する
- 正常・境界・異常条件を検証する
- モック / スタブで依存を分離する
- 再現可能なテストデータを用意する

### 5.4 コード品質を機械的に確認する
- ビルドを成立させる
- 静的解析を確認する
- 単体テストを自動実行する
- カバレッジや規約違反を確認する

### 5.5 変更内容を他者検証可能にする
- コードレビューを依頼する
- 設計意図と差分を説明する
- レビュー指摘を反映する
- 必要に応じ設計側へフィードバックする

### 5.6 統合可能な変更として確定する
- 修正後の単体テストを再実行する
- マージ条件を満たす
- 構成管理へ取り込む
- 次の統合検証対象として識別可能にする

**Flow候補:** 実装 → テスト失敗 → 修正 → 再テスト、レビュー指摘 → 設計見直し → 再実装。

---

## 6. 内部結合テスト設計

### 6.1 内部結合で確かめる責務境界を定める
- 結合対象コンポーネントを特定する
- 内部IFと依存関係を確認する
- 単体テストでは検証できないリスクを抽出する
- テスト対象 / 対象外を定める

### 6.2 結合時の重要な振る舞いを抽出する
- 主要な処理連鎖を抽出する
- 状態・データの受渡しを抽出する
- エラー伝播・ロールバックを抽出する
- バッチ / 非同期 / 並行動作を抽出する

### 6.3 テストシナリオと期待結果を構成する
- 正常シナリオを設計する
- 境界・異常シナリオを設計する
- 前提データと操作を定める
- 期待する状態・出力・ログを定める

### 6.4 再現可能な検証条件を準備する
- テスト環境要件を定める
- テストデータを設計する
- モック / スタブ範囲を定める
- 配備する構成ベースラインを定める

### 6.5 テスト完了判断を定義する
- 開始条件を定める
- 終了条件を定める
- 要件 / 設計とのトレーサビリティを確認する
- テスト仕様をレビューし確定する

---

## 7. 内部結合テスト

### 7.1 結合検証可能な状態を作る
- 対象版を環境へ配備する
- 設定とテストデータを反映する
- 疎通 / スモーク確認を行う
- 実施開始条件を満たす

### 7.2 内部結合の振る舞いを検証する
- 正常シナリオを実行する
- 境界・異常シナリオを実行する
- データ状態・ログ・副作用を確認する
- 実績をエビデンスとして残す

### 7.3 不具合を切り分け修正可能にする
- 期待差異を検出する
- テスト不備 / 環境不備 / 実装不備を切り分ける
- 不具合を記録し担当へ渡す
- 修正版の影響範囲を確認する

### 7.4 修正後の品質を再確認する
- 修正箇所を再テストする
- 影響範囲を回帰テストする
- 不具合状態を更新する
- 未解決リスクを整理する

### 7.5 内部結合完了を判断する
- 実施結果を集約する
- 残存不具合を評価する
- 終了条件と照合する
- 次工程へ進める品質か判断する

**Flow候補:** 失敗 → 原因切り分け → 修正 → 再配備 → 再テスト → 回帰確認。

---

## 8. 外部結合テスト設計

### 8.1 外部接続の責任境界を確定する
- 接続先と対象IFを特定する
- 送受信責任を確認する
- 接続条件・認証・暗号化条件を確認する
- 相手側制約と利用可能時間を確認する

### 8.2 外部連携の契約を検証観点へ変換する
- データ形式・コード値の観点を抽出する
- 順序・タイミングの観点を抽出する
- 再送・重複・冪等性の観点を抽出する
- タイムアウト・異常応答の観点を抽出する

### 8.3 相互検証シナリオを構成する
- 正常連携シナリオを設計する
- 入力不正・応答不正を設計する
- 通信断・遅延・タイムアウトを設計する
- 再送・復旧・重複受信を設計する

### 8.4 共同実施条件を整える
- 接続先と実施日程を調整する
- テストデータを相互合意する
- 接続情報・証明書・アカウントを準備する
- 障害連絡と切り分け窓口を定める

### 8.5 外部結合完了条件を合意する
- 開始条件 / 終了条件を合意する
- エビデンスの責任分担を定める
- 不具合判定ルールを定める
- テスト仕様を双方で確認する

---

## 9. 外部結合テスト

### 9.1 外部接続を成立させる
- ネットワーク疎通を確認する
- 認証・証明書を確認する
- 送受信の基本疎通を確認する
- 接続条件差異を解消する

### 9.2 外部連携契約どおりの動作を検証する
- 正常送受信を検証する
- データ変換・コード変換を検証する
- 順序・タイミングを検証する
- 相手側処理結果まで確認する

### 9.3 障害時の境界動作を検証する
- 異常応答を検証する
- 通信断・タイムアウトを検証する
- 再送・重複処理を検証する
- 復旧後の整合性を検証する

### 9.4 問題の所在を共同で切り分ける
- 自システム / 接続基盤 / 相手システムを切り分ける
- ログ・電文・時刻を突き合わせる
- 不具合責任と修正担当を合意する
- 再試験条件を調整する

### 9.5 修正結果と連携品質を確定する
- 再テストする
- 影響IFを回帰確認する
- 残存課題を評価する
- 双方で完了判断する

**Flow候補:** 連携失敗 → 双方ログ照合 → 境界切り分け → 修正 → 再接続 → 再試験。

---

## 10. システムテスト設計

### 10.1 システム全体で証明する品質を定める
- 業務E2Eの対象を定める
- 機能品質の重点を定める
- 非機能品質の重点を定める
- 本番運用上の重大リスクを定める

### 10.2 業務シナリオをE2E検証へ変換する
- 代表業務シナリオを設計する
- 複数機能・複数IFを跨ぐ流れを設計する
- 権限・状態遷移を織り込む
- 例外・復旧シナリオを設計する

### 10.3 非機能要求を試験へ変換する
- 性能 / 負荷試験を設計する
- 可用性 / 障害試験を設計する
- セキュリティ試験を設計する
- バックアップ / リストアを設計する
- 運用監視試験を設計する

### 10.4 本番相当の検証条件を構成する
- 環境構成を定める
- データ量・データ特性を定める
- 外部接続条件を整える
- 監視・ログ・運用手順を組み込む

### 10.5 システム品質の判定基準を定める
- 開始 / 終了条件を定める
- 欠陥重要度と許容条件を定める
- 要件とのトレーサビリティを確認する
- UATへ渡す条件を定める

---

## 11. システムテスト

### 11.1 本番相当構成を検証可能にする
- 対象版を配備する
- 環境設定・監視設定を反映する
- テストデータを準備する
- スモーク確認を行う

### 11.2 業務E2Eを検証する
- 主要業務シナリオを実行する
- 複数機能間の整合を確認する
- 権限・状態・データ整合を確認する
- 外部連携を含む結果を確認する

### 11.3 非機能品質を検証する
- 性能 / 負荷を計測する
- 障害時動作と復旧を確認する
- セキュリティ観点を検証する
- 監視・バックアップ・リストアを検証する

### 11.4 システムレベルの不具合を解消する
- 期待差異を記録する
- 原因領域を切り分ける
- 修正優先度を判断する
- 修正後に再テスト / 回帰テストする

### 11.5 UATへ渡せる品質を判断する
- 結果を品質指標へ集約する
- 残存不具合・制約を評価する
- 運用上の残課題を整理する
- 終了条件を満たすか判断する

---

## 12. ユーザー受入テスト

### 12.1 受入で確認する業務価値を定める
- 業務要件と受入条件を確認する
- 重要業務シナリオを選ぶ
- 受入判断者と参加者を定める
- 受入対象版を確定する

### 12.2 ユーザーが業務として試せる状態を作る
- UAT環境を準備する
- 業務に近いテストデータを準備する
- ユーザーアカウント・権限を準備する
- 実施手順と問い合わせ経路を共有する

### 12.3 実業務の観点で適合性を確認する
- 業務シナリオを実行する
- 操作性・業務ルール適合を確認する
- 帳票・データ・外部連携結果を確認する
- 業務例外や代替手順を確認する

### 12.4 発見事項を受入判断可能に整理する
- 不具合と要望を区別する
- 重大度・業務影響を評価する
- 修正要否と時期を判断する
- 修正後の再確認を行う

### 12.5 受入可否を決定する
- 未解決事項を一覧化する
- 条件付き受入の条件を整理する
- 受入基準と結果を照合する
- 受入判定を記録する

**Flow候補:** 業務シナリオ実施 → 違和感発見 → 不具合 / 要望分類 → 修正判断 → 再確認 → 受入判定。

---

## 13. 導入

### 13.1 本番へ出す変更範囲を確定する
- リリース対象版を確定する
- 変更一覧と既知制約を整理する
- 配備物・設定・移行物を揃える
- リリースノートを確定する

### 13.2 切替可能性をGo / No-Go判断可能にする
- 導入前提条件を確認する
- 未解決不具合・リスクを評価する
- 関係者の準備状況を確認する
- 実施 / 延期の判断材料を揃える

### 13.3 本番構成を新しい状態へ切り替える
- 本番配備を実施する
- 本番環境設定を反映する
- 必要なデータ移行を実施する
- バージョン / 構成状態を記録する

### 13.4 切替結果を業務利用可能な状態まで確認する
- 技術スモーク確認を行う
- 重要業務の疎通を確認する
- 監視・ログを確認する
- データ移行結果を照合する

### 13.5 異常時に安全な状態へ戻す
- 継続可否を判断する
- ロールバック条件と照合する
- 必要に応じ旧版へ戻す
- データ整合を回復する
- 再導入条件を整理する

### 13.6 運用へ責任を移す
- 運用手順・監視条件を引き渡す
- 既知問題・暫定対応を共有する
- サービスデスク / 保守窓口を有効化する
- 初期流動監視へ移行する
- 導入完了を記録する

**Flow候補:** Go/No-Go → 配備 → 移行 → スモーク → 業務確認 → 継続 / ロールバック → 運用移管。

# 横断 Business 候補

13工程の外に追い出すのではなく、複数工程に反復的に関係する Business としてモデル化する候補です。

## プロジェクトを統制する
- 計画を構成する
- 進捗を把握する
- 見通しを更新する
- 体制・優先度を調整する

## 変更を統制する
- 変更要求を受け付ける
- 影響を分析する
- 採否を判断する
- 要件・設計・コード・テストへ変更を伝播する
- ベースラインを更新する

## 課題とリスクを制御する
- 課題 / リスクを識別する
- 影響と優先度を評価する
- 対応責任を割り当てる
- 状態を追跡する
- 残余リスクを判断材料へ戻す

## 品質を保証する
- 品質目標を定める
- レビュー / テスト結果を集約する
- 欠陥傾向を分析する
- 工程移行可否を判断する

## 構成を再現可能に保つ
- 構成要素を識別する
- 版を管理する
- ベースラインを確定する
- 環境ごとの差分を管理する
- リリース対象との整合を保つ

## 環境を提供・維持する
- 必要環境を設計する
- 環境を構築する
- 設定を反映する
- 利用状態を維持する
- 障害や差異を解消する

## 意思決定を共有可能にする
- 判断材料を揃える
- 関係者で論点を確認する
- 決定を記録する
- 後続の業務へ決定内容を伝える
