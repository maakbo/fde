# 変更を反映する業務を教える

[引き継ぎの全体像へ戻る](README.md)

これは架空の例です。実案件では作業名、環境、権限、承認、確認項目を現場の事実で置き換えます。公開例から本番コマンドや権限を推測しません。

## 何のために

利用者へ変更を安全に届け、失敗した場合も影響を判断して回復できるようにします。アーキチームから移す対象は「実行する作業」です。実施可否の決定、手順変更の承認、異常時の判断を誰が担うかは別に合意します。

| 入口としての工程 | 業務と子業務 | 実演する作業の例 |
| --- | --- | --- |
| 導入、運用 | 実施条件を整える → 対象と前提を確認する | 対象版・変更範囲・権限・停止条件を照合する |
| 導入、運用 | 変更を反映する → 手順に沿って実行する | 合意済み手順を実行し、結果と時刻を記録する |
| 導入、運用 | 結果を確かめる → 継続・回復の判断材料を整える | 疎通・重要な機能・監視結果を確認し、異常を報告する |

工程は索引です。業務から子業務への分解と、作業への具体化は別の関係です。状況に応じて確認や反映を繰り返します。

## 1件を一緒に通す

1. **背景を説明する**：変更の目的、利用者への影響、今回の対象・対象外を確認する。
2. **開始条件を照合する**：対象版、実行権限、承認、連絡先、停止・回復条件を手順と突き合わせる。条件が欠ければ実施判断者へ返す。
3. **実演する**：アーキチームが一度説明しながら作業する。操作だけでなく、その時点で何を判断し、何を記録するかを言葉にする。
4. **再現する**：アプリ保守チームが同じ種類の変更を実施し、アーキチームは観察する。期待結果と証跡を本人が説明する。
5. **例外を試す**：失敗・確認不能・想定外の変更でどこで止め、誰に知らせ、どの情報で継続・回復を決めるかを確認する。実際の切戻し操作は承認された環境と手順で扱う。
6. **受け入れる**：実行と説明を再現でき、必要な権限・手順・判断窓口・支援期間が揃ったことを双方で確認する。

実案件の記録欄：対象作業、起動条件、入力情報、参照先、作成する証跡、作業者、実施判断者、異常時の判断者、権限、実演結果、再現結果、未解決事項、移管日。空欄は合意済みと見なさず、担当者と確認日を残します。
