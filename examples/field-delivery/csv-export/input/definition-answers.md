# 架空SE役からの回答 A1

以下は進行役が用意した演習上の条件。実際の利用者・本人・現場の合意ではない。
このローカル試行の仕様はSE役が回答してよい。実組織の規程・送信・開始は決定しない。

1. 状況・受注日・順序は既存検索と同じ。指定条件に合う全行（今回pagingなし）を出す。
   当該検索条件で取得したJSONとCSVのID・日付・状況と順序が一致することを独立確認役が調べる。
   画面ボタンは「現在の入力条件でCSV出力」。押下時に入力されている条件を使う。
   最後に画面表示した検索結果と、未検索の入力変更後も同じと約束するものではない。
2. 列はこの順で「受注ID」「受注日」「状況」。IDはid、受注日はYYYY-MM-DD、状況は
   NEW/SHIPPED/CANCELLED。見出しあり。利用者が受注の識別・日付・状況を照合するため。
3. このデモはUTF-8 BOMあり、行区切りCRLF、区切りカンマ、filename orders.csv。
   カンマ・二重引用符・CR/LFを含む値はCSV引用で元の値を保つ。値を勝手に改変しない。
   日本語の見出しと、日本語/カンマ/引用符/改行を含む架空IDの整形をローカルで試す。
   実際のExcel環境は未確認。BOMを付ければ全環境で使えるという承認ではない。
   任意の実データ/表計算の数式安全性は別条件。今回は架空データをローカルで検証する。
4. 0件は正常で、見出しだけを出力する。無効検索・未知/重複queryは400 JSONとして
   エラーを返し、CSV attachmentにしない。GET以外405。元データは変えない。
   正常CSVは200、text/csv;charset=utf-8、attachment filename orders.csv。
5. 一覧にCSV取得ボタンを置き、現在の入力条件を送る。確認役がHTTPのCSVを独立parserで
   読み、期待行/順序/バイト/ヘッダを照合し、UIボタン動作も可能ならブラウザで確認。
   運用受取者役には起動/停止、正常/誤条件の確認、旧版への戻し方と未実施を渡す。
6. CSVのHTTP pathは設計案として選び、既存 GET / と /orders を壊さない。
   技術制約はJava16+ plain class・標準ライブラリ、Python3、依存追加なし、localhost。
   選んだpathや実装方法はDesignで根拠を残す。未確認を新しい仕様にしない。
   仕様衝突はSE役へ、実装の不具合は実装役へ、環境/権限不足は進行役へ返す。
   実データ・社内送信・本番・現場pilot・工数削減と定着は今回決めず未実施。

CSV引用形式の照合先: RFC4180 https://www.rfc-editor.org/rfc/rfc4180
これは形式の背景であり、上のBOM/日本語ヘッダ/0件/権限をRFCが決めるものではない。
