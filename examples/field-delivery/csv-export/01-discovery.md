# Discovery｜受注一覧のCSV依頼を使った開発チームの受渡し

この記録は架空相談と架空のSE・開発責任者役からの追加回答に基づく演習用の下書き。対象は**開発チームが依頼を受けて変更を運用担当へ渡す仕事**であり、営業担当が受注一覧やCSVを使う業務そのものの改善ではない。実組織での聞取り、合意、効果測定は行っていない。

**最初に聞く一問**：「このCSVの依頼を受けてから実装者へ設計書を渡すまで、今回どんなことを確認し、何を渡しましたか？」

## 目的と現行

目指すのは、次の担当が未決定を見分け、必要な判断を前の担当へ返せる受渡し。AIの利用自体やコード生成量を成果にしない。レビュー量・確認負担が増えないことも確かめる。

**全体試行の成果物**は、このCSV機能追加を要件→設計→コード→独立受入→運用への変更点・確認／戻し方の引継ぎ準備まで、許可されたローカルで通した一件の記録と実行結果。機能追加はこの試行に含む。コードの採否とリリースは人の判断に残し、今回は判断材料とローカル実行まで進める。正式導入・本番配備はしない。

**改善する受渡し**は、条件と根拠、未決定、確認者を同じ記録へ残し、後工程が要件を補完せず質問・実装・検証を返せる状態。最初にSE→実装者を見て、独立確認役と運用受取者まで同じ記録が役立つかを全体試行で確かめる。成果物の完成と受渡しの改善効果は別々に判断する。

| 受渡し | 相談文で分かる現行 | まだ分からないこと |
| --- | --- | --- |
| 営業担当の依頼 → SE | 「受注一覧の検索結果をCSVでもらい、手元で確認したい」。架空SE役によれば、利用者は検索結果を手元で確認したい。既存一覧には状況・受注日の検索があり、CSV出力はない | 依頼を正式な条件にする方法 |
| SE → 実装者 | SEが利用者へ聞き、要件・設計を作って渡す | 設計書に何が書かれ、どの条件が未決定のまま渡ったか |
| 実装者 → 独立確認役 | 実装者が条件の細部を補い、レビューで聞き直すことがある | 今回どの条件で、誰が、いつ差し戻したか。頻度と所要時間 |
| 確認結果 → 運用受取者 | 変更点と確認・戻し方を渡す | 受取条件、例外時の戻し先 |

相談文と追加回答は架空の担当役による説明であり、一件の実物や実演で照合した現場観察ではない。架空メモにはCSVの列名、文字コード、0件時の扱いがなく、実装者が推測し得る。工数・件数・待ち時間の基準値も未測定。したがって、最大の遅延箇所や改善効果はまだ言えない。

## 最初に変える候補

**暫定候補：SEから実装者へ渡す設計の条件・根拠・未決定・確認者を見えるようにする。** 実装者が補った条件をレビューで聞き直すという相談文に直接対応する。依頼の解釈を誰が決めるかは変えず、未決定を実装者の推測で埋めない。独立確認役が判断に使う根拠も同じ受渡しの中で確かめる。試行中に別の受渡しが主因と分かれば対象を選び直す。

| 仕事の見直し | 今回の候補と確認点 |
| --- | --- |
| なくす | 重複した転記・確認があるか調べる。レビューや受入条件の確認は必要性と責任が未確認なので廃止しない |
| まとめる | SEが説明した根拠と、実装者・確認担当が後で聞き直す事項を同じ記録へ寄せられるか調べる。独立した確認の責任は残す |
| 順番を変える | 実装後に判明する条件不足を、SE→実装者の受渡し時に検出できるか試す |
| 簡単にする | 次の担当に必要な決定済み条件、根拠、未決定と確認先だけを短く渡し、確認項目を増やしすぎない |

**提案する流れ（未採用）**：SE役が依頼と現行仕様から「決まった条件と根拠／未決定と確認者／独立確認役が見るべき点」を整理する → 実装者は未決定を補完せずSE役へ返し、決まった条件に沿ってローカルで実装・テストする → 独立確認役は決定根拠と実装・実行結果を照らす → 運用受取者へ変更点と確認・戻し方を渡す準備をする。各受渡しの具体的な成果物と責任はDefinitionで決める。

## 手段の比較

| 候補 | 期待できること | 成立条件・懸念 | 今回の扱い |
| --- | --- | --- | --- |
| 人が設計の受渡しを明確にする | 未決定をその場で戻せる。追加の接続や費用が不要 | SE・実装者・確認担当が使える短さと責任分担が必要 | 最初の基準案 |
| 定型の確認表や既存の開発手順を整える | 決まった項目の抜けを検出しやすい | 条件が一律か、項目追加が負担を増やさないか未確認 | 人の案と比較する |
| AIが依頼・設計の曖昧な点を候補として示す | 文脈のある文章から不足候補を拾える可能性 | 根拠を示せる入力、許可された環境、誤指摘・見落とし時の人の確認負担を要検証 | 限定した補助案。採否は人 |
| AIエージェントが工程を自律的に進める | 複数工程の接続余地はある | 判断・承認・接続の境界が未定。現時点の根拠では自律化を正当化できない | 最初の改善手段には選ばない |
| CSV機能だけを単独で作る | 利用者の依頼には応える | 受渡し改善の証拠が残らなければ今回の目的を測れない | 機能実装は全体試行に含め、判断記録と独立受入まで通す |

現時点で、SE→実装者の受渡しを整える案は相談された手戻りへ直接届き、ローカルの架空例で試しやすい。AI補助の適合性は未検証で、誤指摘が確認負担を増やす恐れがある。影響・実現性・リスクの数値評価や費用対効果は、基準値と実例がないため行わない。

## Definitionへ渡す判断と問い

- **全体試行の範囲**：CSV機能追加の要件からローカル実装・テスト・独立受入・リリース準備まで一件として通す。受渡し改善の仮説を、その後工程で実際に使えるか確かめる。
- **最初に改善する受渡し**：SE→実装者で決定済み条件と根拠、未決定と確認者を分ける。独立確認役も使えるかを見る。対象選定の根拠は架空相談の「実装者が細部を補い、レビューで聞き直すことがある」という申告のみ。
- **次工程で決める詳細**：CSVの列名、文字コード、0件時の扱い、検索条件との関係や出力範囲、通常・例外の受入条件。架空SE役へ質問し、決定・根拠・未決定・確認者を同じ記録へ残す。Discoveryでは値を推測しない。
- **対象外**：実データの取得、AIによる要件・コード採否・受入・リリースの承認、実組織への導入・展開、本番配備。
- **受渡しの質問**：架空の一件で、設計書のどの条件を実装者が補い、独立確認役は何を聞き直したか。SE役・実装者・独立確認役は、どの情報が揃えばそれぞれ先へ渡せるか。運用受取者が受け取る確認・戻し方は何か。
- **負担と効果の証拠**：同じ範囲で、書く・読む・聞き直す作業時間、返答待ち、差戻し、レビューの確認量と結果を区別して記録する。現行値がないため、改善や削減の主張は保留する。
- **最初の確かめ方**：許可された架空の一件で、通常例と条件不足の例を流す。短い受渡し記録で実装者が未決定を返し、決定後にローカル実装し、独立確認役が根拠と実行結果を照らせるかを見る。追加の確認量も記録する。演習中の役割名や返答を実在の合意とみなさない。
- **今進められる範囲／停止点**：公開の架空資料とローカル下書き、許可されたコード・テスト実行とlocalhost通信で、独立受入の結果とリリース判断材料まで作る。外部送信、費用追加、実データ、GitHub操作、merge、本番配備は行わない。実組織の開始・承認・定着・効果は未確認のまま残す。

次の担当は、この暫定対象、根拠、未決定、許可範囲を引き継ぎ、入力・観測可能な結果・通常／例外・合格条件・決定者をDefinitionで明確にする。仕様不足は決められる担当へ返し、実例から対象の誤りが分かればDiscoveryへ戻す。
