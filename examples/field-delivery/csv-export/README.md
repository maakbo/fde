# 受注一覧にCSV出力を追加する

「検索した受注をCSVでもらいたい」。この依頼を受けた開発チームが、要件を確かめ、設計し、実装・テストして、運用担当へ渡すところまで進めた架空の開発例です。

fdeとAIエージェントを使い、各工程を別のコンテキストへ引き継ぎました。次の担当には、その時点の依頼・条件・成果物を渡し、後の完成形は見せません。実装者とは別に、受入条件から期待を先に作る確認役も置きました。コンテキストは分けていますが、OSのアクセス権を隔離した実験ではありません。

狙いは、AIにコードを書かせることだけではありません。「どこまで決まっているか」「何を確認してから次へ渡すか」を揃え、後工程が条件を推測せずに仕事を進められるかを試しています。実在するチームの作業時間や改善効果は測っていません。

## 依頼を受けてから、次へ渡すまで

| 工程 | エージェントが受け取り、行ったこと | 実際に残ったもの |
| --- | --- | --- |
| 業務を聞く | [相談](input/field-request.md)から、開発チームの受渡しと製品利用者の仕事を分ける | [Discovery](01-discovery.md)。条件不足を推測で埋めずに返す、という改善仮説 |
| 要件を決める | [六つの質問](02-questions.md)を返し、進行役が架空SEとして[回答A1](input/definition-answers.md)を作る | [Definition](02-definition.md)。受渡し条件D-Hと機能条件D-Pを分け、根拠・例外・決定者を記録 |
| 設計する | 決まった条件と[既存仕様](input/baseline-contract.md)から、実装者が判断できる設計を作る | [設計](03-design.md)。検索条件の共用、CSV API、クリック時の入力取得、例外時の応答 |
| 実装する | 設計と固定した旧コードを受け取り、CSV出力と画面ボタンを作る | [コードと自己確認](implementation/04-implementation.md)。既存検索サービスは変更せず、CSV整形を分離 |
| 独立して確認する | 実装を見る前に[期待](acceptance/expected-cases.md)を固定。設計から接続先を確認し、実際のHTTPとCSVを照合 | [独立受入](acceptance/05-acceptance.md)。132項目を通常実行とPython最適化実行で確認 |
| 運用担当として受け取る | 設計・実装・確認結果を読み、新版の起動・照合・停止と、旧版の別起動を行う | [受取結果](06-operations.md)。ローカルの準備は進められるが、現場導入の判断材料は未充足 |

役割ごとの資料作成・質問・コード実行は実際にエージェントが行いました。一方、SEの回答、組織、依頼、受注データは架空です。人の合意、担当者の習熟、本番への配備を実施した記録ではありません。

## 進めてみて、Skillへ戻したこと

最初のDiscoveryは「CSVの細部は次で決める」という判断と一緒に、コードまで試す範囲も狭めてしまいました。[追加回答](input/discovery-feedback.md)を返し、**全体で確かめる成果物・最初に改善する受渡し・次工程で決める詳細**を分けてやり直しました。後工程へ送る詳細は、全体の対象外ではありません。この区別をDiscovery Skillへ戻し、修正版の手順で再実行しました。

また、DiscoveryとDefinitionのテンプレート表記では、Skillのフォルダ内にテンプレートがあると読めてしまいました。実際の保存先への相対リンクへ直しました。別の担当が資料だけで進めると、こうした入口の詰まりも見つかります。

今回の進め方は[工程ごとの独立した引継ぎ](../../../.agents/skills/discovery-facilitation/references/independent-delivery-rehearsal.md)へまとめています。日常の小変更すべてに役割分割を課す手順ではなく、一連の方法を確かめたい時に使います。

## 自分で動かす

Python 3.9以上とJDK 16以上を用意し、このディレクトリで実行します。追加のPythonパッケージは不要です。生成物は一時フォルダへ置き、サーバーは127.0.0.1の一時portで起動・終了します。

```sh
python3 replay.py
```

自己確認（既存Java 25、CSV整形5、既存HTTP検索9・不正4、CSV HTTP 17）、独立受入132項目を通常・最適化で各一回、別条件のCSV、旧版の検索再開とCSV未提供、停止後のport閉鎖を再現します。旧版は[元コミットとファイルのhash](baseline/source-manifest.json)を固定した架空fixtureです。稼働中の本番切替やデータ復旧は再現しません。

画面を開いて操作する場合は次を実行し、表示されたURLへ接続します。Ctrl-Cで停止します。

```sh
python3 implementation/run.py --serve
```

実ブラウザの自動確認も行いました。検索後に入力を変えてからCSVボタンを押すと、前の検索結果ではなく**現在の入力条件**で出力されること、保存名・BOM・内容、不正条件では保存せずエラーになることを確認しています。再現にはNode.js、Playwrightと対応ブラウザが別途必要です。既存Chrome等を使う場合は`FDE_BROWSER_EXECUTABLE`へ実行ファイルを指定できます。依存関係をこのスクリプトがインストールすることはありません。

```sh
python3 replay.py --browser
```

## 別条件で、もう一度確かめる

独立受入では、日本語・カンマ・引用符・改行が一つに入ったIDを復元しました。それだけでは「CRだけ」「LFだけ」でも引用されるかを切り分けられません。そこで[別のfixture](forward/AlternateCsvHarness.java)として、カンマだけ・引用符だけ・CRだけ・LFだけ・日本語だけの五つのIDを作り、独立したPython CSV parserで元の値と順序を復元しました。実行結果はPASSです。これは`replay.py`にも含みます。

今回、実装の条件違反は見つかりませんでした。検証の穴を補ったことと、機能の不具合を修正したことは区別しています。

## ここまで分かったこと

資料を引き継いだ別のエージェントが、条件を質問し、設計から実装し、独立した期待で照合し、受取手順を動かすところまでは通りました。ブラウザ、CSVの別条件、旧版の再起動もローカルで確認しました。

残るのは、実案件の入力許可・権限・担当者・支援能力を確かめ、現行の作業時間と品質を測ってから限定試行することです。実Excelの互換性、任意の入力の安全性、認証・DB・性能・本番復旧は未検証です。AIで手戻りが減るか、総負担が下がるかという効果は、この架空例のPASSだけでは判断できません。
