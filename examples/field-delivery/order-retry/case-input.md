# 注文再送の相談と、今回の合意条件

架空の業務・担当者・資料。実在の現場の観察や承認ではない。以下は演習用に先に
定めた入力で、Javaの実行結果とは区別する。

## 相談時の一件

営業担当者は注文登録後に画面の応答が途切れ、登録されたか分からず再送した。
登録側には二件の注文ができた。開発担当者は、その都度ログと注文を照合していた。
件数・時間・発生率の記録はない。既存システムのログやコードを実際に収集した
設定ではなく、この出来事自体が架空の入力である。

現行の仮説は「入力→登録→応答を受け取る。応答不明なら再送→担当者が照合」。
変更案は「一つの注文操作を識別し、再送でもその識別子を保持して同じ結果を返す」。
取消・注文変更は別の仕事で、今回の再送と混ぜない。

## D-01：演習の仕様責任者が合意した条件

| ID | 条件 | 独立に確かめる結果 |
| --- | --- | --- |
| R1 | 同じ注文操作の再送で二重登録を防ぐ | 同じ依頼を繰り返しても注文IDは一つ |
| R2 | 顧客IDと依頼キーの組で識別する | 別顧客の同キー、同顧客の別キーは別注文 |
| R3 | 同内容は初回の結果、異なる内容は競合 | 初回201、同品目・数量の再送200と同ID、異なる内容409。元の注文は不変 |
| R4 | 顧客ID・キー・品目のnull／空文字、数量0以下を拒否する | 400。保存せず、キーも予約しない |
| R5 | ローカル単一processで並行呼出しを扱う | 同じ依頼の作成は一度だけ |

201等は応答相当の値として扱う。今回HTTPサーバーは作らない。
この仕様の対象はメモリ上のサービス演習。実装担当はplain class、Java標準
ライブラリ、外部依存なしで作業し、数量の上限・役割・正規化規則を追加しない。

## D-02：実装前に渡す設計判断

- 顧客とキーの組で、最初の品目・数量と注文IDを保持する。
- 読取と作成を同じ排他区間に置く。別process・DB・永続化は対象外。
- 必要情報はこの資料と作成したコード・テスト。直接参照で足りるためRAG基盤は作らない。
- agentはローカルのコード・テスト作成と実行を担当し、仕様変更・外部送信・merge・
  本番操作の権限は持たない。仕様不足は演習の仕様責任者へ返す。
- 数量上限、空白文字、依頼キーの期限、永続化、認証、利用者の操作画面は未決定。
- 合格はR1〜R5のケースとの照合。実装者自身のテストだけで終えず、別の役が
  入力・返り値・副作用・並行呼出しを確認する。

## D-03：呼出し側を試した後の追加条件

最初は「呼出し側が同じキーを保持できる」を未確認の仮定としていた。
別キーで二回送る実行演習で二件作成されたため、依頼キーの発行・保持・再送を
サービスの外も含む条件として追加した。

今回の再試行では一つのユーザー操作でキーを作り、再送で同じ値を使う呼出し方を
試す。実際の画面への実装、保持期間、画面再読込や端末変更時の継承は未実装。
担当者が元の操作を識別できなければ、自動再送を止めて確認へ返す案を検討する。
実案件での決定をこの演習が代行するものではない。
