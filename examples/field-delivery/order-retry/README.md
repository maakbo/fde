# 注文を再送したら、二件できてしまった

営業担当者が注文を登録したところ、画面の応答が途切れた。登録されたか分からず
もう一度送ると、同じ注文が二件できた。開発チームはログと注文を見比べて調べていた。

この架空の相談に、fdeの聞取り・対象選択・条件整理・設計・実行・評価の手順を
通した。担当者の回答と合意条件は演習用に設定したもの。Javaのテストは実行したが、
実際の現場での効果や定着を測った結果ではない。

[相談から試行までの進め方](../../../.agents/skills/discovery-facilitation/references/field-delivery-loop.md)

## 最初に、何を改善するかを合わせる

「AIに注文を判定させたい」と始めず、最近困った一件を聞く。

> 登録ボタンを押してから、注文が確定したと判断するまで、何を見ましたか。

演習では「応答がないと登録済みか分からない」「再送後の二件を開発者へ問い合わせる」
という回答を置いた。発生頻度や調査時間は不明なので、深刻さを数値で補わない。
現行と変更案は[相談と合意条件](case-input.md)へ分けて残した。

候補は、担当者が毎回照合する、画面に登録状況を出す、登録側が同じ依頼を識別する、
AIがログから原因と対応案を出す、の四つ。最初に試す対象は同じ依頼の識別とした。
決定的なルールで処理でき、二重作成そのものを防ぐ仮説に直接関係するためだ。
ログ調査のAI化だけでは重複の発生は残る。画面の状態表示は補完策として残す。

製品の注文判定にAIを組み込む必要はない。一方、開発者の調査・実装・テストを
エージェントへ任せる余地がある。今回はこの開発業務への導入を試す。

## 「同じ注文」の意味を決めてから実装を渡す

品目と数量だけで同じ注文と判定すると、別の日の正当な追加注文も止めてしまう。
演習の仕様責任者は、顧客IDと依頼キーの組を一つの依頼と決めた。

同じ依頼・同じ内容なら初回の注文IDを返す。内容が変わったなら上書きせず競合に
する。別顧客のキーは衝突させない。これらをR1〜R5として、期待する結果と結んだ。
数量上限やキーの有効期限は、分からないまま新しい規則を作らない。

エージェントには処理の列だけでなく、二重登録を防ぐ目的、追加注文を妨げない理由、
競合時に元の内容を守る判断、実行範囲と質問先を渡した。これが今回の設計意図の引継ぎだ。

必要な根拠は一つの合意資料で足りるので直接参照とし、MCP・検索基盤・追加学習は
選ばなかった。Java標準ライブラリのメモリ上のサービスで最小範囲を確かめる。
HTTP・DB・実画面は作らず、本番の設計と取り違えない。

## 実装役へ任せ、別の役で確かめる

実装役は[OrderService.java](OrderService.java)と[自前のテスト](OrderServiceTest.java)を作成し、
Java 16.0.1で実行した。初回・同内容の再送・競合・入力拒否・顧客別の識別・並行呼出しを確認した。
返却時には、メモリが消えれば識別情報も失われること、呼出し側が同じキーを渡せるかは
未確認であることを残した。

その後、別の役が仕様条件から[受入テスト](AcceptanceTest.java)を作り、実行した。
実装内部のMapを読んで合否を決めず、返り値と後続呼出しで確かめた。

| 実際に実行した確認 | 結果 |
| --- | --- |
| 初回・再送・内容違い・顧客とキーの分離 | 期待どおり。競合後も元の注文を返す |
| null・空文字・数量0以下、その後に同キーで正常入力 | 拒否後にキーを占有せず、正常入力は作成できた |
| 同内容を120回、並行して呼ぶ | 一回だけ作成し、残りは同じ注文IDを返した |
| 再送時に違うキーを渡す | 二件作成された。サービス単体では防げなかった |
| 一つの操作のキーを保持して再送する | 同じ注文IDを返した |
| サービスを新しいインスタンスへ置き換える | 同じ依頼を再度新規作成した。永続化なしの限界を確認 |

## 単体が通っても、仕事ではまだ成立しない

再送のたびにキーを作り直す条件は、呼出し側の失敗を調べるため意図的に追加した
別条件である。実装が偶然バグを出したと装ったものではない。

この実行で、最初の「呼出し側が同じキーを保持できる」という仮定だけでは、業務の
二重登録防止を確認できないと分かった。そこで、誰がキーを発行・保持・再送するかを
設計へ戻し、一つの操作で同じキーを使う呼出し方を再試行した。結果は同じ注文IDだった。
この条件を[追加条件D-03](case-input.md)へ残し、再送を扱う設計手順にも戻した。

ただし、実画面・通信タイムアウト・端末変更・processを跨ぐ保存は試していない。
サービスを作り直すと再登録される結果もあるので、この実装で本番の二重登録を防げるとは
判断しない。DBの一意性とトランザクション、既存注文への影響、監視・復旧を別途設計する。

## 品質・使いやすさ・効果を分けて判断する

| 観点 | 今分かったこと | まだ分からないこと |
| --- | --- | --- |
| 品質 | 限定したサービス条件と呼出し方を実行検証した | HTTP・DB・実画面・再起動・負荷・障害時の正しさ |
| 定着・仕事への適合 | エージェントが条件から実装・実行結果と限界を返せた | 実際の開発者がレビューし、継続利用できるか。営業が再送を判断できるか |
| 業務効果 | 効果を測る対象が、重複注文・照合・修正・レビュー負担だと整理できた | 現状値、導入後の発生率と担当者の負担、運用保守費用 |

今回の判断は「開発者のレビューと次の限定試行へ進める。本番展開はしない」。
次は、許可された検証環境で実際の呼出し側と永続化を含め、タイムアウト後の再送と
再起動を試す。仕様責任者はキーの有効期間等を、運用担当は監視と切戻しを確認する。
現場の記録がなければ改善率は出さない。

## 同じ結果を確かめる

Java 16以上のJDKとPython 3を使う。外部ライブラリ・ネット接続は不要。
コンパイル結果は一時ディレクトリに置く。

```bash
python3 examples/field-delivery/order-retry/run.py
```

自前テストは`PASS all 5 test groups`、受入テストは
`PASS all independent acceptance groups; production readiness NOT established`で終了する。
`REPRODUCED caller failure`と`OBSERVED limitation`は、上記の失敗条件と適用限界を
確認した出力で、成功から除外して隠すものではない。
