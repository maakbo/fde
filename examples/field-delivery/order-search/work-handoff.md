# 設計がまとまったら、次の作業へ渡す

[受注検索の機能追加](README.md)で、SEがまとめた[要件](requirements.md)と[設計](design.md)を
次の担当へ渡す。一回ごとの長い説明に頼らず、何を開始してよく、何が足りなければ戻すかを決めた。
ここで扱うのは開発チームの作業の起動と受渡し。検索画面の入力条件とは区別する。

## どこまで任せるか

要件の採否とリリースは担当者が判断する。調査・実装ではエージェントが結果を見ながら
次の作業を選び、コンパイルとテストは決めたコマンドで実行する。一つの案件の中でも
任せ方を組み合わせる。高度な自律性を得るためだけに、工程や権限を増やさない。

今回は、設計を渡す担当の直接依頼を起点にした。設計の状態変更をイベント通知で受ける案や、
定時に準備済み案件を拾う案もあるが、外部システムへの接続はまだ行っていない。

| 処理 | 入力と担当 | 次へ渡す成果 |
| --- | --- | --- |
| 作業を受ける | 担当者の依頼ID・対象と版・今回の許可範囲 | 入力不足・対象外、または着手できる範囲 |
| 必要な情報を揃える | 要件R1〜R6、設計理由、plain classの作法、対象コード、実行方法 | 今回の作業用の文脈。無関係な過去会話は含めない |
| 実装・検証を進める | エージェントが合意範囲で作業し、通常ツールで実行 | 差分・根拠・実行結果・未実施。前の実装と検証は[レビュー記録](review-and-release.md)を参照 |
| 結果を返す | レビュー担当が条件と実物を照合 | 修正、追加確認、受入の判断材料。リリースの承認とは分ける |

## 後工程で使う値を曖昧にしない

| 値 | 意味と入力元 | 検証と保持 |
| --- | --- | --- |
| work_id | 一回の開発依頼の識別子 | 空でない文字列。今回の実行結果に引き継ぐ |
| conditions_confirmed | この実行範囲で要件を確認したという依頼側の宣言 | bool。文字列のfalseを真と扱わない。資料のsnapshotだけでtrueにしない |
| unresolved | この作業を止める未決定事項 | 文字列の配列。未決定があればSEへ戻す |
| action | 今回許された作業 | この実行例はverify_localのみ。merge・本番操作は対象外 |
| sources | 記録対象とした正本・コード・実行器・受渡し契約の版 | ファイル名とSHA-256。実行前後で版が変われば再確認 |
| state | 今の進行状態 | 着手可能、入力待ち、対象外、検証失敗、review待ちを区別する |

これらは一回の仕事の状態であり、正式な要件を保存する正本ではない。
宣言のboolは実際の承認者の認証を代行しない。外部入力を信頼して操作できるサービスではない。

## 分岐と、次に返す相手

入力不足・型違いを先に確認し、未設置の起動方式や対象外の操作なら実行しない。
次に要件の確認・未決定・条件ID・資料の版を確かめる。これらが揃った場合にだけ、
限定したローカル検証へ進む。AIの自信度では進行を決めない。

| 条件 | 返す状態と相手 |
| --- | --- |
| 日付の意味等が未決定、値の型が違う、要件の版が変わった | needs_input。SEまたは開発者が条件を合わせる |
| 未設置のWebhook起動、本番操作等を要求、実行環境が未対応 | blocked。運用・権限・環境の設計へ返す |
| 許可範囲の検証で不合格 | failed。結果を開発者へ返す。無制限に繰り返さない |
| ローカル検証が通った | awaiting_review。結果と版をレビュー担当へ返す |

受注検索の状況・日付は、各注文を結果へ通すかのフィルタ。一方、上の表は開発作業を
どこへ渡すかの分岐。同じ「条件」でも役割が違う。検索0件を作業の失敗とは扱わない。

## 引継ぎの条件を、実際に動かした

[workflow.py](workflow.py)は、この受渡しのうち入力・版の確認、作業用の文脈の組立て、
既存のローカル検証の実行、review待ちへの返却を動かす小さな実行例だ。
LLM・イベント基盤・認証機能は組み込んでいない。Javaの実装を自動生成する機能ではなく、
前の実装成果を次工程へ渡す条件を確かめる。
実行例のexecuteは、子プロセスをまとめて停止できるPOSIX環境（Mac/Linux）に限定する。
Windows等では実行前にblockedを返し、処理を開始しない。OS間の運用互換性は検証していない。

```bash
python3 examples/field-delivery/order-search/workflow.py --new-request > /tmp/search-work.json
```

作成した依頼のaction・条件・正本の版を確認し、この演習のローカル検証へ進める時だけ
conditions_confirmedをtrueにする。生成直後はfalseであり、自動的な承認にはしない。

```bash
python3 examples/field-delivery/order-search/workflow.py /tmp/search-work.json
python3 examples/field-delivery/order-search/workflow.py /tmp/search-work.json --execute
```

最初のコマンドは作業用の情報を返す。二つ目は固定のJava・HTTP検証を実行し、結果と
資料の版をreview待ちとして返す。資料が変わった場合は、その変更を確認して依頼を作り直す。
同じ依頼を機械的に承認し直す手順にはしない。

別条件の自動確認は次で実行できる。テスト中の成功・失敗の一部は仮の検証器で作る
分岐確認であり、Javaの実行結果は上のexecuteで別に得る。

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s examples/field-delivery/order-search -p test_workflow.py -v
```

資料の版、未決定、型、権限、検証結果を別条件で確かめる。復帰する時も、作業ID・
今の版・残件を確認して同じ目的から続ける。継続中のjob管理、重複排除、承認者認証、
外部接続・定時実行の運用は、このローカル実行例の検証外。

## 試した結果を、次の作業へ戻す

| 実行した確認 | 観測した結果 |
| --- | --- |
| 未確認のまま生成した依頼 | needs_input。コード実行を始めなかった |
| この演習の条件を確認した依頼 | 実際のJava25チェックとHTTP検索9ケース・不正4種等を実行し、awaiting_reviewへ返した |
| 型違い・未決定・対象外・資料の変更 | 分岐テストで実行を止めた。仮の検証器を使う確認と、上のJava実行は別の証拠 |
| 実行器・引継ぎ契約だけを変更 | 依頼の版が合わなくなり、再確認へ戻すことを確認した |
| 未対応のOS | プロセスを起動せずblockedへ返すことを確認した |

最初の実装では、実行器自身の版を確認対象から落としていた。独立レビューで指摘され、
引継ぎ契約と実行器も対象へ加えて再試行した。未対応環境を検証失敗へ混ぜていた状態も、
対象外として返すよう直した。

別担当には、同じ開発案件の次の「CSV出力追加」で手順を使ってもらった。
検索の条件を参照しながらCSV固有の条件を分け、未確認の文字コード・Excelでの開き方は
SEへ戻し、設計レビュー用の記録と次担当への文脈を作れた。CSV実装・利用者確認は未実施。
その記録で製品側の利用と開発側の親業務が一箇所混ざったため、開発業務を親として
対象機能を分ける問いをSkillへ戻し、同じ記録を再点検した。
