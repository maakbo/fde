# 検索条件を、画面・API・テストへ引き継ぐ

[要件R1〜R6](requirements.md)を正本にし、同じIDで設計と確認をつなぐ。
仕様上の不明点はSEへ返し、実装役が新しい業務ルールを作らない。

| 対象 | 設計と理由 | 要件と確認 |
| --- | --- | --- |
| 画面 | 状況・開始日・終了日を入力し、検索後に件数とID・受注日・状況を表示 | R1〜R5。0件・入力不正の表示も用意 |
| API | GET /orders?status=NEW&from=2026-10-02&to=2026-10-04。空の値は未指定 | R1〜R3・R6。JSONにcountとorders、入力不正は400 |
| 検索処理 | LocalDateで両端を含む比較、状況とAND。日付降順・ID昇順 | R2〜R4。判定を生成AIへ依存させない |
| データ | ID・受注日・状況の固定5件を読取専用で使う | R6。実データやDBの変更を避け、条件照合に集中 |
| 検証 | 実装役のJavaテストに加え、別役がHTTPの条件と返り値を照合 | R1〜R6。コードの自己テストだけで合格にしない |

## 実装役への受渡し

Java 16以上の標準ライブラリで、小さな検索サービスとlocalhost限定のHTTPサーバーを作る。
GET / は検索画面、GET /orders は検索JSON。実行ポートは指定または自動割当を使える。
生成コードはplain classで、外部依存を足さない。一般利用向けのサーバー設計ではない。

根拠はこの設計と要件で直接参照できるため、RAG・MCP・追加学習を導入しない。
エージェントはローカルのコード・テスト作成と実行、結果の返却を行う。
返却物はコード、R1〜R6との対応、実行方法・結果、未実施と制限。
担当者が設計・差分・テストの期待を確認し、採用やリリースを判断する。

未知の検索項目や同じ項目の重複は、試作上は400で拒否する設計案とした。
これはR1〜R6から必然的に決まる業務仕様ではない。実システムの既存APIとの
互換性を確認してから採否を決める。実際のSEが承認した設定にはしない。

## 検証用データ

| ID | 受注日 | 状況 |
| --- | --- | --- |
| O-101 | 2026-10-01 | NEW |
| O-102 | 2026-10-02 | SHIPPED |
| O-103 | 2026-10-03 | NEW |
| O-104 | 2026-10-03 | CANCELLED |
| O-105 | 2026-10-04 | NEW |

この5件の条件別の期待値を実装前に決める。例：NEWかつ10月2日〜4日はO-105、O-103。
全状況かつ10月3日〜3日はO-103、O-104。
