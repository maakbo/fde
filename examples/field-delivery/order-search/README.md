# 受注一覧の機能追加を、要件定義からリリース準備まで進める

営業担当者から「受注一覧を、状況と期間で絞り込みたい」という依頼が来た。
SEが要件を確認し、設計へまとめ、開発者が実装する。テスト担当が結果を確認し、
レビューを経て、運用担当へ変更内容を引き継ぐ。通常の機能追加を進める架空の開発案件だ。

この一件にfdeの手順を使い、各工程でAIへ何を任せ、どんな成果を次へ渡せるかを試した。
担当者の発言と合意は演習用に設定したもの。コードとテストは実行し、実在のチームでの
利用・効果測定とは区別する。

## 開発チームの仕事を、依頼からたどる

まず聞くのは、「この機能を、誰がどこまで具体化して、次へ渡しますか」。
演習では、SEが要件と設計をまとめ、開発者がコードと単体テストを作り、テスト担当が
要件への適合を確認する分担を置いた。受入とリリースの採否は担当者が決める。

現行の進め方では、それぞれが前工程の資料を読んで、確認事項・実装・テスト項目を
個別に作る。変更案では、担当者が判断する条件を共通のIDで残し、エージェントが
設計案・コード・テストの対応を引き継ぐ。人は、業務条件と設計の採否、受入を判断する。
この現行と変更案は架空の設定で、実際の現場を調べた結果ではない。

| 担当する仕事 | AIへ任せること | 担当者が確認し、次へ渡すもの |
| --- | --- | --- |
| 要件定義 | 依頼から確認事項と受入例を整理 | 利用者が望む動作、未決定、要件R1〜R6 |
| 基本設計・詳細設計 | 画面・API・検索処理・テストの案を対応付ける | 設計の選択と理由、規約、実装範囲 |
| 実装・単体テスト | 設計を読み、コードとテストを作成・実行 | 差分、変更理由、実行結果、未実施 |
| 結合確認・レビュー | 画面とAPIの条件、要件とテストの対応を整理 | 独立した確認結果、指摘への対応、残件 |
| リリース準備 | 変更内容と確認・切戻しの手順を下書き | 運用担当の確認事項と開始判断に必要な材料 |

今回はこの受渡しを一件で通す。画面作成だけ、テスト生成だけの効果には切り分けず、
要件が設計・コード・検証に保たれたか、次の担当が判断できる材料を受け取れたかを見る。

## 要件定義で、検索の意味を合わせる

最初の依頼は「状況と期間で絞りたい」までだった。AIが次の確認事項を下書きし、
SEが利用者へ聞く想定で具体化した。

> 期間は受注日ですか、出荷日ですか。終了日当日の注文も含めますか。
> 条件を入れなかった場合と、見つからなかった場合はどう表示しますか。

この演習では「受注日で、開始日・終了日を含む」「未指定は全件」「0件は正常」と
回答を設定した。[要件](requirements.md)へR1〜R6と受入例を残す。担当者の回答を
待たずに、実装役が日付や取消済みの扱いを推測して確定させない。

## 設計の理由を、実装とテストへ渡す

SEは、状況・開始日・終了日を持つ検索画面と、読取専用の検索APIを設計する。
日付は両端を含み、状況と期間をANDで絞る。結果は受注日の新しい順に並べる。

AIが[設計](design.md)に要件IDとの対応を付けた。例えば、R2は日付比較と境界日の
テストへ、R5は0件の応答と画面表示へつながる。単に「検索処理を実装して」と渡さず、
期待する結果とその理由を、コード・テストを作る担当へ引き継いだ。

試作はJava標準ライブラリのローカル画面・APIと架空データ5件に絞る。
検索判定は通常コードで行い、AIは開発者の作業を支援する。必要な根拠は要件と設計を
直接読めるため、検索基盤や追加学習は使わない。

## 設計を渡し、実装・検証・レビューを進める

実装役には要件と設計、Javaの規約、ローカル実行の範囲を渡した。
別の確認役は同じ要件から受入ケースを作り、実装役のテストと分けて確認する。
実装結果と確認内容は[レビューとリリース準備](review-and-release.md)へつなぐ。

要件確認で曖昧だった「期間」は、対象日付と両端の扱いを決めてから実装へ渡した。
その判断を、同日検索・片側だけの期間・状況との組合せでも確かめる。
このように、合意した一例だけでなく、別条件で同じ要件が守られるかを見る。

## 次の担当が、使える成果を受け取れたか

今回の品質確認は、要件R1〜R6、Javaの単体テスト、ローカルHTTPを通す結合確認の対応で行う。
画面の操作感、実データ量での性能、認証・閲覧制限、実際の利用者による受入は別途必要だ。

開発者が設計意図を説明できるか、レビューで確認・修正が増えていないか、普段の仕事で
継続して使えるかは実チームで測る。この演習だけでは工数削減や定着を達成したとは言わない。
リリース準備の材料は作るが、本番の接続・配備や正式な開始判断は行わない。

実行方法と確認結果は[レビューとリリース準備](review-and-release.md)を参照。
