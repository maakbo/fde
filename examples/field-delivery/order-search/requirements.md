# 受注一覧の検索条件を合わせる

架空の開発依頼と確認回答。実在する利用者の発言・承認ではない。
担当者を想定した机上の確認と、後で実行するコード検証は分けて扱う。

## 開発依頼

営業担当者が受注一覧から、出荷状況と受注日を指定して注文を探せるようにしたい。
SEが依頼を要件と設計へまとめ、開発者が実装し、テスト担当が結果を確かめ、
運用担当へ変更内容と確認方法を渡す、通常の機能追加案件とする。

開発チームは、要件メモから設計・コード・テストへ同じ条件を引き継ぎたい。
エージェントには確認事項の整理、設計・実装・テストの下書きと実行を任せ、
業務条件の決定、設計の採否、受入とリリース判断を担当者に残す。

## 要件確認で具体化したこと

最初の依頼の「期間で検索」だけでは、対象の日付と端の扱いが決まらない。
SEが「受注日ですか、出荷日ですか。終了日当日の受注も含めますか」と聞き、
この演習では受注日・両端を含むと回答する。未指定時の対象、0件の表示、
複数条件の組合せも、実装者の推測にせず以下へ反映した。

| ID | 合意する振る舞い | 受入例 |
| --- | --- | --- |
| R1 | 状況はNEW（未出荷）・SHIPPED（出荷済み）・CANCELLED（取消済み）。未指定は全状況 | NEWだけ指定すると未出荷だけ。未指定なら取消済みも含む |
| R2 | 受注日の開始・終了は任意、指定した日を含む。日付はYYYY-MM-DD。開始が終了より後なら入力エラー | 10月3日〜3日なら3日分。開始だけなら以降、終了だけなら以前 |
| R3 | 状況と期間はAND条件 | 未出荷かつ10月2日〜4日の注文だけ |
| R4 | 受注日の降順、同日は受注IDの昇順 | 10月4日→3日→2日。同じ3日はID順 |
| R5 | 0件も正常結果。件数と「該当する受注はありません」を表示 | 条件に合う注文がなくてもエラーにしない |
| R6 | 検索では注文を変更しない。未定義の状況・不正な日付をエラーとして返す | 検索前後で元データが不変。不正条件は400、正常検索は200 |

## 範囲と担当者の判断

検索の基本動作を確かめるため、架空データ5件を使うローカル画面とAPIを作る。
認証、顧客ごとの閲覧制限、DB、ページング、タイムゾーン、検索性能目標は
実システムの条件がないため未決定。この試作の全件表示を、本番の権限仕様にしない。
外部通信・実データの収集・本番反映は行わない。

要求→設計→実装→単体・結合確認→レビュー→リリース準備まで成果を渡す。
実際の営業担当者による受入、実システムへの組込み、正式リリースは未実施。
