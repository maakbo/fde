# 設計を渡すところから、チームでAIを試す

[受注一覧の検索機能追加](README.md)を進める開発チームが、設計から実装・テストへの
引継ぎにAIを使う。狙いは「コードを早く出す」だけでなく、設計の判断を保ち、
次の担当が確認できる成果を渡すことだ。

担当者の発言と分担は架空の演習設定。実在のチームで合意した記録ではない。
ローカルのコード・検証を実行した事実と、チームで使えるかという仮説を分ける。

## まず、レビューする人の仕事を聞く

開発者は「設計を読み直してテストを考えるところを手伝ってほしい」と話す。
レビュー担当は「生成された量が増えて、結局こちらの確認が増えないか」と心配する。
SEは「期間の意味を勝手に解釈されると困る」と言う。

進行役は「実装の下書きは助けになるかもしれない。でも、仕様の推測と確認負担の移動を
避けたい、という理解で合っていますか」と返す。賛成か反対かを聞く前に、
[日付の意味と0件の扱い](requirements.md)のような具体例を一緒にたどる。

最初は、SEが確認した要件・設計を入力に、ローカルの実装案と検証結果を受け取る範囲にする。
コードの採否やリリースまでAIへ任せない。製品へAI機能を追加する試行でもない。

## 誰が決め、誰が手を動かすか

| 仕事 | AIと通常ツールの担当 | 人が判断し、次へ渡すこと |
| --- | --- | --- |
| 要件・設計の準備 | 確認事項と要件・実装・テストの対応を下書き | SEが仕様と未決定を確認。確認できない条件は実装役へ推測させない |
| 実装・検証 | 許可されたローカルで差分を作り、テストを実行 | 開発者が規約と根拠を説明し、差分・結果・未実施を渡す |
| レビュー | 条件との対応と確認材料を整理 | 確認役が独立に適合を調べ、採否・差戻しを返す |
| 利用範囲と支援 | 残件と選択肢を整理 | チーム責任者が試す範囲、担当時間、相談先、停止と再開を決める |
| 本番・外部接続 | 今回は行わない | 実際の権限者が環境・データ・運用の条件を別に確認する |

この試行では既存の開発チームで役割を分ける案にした。新しい推進部署は作らない。
共通の環境・情報・ツールのルールは既存の管理担当へ確認し、その内側の作業の工夫は
チームで決める。これは演習上の案であり、現場の規程や管理者の権限を確認したものではない。

レビュー担当に資料の読取権限と時間がないなら、確認欄だけを置いて始めない。
代替担当か対象を狭める案を責任者へ返す。止めた場合は従来の人の実装・確認へ戻す。
実際のチームでの開始は、許可環境・担当時間・相談先を確認してから判断する。

## 一件を受け取り、自分で確かめて返す

練習では、SE役が要件R1〜R6と[設計](design.md)を渡す。開発役は「受注日を両端込みで
比較する」「0件は正常」「plain classを使う」と説明してから、実装とテストの対応を見る。
確認役は、終了日当日の注文や該当なしの場合を要件から選び、期待と出力を比べる。

既存の実行可能な[作業引継ぎ](work-handoff.md)を使うと、未確認のままの依頼や資料の
変更は確認へ戻り、検証成功はレビュー待ちへ返る。実行器と引継ぎ手順自身の変更も
版確認へ含めた。成功の表示だけで、確認役の判断を済ませたことにはしない。

| 確かめたこと | 証拠と限界 |
| --- | --- |
| 要件とコードの適合を調べる | Java25チェック、独立HTTP検索9ケース・不正4種などを実行。実DB・認証・実ブラウザ操作は未確認 |
| 引継ぎの進む／戻すを調べる | 10件の分岐テストとローカル実行。組織の承認や実際の担当者の習熟は測っていない |
| 別条件へ適用できるか考える | CSV出力追加の机上演習。文字コードを未決定で残し、製品利用業務と開発側の親業務の混在を直して再試行。CSV実装は未実施 |

実在の担当者が一人で受け取り、根拠を説明し、誤りを直し、次へ渡す練習は未実施だ。
現場ではこの受渡しを本人にやってもらい、説明を聞いたことと自分でできたことを分ける。
支援は、その結果に応じて資料・練習・時間・権限・相談先のどこを補うか決める。

## 試す回数より、受渡しがよくなったか

チームの目標案は「設計意図を保った差分を、確認できる状態で次へ渡す」。
AIの利用回数を個人の評価へ使う案は採らない。レビューや根拠整備も成果を支える仕事として扱う。
今回は現場の比較値がないため、以下の数値目標は未設定、結果も未測定とする。

| 見たいこと | 現場で集める根拠と、その後の判断 |
| --- | --- |
| 品質 | 同じ要件範囲で重大欠落・差戻しと原因を確認役が記録。許容できない仕様誤りなら採用を止め、要件・設計・実装へ戻す |
| 利用 | 対象となる引継ぎの総数、利用・見送り・中断と理由を記録。利用できない原因が時間や権限なら、研修を増やす前に責任者が調整 |
| 効果 | 同程度の機能追加について、準備・実装・確認・修正・待ちの時間と受入後の手戻りを比較。片方の短縮をチーム全体の削減にしない |
| 理解と支援 | 担当者が説明・修正・引継ぎをできたか、何に困ったかを対話で確認。失敗の報告を本人の不利益にする評価へ使わない |

実際の限定試行を始める前に、責任者と実行・確認役が対象、観測期間、記録担当、
許容しない失敗を決める。各受渡しで負担と見送り理由を残し、終了時に続行・修正・停止を判断する。
機能の難しさや担当者が違えば比較の限界も残す。準備や教育・保守を含めて得かを確かめる。

## チームからの問いへ、今分かる範囲で答える

「間違うのでは」には、独立確認と差戻しを説明し、今回のテストと未検証を示す。
「本番でも使えるか」には、実DB・認証・負荷・復旧は未確認と返す。
「社内資料を渡せるか」には、今回は架空資料だけであり、実資料の送信許可は別の確認だと返す。
「得なのか」には、開発者だけでなく確認役の時間も測るまで未判断と返す。
「誰が責任を持つか」には、仕様、コードの採否、試行開始、停止・再開の担当を分け、
実際の契約・社内規程に関わる判断は権限者へ渡す。

今できるのは、この架空例で受渡しを練習し、現場の限定試行に必要な条件を用意するところまで。
現場導入・工数削減・定着を達成したという結論にはしていない。
