# 実装結果を確認し、リリースの準備へ渡す

[要件](requirements.md)と[設計](design.md)を受け取った実装役がコードとテストを作り、
別の確認役が要件からHTTP受入ケースを作った。どちらも演習中のAIによる作業で、
実在のSE・利用者・運用担当による承認ではない。

## 工程ごとの成果

| 仕事 | 次の担当へ渡した実物 | 確認の観点 |
| --- | --- | --- |
| 要件定義 | [要件R1〜R6](requirements.md) | 状況、対象日付、境界日、未指定、0件、並び順 |
| 基本設計・詳細設計 | [画面・API・検索処理の設計](design.md) | 要件との対応、選択理由、規約と対象外 |
| 実装 | [検索サービス](OrderSearchService.java)、[画面・API](OrderSearchServer.java) | 読取専用、条件の解釈、返却形式、localhost限定 |
| 単体・実装役の確認 | [Javaテスト](OrderSearchTest.java) | 通常と別条件、元データ不変、HTTP応答 |
| 結合確認 | [独立したHTTP受入](acceptance.py) | 要件から別に作った入力と結果、画面の配信 |
| 再現と引継ぎ | [実行スクリプト](run.py)と下の準備事項 | 同じコードで確認できるか、実システムへ進むための残件 |

## レビューで合わせ直したこと

文書レビューで、設計担当をSEとする本文と、開発者とする要件の不一致が見つかった。
この案件ではSEが要件・設計、開発者が実装という分担に統一した。

コードレビューでは、plain classという作法に対してrecordが使われていた。
実装役へ差し戻し、通常のclassへ修正してテストをやり直した。業務条件と同様に、
チームが保守するコードの作法も受渡しとレビューの対象になる。

未知・重複した検索項目を400にする扱いは、要件から必然的に決まる規則ではないため、
試作上の設計案として明記した。実システムの互換性確認前に正式仕様へ格上げしない。

## 同じ開発成果を確かめる

Java 16以上のJDKとPython 3で実行する。外部ライブラリは不要。
HTTPの接続先はこの試作の127.0.0.1のみで、コンパイル結果は一時ディレクトリに置く。

```bash
python3 examples/field-delivery/order-search/run.py
```

Java 16.0.1で実際に実行し、次を確認した。テスト成功を、正式な利用者受入や
本番の品質保証へ格上げしない。

| 実行した確認 | 結果 |
| --- | --- |
| 実装役のJavaテスト | 25チェック通過。別データでの並び順・日付境界も含む |
| 独立したHTTP検索 | 9ケース通過。全件、状況、同日、片側期間、AND条件、0件 |
| 入力と読取専用の確認 | 4種類の不正条件は400、検索前後のデータ不変、POSTは405 |
| 画面の配信 | HTMLと検索項目・結果表示用の記述を確認。実ブラウザ操作は未確認 |

画面を開いて確認する場合は次を使う。テスト後に表示されるlocalhostのURLを開き、
確認後にCtrl-Cで終了する。

```bash
python3 examples/field-delivery/order-search/run.py --serve
```

実ブラウザの操作感・アクセシビリティと、実際の利用者の受入は別に確認する。
HTMLの配信確認だけでは、画面の操作確認を完了したと扱わない。

## リリース準備として渡すこと

今回の試作は検索の基本動作を確かめるものなので、そのまま本番へ配備しない。
運用担当へは、次を実システムの条件に合わせて具体化するための材料として渡す。

- 変更内容：受注一覧の状況・期間検索。要件R1〜R6と、実装・テストの対応。
- 組込み：既存画面・API・DB・認証・顧客別閲覧権限との接続。担当と実施環境は未決定。
- 検証：利用者による検索・0件・入力エラーの確認、実データ量での応答、既存機能の回帰。
- 配備と切戻し：実システムの変更単位・配備方法・旧画面/APIへ戻す方法を担当者が決める。
- 運用：検索失敗・応答・アクセス権をどう観測し、誰が判断するか。手順と問合せ先を確認する。
- 開始判断：SE・利用者・運用担当が残件と結果を確認する。この演習では正式判断を行わない。

## 開発業務への導入として、次に確かめること

要件から設計・コード・検証へ条件を引き継ぎ、指摘を戻す一周を試した。
次は許可された開発環境で、開発者が成果をレビューできるか、要件や規約の修正を
次の担当へ保てるかを確かめる。確認・修正を含む負担、実際の利用理由、品質を見る。
工数短縮・定着・本番効果は、この架空の一件だけから数値化しない。
